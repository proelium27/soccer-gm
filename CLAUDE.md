Audit scripts live in `scripts/` (e.g. `divisionAudit.ts`, `weakLeaguesAudit.ts`) — run with `tsx`.

**Open work queue from real player saves: `docs/player-save-findings.md`.** Six saves sent in by players were audited 2026-08-17; that file is a *fix queue*, not a design doc — each item carries evidence, root cause with line refs, fix shape and gating, and they're independent of each other. Two things there generalize beyond the individual bugs: **(a) real players reach season 75**, roughly triple the 20-30 season horizon every dynasty audit in `scripts/` gates at, and at least one invariant (the country strength ladder) fails only out there while the 20-season gate stays green; **(b) `scripts/playerSaveAudit.ts`** audits any exported save for size/integrity/balance, and reads the **raw parsed file rather than going through `migrateLeague`** — migration repairs and culls, so a migrated league tells you what the game would fix, not what the player has. Player saves live in `leaguesaves/` (gitignored, other people's data, never committed) and exist only on the machine they were sent to.

**EA FC roster converter** (`scripts/eafcRosterConvert.ts` + `scripts/eafc/`, docs in `docs/eafc-import.md`): turns an EA FC player CSV into a roster file for the Leagues → Import Custom League flow, for playing with real clubs/players. Dev-only and **never shipped or committed** — the CSV and generated JSON are gitignored, the game keeps shipping fictional clubs (trademark caution). The load-bearing part is the rescale: EA overalls are **rank-matched onto a freshly generated world's OVR distribution** rather than used raw (a generated world spans ~23-81 and only reaches 90+ via progression; EA's top flights run 47-91), so the imported world carries the same OVR distribution a generated one does and the anti-inflation equilibrium is untouched. Per-skill ratings come from EA's attributes (the two sets are both 1-99 and mostly namesakes) then get uniformly shifted to hit the rescaled overall, so players keep their individuality; potential gets its *own* curve (different distribution — reusing the overall curve gave every wonderkid an identical ceiling). **Leagues are matched by `league_id`, never by name**: names collide across federations and the exports drop the country prefix ("Bundesliga" is Germany's *and* Austria's, "Premier League" England's *and* Ukraine's), which silently imported 12 Austrian clubs into the German top flight — `scripts/eafc/inspectLeagues.ts` audits a dataset for exactly this before you trust it. **Coverage is now all 16 competitions** (Belgium and Turkey added 2026-08-12; `COVERED_COMPETITIONS` is derived from the rules so the "which divisions stay fictional" report can't drift). Two traps that generalize: **(a)** FC26 has *three* leagues named exactly "Pro League" — Belgium's (4), Saudi Arabia's (350), the UAE's (2013) — so Belgium has **no bare name rule at all** and is reached by id only; a `pro_league` pattern would have put Al Hilal in the Belgian top flight. **(b)** `normalizeLeague` **must not fold accents**, however much `s_per_lig` ("Süper Lig") looks like a bug: folding was tried and measured to hand Brazil's "Série A" (14 clubs) to Italy and "Primera División" to Spain, since both then match a pattern *and* are unique names in the file, so the unambiguous-name fallback trusts them — 19 foreign clubs, silently. Turkey carries the mangled form as a pattern instead. No dataset seen so far has Belgium's, Turkey's or Portugal's second tier, so those resolve by name only and stay fictional unless a names file fills them. `applyRosterFile` realigns each slot's shuffled `academyBase` (`realignAcademyBases`, 2026-08-10): imported clubs are sorted by `computeTeamRating` and handed *that same group's* existing anchors in descending order, so a superclub can't inherit a weak youth anchor and drift over a long dynasty. **It's a permutation, not a recalculation** — same multiset, reassigned once, nothing derived from the imported ratings — so the anti-inflation equilibrium is untouched (a test pins the multiset). Only squad-*replaced* clubs take part, so a partial import can't degrade untouched clubs; the corollary is an imported club can only take an anchor another imported club held.

**Imported clubs draw no crest art (2026-08-10, user call).** `ClubCrest` keys crest images by **tid — a slot** — which is right for the shipped fictional clubs (a club's name is editable, its tid never changes) and wrong the moment a slot becomes a real club, since the badge then belongs to the club it displaced. `applyRosterFile` flags every slot the file *named* (squads or not — an identity-only entry is exactly the stale-crest case) with `StoredTeam.importedIdentity`, and `CrestArtProvider` suppresses art for those tids. **A context, not a prop**, because `ClubCrest` is rendered from 14 call sites that mostly hold only a tid; one of them forgetting the flag would show a wrong badge on that surface alone — the kind of bug that hides. Wrapped around the in-league shell (`Layout.tsx`) *and* the new-league club picker, so the preview matches the save. Optional field → no migration (absent = not imported). Knock-on: colors become the club's entire identity, so `mergeRosterFiles` now adopts real colors from the names file (the converter hashes them out of the club name — Liverpool came out purple).

**Roster import is creation-only (2026-08-10, user call).** The per-save "Import Teams" button is gone; the entry point is Leagues → **Import Custom League** → `/new-league?roster=1`. Reason: a roster file *replaces squads*, and `applyRosterFile` drops every replaced player who has no recorded stats — on a save in progress that silently deletes real careers, stat lines and the transfer history keyed to those pids. At creation there is nothing to destroy. Three consequences worth knowing: **(a)** `applyRosterFileToNewLeague` (`teams/rosterImport.ts`) is the entry point, and it re-runs `assignAIFormations` + `reconcileScoutingObserved` after the import, because `createLeagueState` derives both from squads the import then throws away (formations picked for deleted players; the user's fog-of-war stamps pruned along with the pids they pointed at, leaving the imported squad permanently unscouted). It is **only** safe on a fresh league — re-stamping scouting resets every observation to season 1, which mid-save hands the user a fully-scouted squad. **(b)** `resolveRosterSlots` now takes a structural `RosterSlotWorld` (`{competitions, teams}`) rather than a `LeagueStore`, so the club picker can resolve a file against `worldTeamSlots()` — the slot layout of a save that doesn't exist yet — and show real club names *before* paying 4s to generate 6000 players. `worldTeamSlots` duplicates `generateWorld`'s tid layout by necessity; `rosterImport.test.ts` pins it against a real generated world so the two can't drift. **(c)** Crest art does **not** follow an import (`ClubCrest` keys images by tid, i.e. by slot), so an imported club wears whatever crest its slot had. Colors do follow.

**Roster import takes several files (2026-08-11).** A world is authored a league at a time (an AI won't emit twelve competitions of squads in one answer), so both pickers — Leagues → Import and the `?roster=1` screen's "Add another file" — are `multiple` and the selected files are folded by `combineRosterFiles` (`teams/rosterFile.ts`) into the single file `applyRosterFileToNewLeague` applies. Competitions are independent, so combining is concatenation in load order; the one ambiguous case, two files claiming the same competition, can't be interleaved (clubs map *positionally* onto slots) so the later file wins outright and the collision is reported. `PendingRoster` therefore hands over `files[]`, and `NewLeague` keeps the loaded `sources` so later picks add to them rather than replace. A file that won't parse is skipped and named on the picker screen; on the Leagues screen it stops the batch instead, because that screen is left behind on the way to the picker and any error it raised would go with it.

The first `npm test` after any `src/core` change rebuilds the cached test worlds (see `test/` below); later runs reuse them. `SOCCER_GM_NO_FIXTURE_CACHE=1 npm test` skips the cache.

## Analytics & deploy config

**PostHog needs `VITE_POSTHOG_KEY`/`VITE_POSTHOG_HOST` at BUILD time, and a build without them fails silently (2026-08-20).** Vite inlines `import.meta.env.VITE_*`, so the values are baked into the bundle by `npm run build` — they are not runtime config, and a host-side secret cannot reach an assets-only static deploy. Missing, `posthog.init()` (`src/ui/main.tsx`) is handed `undefined`: nothing throws, nothing logs, and the site reports no pageviews, no gameplay events and no crashes while looking perfectly healthy. That is what the 2026-08-15 Vercel → Cloudflare move (`wrangler.jsonc`, assets-only) did — the vars lived in the Vercel project, didn't come along, and production went analytics-dark for five days while Vercel *preview* deploys kept reporting normally, which is what made it look like a PostHog outage rather than a build problem. **The values are therefore committed, per build target** — `.env.production` (web) and `.env.itch`, both carrying the key, so any checkout builds a working bundle with no dashboard configuration anywhere and there is nothing left to lose in the next host migration. Safe because the project key is PostHog's public write-only token, already served to every visitor in the bundle. Three gotchas: **(a)** Vite loads only `.env` and `.env.<mode>`, and `.env.production` is itself a mode file, so it is *not* loaded by `--mode itch`/`--mode crazygames` — hence the duplication rather than one shared file (`.env` would cover every mode, but it is gitignored, which is the out-of-band storage this arrangement exists to avoid). **(b)** `.env.crazygames` deliberately carries **no** key: that build aliases `posthog-js` to a no-op shim (`vite.config.ts` → `src/ui/vendor/posthogNoop.ts`), so the omission looks like an oversight and isn't. **(c)** `npm run dev` runs mode "development" and so loads neither, meaning dev sessions report nothing by default — which is wanted, since dev clicks would otherwise land in the same project as real players and burn quota. `.env.example` exists only to opt a local dev session in. **Verify a deploy, don't assume:** `curl -s https://worldsoccersim.org/assets/index-*.js | grep -c phc_` — zero means that build has no key.

**The free tier is 1M events/month, and it has been exhausted once.** Autocapture fired on every click in a click-heavy game (685k events in 30 days, 67% of volume) and blew the allowance on 2026-08-03; ingestion stopped project-wide for the rest of the cycle and only `$exception` kept flowing, on its own quota. `autocapture: false` shipped in #205. Nothing reads autocapture data — every dashboard is built on the explicit events in `src/ui/analytics.ts`, whose rule is "a handful of meaningful moments, not one event per click". Keep it that way before adding events.

## Architecture (where things live)

- `src/core/` — pure sim logic (no UI/DOM). `constants.ts` is the central tuning table. Sub-areas: `players/` (generation, progression, youth, nationalities), `teams/`, `league/`, `ai/` (GM evaluation core), `transfers/`, `finance/`, `lineup/`, `cup/`, `scouting/`, plus top-level `offseason.ts`, `simThrough.ts`, `promotion.ts`, `loans.ts`, `awards.ts`, `godMode.ts`, `competitions.ts`.
- `src/engine/` — match sim (`matchSim.ts`, `attribution.ts`, `matchRating.ts`, its own `constants.ts`).
- `src/db/` — IndexedDB persistence (`leagueDb.ts`, `activeLeague.ts`) and **`migrate.ts`** (backfills every new field for old saves — update it whenever you add a persisted field).
- `src/ui/` — React pages (`pages/`), components, `context/LeagueContext.tsx` (all league-mutating actions, serialized through one promise chain).
- **Build targets** (`vite.config.ts`, `.env.<mode>`) — the default build serves worldsoccersim.org; `itch` and `crazygames` are **embedded** targets (someone else's iframe, at a path we don't control), grouped by the `EMBEDDED` set: relative `base` and hash routing, because there's no server to answer a history-API deep link. `crazygames` additionally strips AdSense and the SEO block from `index.html`, aliases `posthog-js` to a no-op, skips `<RouteSeo />` (or `useRouteSeo` recreates the canonical tag at runtime, pointing at a playable copy of the game — the one outbound link their rules forbid), and adds the CrazyGames SDK. **`src/ui/crazygames.ts` is the only place that touches the SDK**: no-ops everywhere else, queues every call behind the async `init()`, and survives the script being blocked. It also drops the announcement banner (theirs is a fixed 16:9 container as small as **914x514**, where a 36px strip is 7% of the height, and a full-width "Join the Discord" bar risks reading as the main CTA their rules disallow; the sidebar link is fine). **Two layout fixes it surfaced are global, not embed-only**, because they were equally broken in any narrow browser window: the top bar's inline save controls collapse into the existing overflow menu below `xl` (1200px) rather than `md` (768px) — the row needs ~1020px and was wrapping onto two lines and truncating the season — and the sidebar narrows 220px → 170px between 768px and 1199.98px. Full runbook + upload-form answers: `docs/crazygames.md`. Three gotchas: **(a)** the HTML surgery keys off marker comments and **throws if they go missing**, so editing `<head>` can't silently ship AdSense to review; **(b)** files in `public/` are copied verbatim and do *not* get Vite's base rewriting, so they must go through `publicAsset()`/`LOGO_URL` (`src/ui/publicAsset.ts`) — a bare `/favicon.png` resolved against the *host's* domain and 404'd the top-bar logo in both embedded builds, a bug that only shows up in an iframe at a subpath; **(c)** `dist-crazygames-harness.html` (repo root, never shipped) loads the built bundle in an iframe pinned to both measured CrazyGames sizes — the only way to see either the subpath bugs or the cramped layout, since a plain tab is neither iframed nor 16:9.
  - **`pages` is a fourth target and it is NOT embedded (2026-08-26).** It publishes the same game to `proelium27.github.io/world-soccer-sim/` from `.github/workflows/pages.yml` on every push to main. Not in `EMBEDDED`, deliberately: it is an ordinary page on its own domain, so it keeps history-API URLs rather than switching to hash routing. What it needs instead is the **two things a subpath host takes**, and both are silent when missing. **(a) A base path**, `PAGES_BASE` (default `/world-soccer-sim/`, which must track the repo's current name; the workflow fills it from `configure-pages`' reported base path, which is the only source that knows about a custom domain, and falls back to the repo name so a fork or rename needs no edit), which reaches the app as `import.meta.env.BASE_URL` and is now the **router's `basename`** — without it the browser sits at `/world-soccer-sim/manual` while React Router looks for a `/world-soccer-sim/manual` route and matches nothing. `basename` is `undefined` for the hash builds, whose base is the relative `./` (not a URL path, and a hash router has no prefix to strip). **(b) `404.html`**, a copy of `index.html` written by the pages build: Pages has no rewrite rules, and its one hook is serving that document for any path it can't resolve, with the requested URL intact — so a deep link boots the app on the right route. It answers **404**, which is invisible to a player and costs nothing in search because `SITE_ORIGIN` canonicalizes every page to worldsoccersim.org. The workflow asserts the file exists, since a missing fallback only shows up when someone opens a page other than the entry point. The pre-React placeholder's absolute `/leagues` links get the base prefix here for the same reason the CrazyGames build hash-rewrites them. **`.env.pages` carries the PostHog key** — a third copy, for the reason `.env.itch` spells out: `.env.production` is itself a mode file and is not read for `--mode pages`, so a key kept only there ships a bundle with `posthog.init(undefined)`, silent and inert. **The base is baked into every asset URL at build time, so RENAMING THE REPO BREAKS THE LIVE SITE until it is redeployed** — the deployed HTML keeps asking for the old name's `/assets/`, the page loads and every asset 404s. Measured, not hypothetical: `soccer-gm` became `world-soccer-sim` hours after the first deploy and the site went blank. No static file can detect its own URL changed, so a rebuild is the only fix and also the whole fix (the workflow reads the name at build time). Same applies to adding or removing a custom domain.
- `test/` — vitest. `test/validation/` holds the M1/M4 §8 gate tests.
  - **A world-wide `max` is not a league statistic, and the M3 top-scorer gate learned this the hard way (2026-08-11).** It asserted a Golden-Boot-shaped band (18–36) but measured the max goals over **every player in the world, second divisions included**. Both halves drift for reasons unrelated to scoring realism: a max rises with sample size (12 competitions → 16 raised it on its own), and tier-2 defences are weaker, so the world max was *set by a tier-2 player* and exceeded every top-flight leader that season (43 vs 32, 40 vs 34). It failed at a 36.2 mean while all 40 measured tier-1 Golden Boots sat between 23 and 34 — inside the band, never once above it. Now measures the **mean tier-1 top scorer** (27.7, per-season range 27.0–28.8), which is what the band describes and is invariant to both world size and tier-2 quirks. `scripts/topScorerProbe.ts` prints both side by side. **Widening the ceiling would have been the wrong fix** — it keeps a number that needs re-widening every time a country is added.
  - **"Average team" must mean the average team, not the middle array index — the M1 §8 benchmark gate (2026-08-13).** `averageMidVsMid` sampled one club per seed as `seedComps[len / 2]`. Strength targets are shuffled across tids at generation, so that is an arbitrary club, not the median one — the same file already sorts by `avgOvr` "rather than array position" to pick its strong/weak pair, and this function was simply never given the same treatment. The gate therefore reported the sampled club rather than the league, and it sat on its floor (goals/game **2.6019** against a 2.6 floor). A change that provably did not move scoring — **2.8566 → 2.8560 measured across all 100 teams, a difference of 0.0006** — failed it, purely because a different club landed at that index. It now averages **every** team's self-match, which lands all six metrics inside their **existing** bands on both the old commit and the change that exposed it. **No band was moved**, deliberately: the bands are the spec's realism targets and none of them was the problem. `scripts/midVsMidProbe.ts` prints both estimators side by side. Same lesson as the top-scorer gate above — fix the statistic, don't widen the band.
  - **A 5-season average is not precise enough to gate on — the M1 table-spread gate (2026-08-16).** It averaged **5** seasons of champion points against a 78-94 band. A single season's champion total has sd ≈ **5** points (`scripts/championPointsProbe.ts`, 20 seasons span 72-91), so that average carried ~**2.2 points of its own sampling error**, against a true mean of ~82 sitting only ~1.8 of those above the floor — i.e. **it could fail on seed luck with nothing wrong with the sim**, which is the precise sense in which CLAUDE.md already said it "sits near its floor by construction". Demonstrated: raising `YELLOW_GIVEN_FOUL` 0.11 → 0.18 read **75.8** here, a clean failure, while the *same change* over 20 seasons moved the champion mean **up** (81.75 → 82.20) and **reduced** its spread (sd 5.80 → 4.66). Now averages **20** seasons (~22s, against 13-minute gates elsewhere), which halves the estimator's error; **the band was deliberately not moved**, and the widened gate was verified green on **both** sides of the change so the fix can't be tuned to it. Third instance of the same lesson as the top-scorer and "average team" gates: **fix the statistic, don't widen the band** — and note the failing statistic here was the *sample size*, not the quantity.
  - **A minimum over 320 clubs is not a safety invariant either — the offseason roster-floor test (2026-08-13).** It asserted every club sits at or above `ROSTER_SAFETY_FLOOR` (18) after one offseason. Nothing enforces that: retirement and contract expiry are not sales, so `runAITransferMarket`'s per-sale depth floor never sees them, and `ensureUserRosterSafety` can only promote academy players a club actually has. Measured over five seasons on the test's own seed, **`origin/main` itself dips to 16 — the user's own club, season 4** — and the test only ever looked at season 1, where it happened to land exactly on 18. It was passing by luck, and any change that perturbs match results can tip it (across 8 seeds at season 1: main `20 19 18 19 18 18 18 20`, i.e. sitting *on* the floor half the time). Now asserts the engine's real requirement as a hard floor (**11** fit players, below which `selectXI` silently leaves slots empty) plus the healthy-squad target on the **5th percentile**, which is 21 on every seed on both sides and doesn't move. Dips recover by the next offseason. If the floor should be a genuine guarantee for AI clubs, that needs a mechanism (AI free agency refilling to it), not a tighter assertion — see the lower-severity leftovers about squads dropping below 11.
- **CI shards are packed by cost, not by file count (`test/helpers/shardPartition.ts`, 2026-08-25).** Vitest's `--shard` hashes each path with sha1, sorts, and slices into equal *counts*, which is deterministic and cost-blind — a bad pair here, because the suite's work sits almost entirely in a few full-world sim files. Measured over three consecutive CI runs: slowest shard 1749/1765/1863s against a fastest of 40/41/47s, on ~75 minutes of total work, i.e. one runner carried the build while another idled for half an hour, the same way every run. A `CostAwareSequencer` (wired at `test.sequence.sequencer` in `vite.config.ts`) weights each file and greedily packs the shards instead. Three things to know: **(a)** the weights are a hand-maintained table of measured seconds, defaulting to 10s for anything unlisted — being wrong costs *balance only*, never correctness, since `partitionByCost` is total and disjoint whatever the weights say (`shardPartition.test.ts` pins that, and it is the point of the file: a partition bug drops a file from every shard and CI still reports green). Add an entry when a new file runs longer than ~30s. **(b)** **Balancing alone did NOT speed CI up, and the measurement is the point.** The floor is the slowest single *file*: on the first packed run shard 1 ran `offseason.test.ts` **alone** for 1933s, against a pre-balancing worst shard of 1749-1863s — i.e. the old worst shard was already essentially that one file, so there was never a wall-clock win to take (the estimate that there was assumed no single file exceeded an even share; this one is ~2.2x it). What balancing bought is the other five shards getting lighter — spare capacity, not a faster build. It also makes the floor *mechanical*: shard 1 is provably one file, so the next move is unambiguous. **(c)** **The giants have since been split, and that is what actually moved the number.** `offseason.test.ts` (23 tests, ~1933s CI) became `offseason` / `offseasonSquads` / `offseasonRetirement` / `offseasonFinance` / `offseasonSolvency`, and `international.test.ts` (25 tests, ~1082s) became `international` (the pure structural tests, which drop to ~7s once the sims leave) / `internationalCampaign` / `internationalPlayerRecord` / `internationalEquivalence` / `internationalConfederationCups`. Every test moved **byte-identically** — they were already independent, each building its own seeded rng — with the shared `playFullSeason` / `advance` helpers lifted into `test/helpers/offseasonLeague.ts` and `test/helpers/intlLeague.ts`. The packing is what then spreads the pieces; without it two halves land back on one shard. **Measured after the split: shards 603/639/666/685/698/725s against a 669s even share, i.e. within 8% of the best any partition could do, and CI wall-clock 1863s -> 725s (~31 min -> ~12 min).** Total work did not grow (4016s against a 4131-4922s baseline), so splitting a hot sim file across processes costs nothing measurable in re-JIT. **(d)** With no file dominating, the binding constraint is now **total work / shard count**, so the next lever is the shard count in `ci.yml`, not more splitting — the packing test asserts against exactly that bound (`max(slowest file, total/shards)`) rather than a fixed number, so it stays honest in either regime. **(e)** CI runners are ~1.5x slower than a dev machine here, and a dev machine running full-world sims back to back **thermally throttles** — the same file measured 234s and 557s an hour apart — so treat the weights as an ordering, not as seconds, and don't chase a small discrepancy.
- **Test worlds are cached on disk** (`test/helpers/worldCache.ts`, used by `makeLeague`). `createLeagueState` costs ~4.1s for the 240-club/6000-player world, and vitest gives every test file its own worker process, so an in-process memo died at each file boundary and the same world was regenerated in all 36 files that wanted one — the single dominant cost in the suite. Worlds are now generated once ever into `node_modules/.cache/soccer-gm-worlds/<hash>/` and parsed back in ~12ms (~340x). **Always build test worlds with `makeLeague(tid, seed)`, never `createLeagueState` directly** — the one exception is a test that *reuses its rng after generation* (threading it into a later `simThrough`/`simOffseason`), which needs the rng advanced by generation and so must keep generating; those live in `international.test.ts`, `offseason.test.ts`, `simThrough.test.ts`, `transfersRender.test.tsx`, the m3/m4 validation gates and one case in `loans.test.ts`. Gotchas: **(a)** the cache key is a content hash of **all of `src/core`** plus `src/engine/rng.ts` and the Node version — deliberately broad, because generation cannot then depend on anything unhashed. Narrowing it to generation's current import list reintroduces silent staleness; don't. A core edit costs one rebuild (~60s) and is free thereafter. **(b)** It is only sound because generation is deterministic apart from `meta.created` (a wall-clock stamp) — `fixtureFidelity.test.ts` asserts both that and cached-equals-fresh, and is what stops the cache drifting silently. **(c)** `SOCCER_GM_NO_FIXTURE_CACHE=1` bypasses disk entirely if you ever suspect the cache.

## Core invariants & gotchas (durable — read before touching sim code)

- **RNG stream order is load-bearing.** The sim is seeded/deterministic; inserting or removing an `rng` draw shifts every downstream roll (different ratings, names, results). When adding per-player traits or post-hoc attribution, derive them from a *separate* seeded stream (`mulberry32`/`hashInts` off pids/match-intrinsics), never from the shared `rng`. This has caused real bugs (AI deficits, shifted generation) multiple times — see any "RNG-stream-order" mention in git history.
- **OVR scale:** 65 ≈ average starter, 70 ≈ good starter, 75 ≈ a team's best, 80-85 ≈ league-wide elite, 90+ ≈ rare outlier. `OVR_WEIGHTS` (`players/templates.ts`) drives both generation and progression's `computeOvr`.
- **OVR is calibrated to mean the same thing at every position, and it takes TWO constants because two independent mechanisms break it (2026-08-23).** A position's OVR weights sit on the very skills its generation tiers roll highest — that is *what makes them* its key skills — so the weighting and `GEN_OFFSETS` amplify each other. Measured on a fresh world before the fix: mean OVR ST 55.9 down to FB 49.4, and **132 of 320 clubs had a striker as their best player against 1 with a full-back and 6 with a centre-mid** (expected ~38/51/51 at their roster shares). Full-back is the only position with no `star` skill; striker and winger have two each. The fix is *not* a reweight — the rows are read by the sim's slot logic, secondary positions and the position-change check, so flattening them would trade a true statement about football for arithmetic. Instead: **(1) `POSITION_OVR_CALIBRATION` (levels)** — an additive per-position shift, **zero-sum weighted by `ROSTER_COMPOSITION`**, so the world mean OVR is untouched and `LEAGUE_BASE` / `GROWTH_DAMPING_START` / `DIVISION_2_REFUSAL_OVR_THRESHOLD` / `PROTECTED_STAR_OVR` / the wage and valuation curves all still mean what they did. **(2) `POSITION_RATING_SPREAD` (spread)** — OVR is a weighted *mean* of independent draws, so its noise is `RATING_NOISE_SD × sqrt(Σ(w/W)²)`: a row concentrated on few attributes varies more and wins every extreme. Keeper is the outlier (goalkeeping is over half his weighting, 0.58 vs 0.34-0.42 outfield), and fixing only the levels handed him the problem instead — **GK went 68 → 103 of 320 clubs**. It scales the *generation draw* rather than the weight row, because the sim's `keeping` composite **is** the goalkeeping rating (`league/matchPlayers.ts`) and the AI prices keepers off OVR, so a diluted row would make OVR a worse read on the one thing he does; composites are z-normalized per competition, so a uniform change in a position's raw spread is nearly invisible to the football. **Derived at module load from `OVR_WEIGHTS`**, so editing a row re-derives it instead of silently reopening the gap. `computeOvr` also now **normalizes** skill weights (a row states relative importance only — GK's 92-sum hand-correction is obsolete and was also compressing keepers' slope against team strength) and **centres height** on the position's own range (a level effect wearing a skill weight's clothes). Result: every position within 0.3 OVR on mean, sd and p90, and club-best tracks roster share. Tools: `scripts/positionOvrCalibrate.ts` (prints the table), `scripts/positionOvrProbe.ts` (the symptom), `test/core/positionOvrBalance.test.ts` (the gate). **Three traps.** (a) **`SECONDARY_POSITION_CUTOFF` MUST be re-derived in the same change** — its bars are percentiles of a per-pair *gap*, so any level move shifts every bar touching that position; left alone, "holds a second position" ran CB 93% / DM 93% against FB 1%, i.e. the fixed share the design rests on had stopped being fixed. (b) **Measuring "best player at his club" needs a fair tie-break.** OVR is an integer and a squad's top few sit within a point or two, so awarding the tie to whoever comes first in the roster array biases the whole table by generation order — it read as a 4-point positional skew that wasn't there. (c) The 8×8 matrix of "mean OVR of position A's players evaluated at B" must keep its **diagonal maximal** (it does, before and after) — that is the check that the calibration didn't turn some position into a conversion magnet. `migrate.ts` re-derives `ovr` (and every `hist` snapshot's) from stored ratings on load, clamping `potential` up to it; the spread half applies at generation only, so old saves keep their original spread.
- **Anti-inflation (fragile equilibrium — several mechanics exist only to hold it):** youth intake anchors to a fixed-at-generation `academyBase`, never to the club's current roster average (the torn-out anchor caused unbounded ratchet). Potential is a *scout estimate* (`estimatePotential`), never a growth input. Every position's expected lifetime rating arc is ~0/slightly negative. `developmentBias` (persistent per-player trait, deterministic from pid) **must taper to exactly 0 by peak age**, or inflation reopens. `growthDamping` scales down only *positive* deltas as ovr climbs. `YOUTH_BASE_OFFSET` offsets the fact that `generatePlayer` doesn't vary quality by age. Any new mechanic that shifts these must be dynasty-audited (`scripts/`).
- **The user's club is unmanaged by design** in headless audits — no AI free agency/renewals/buys touch it, so it rots and produces *all* extreme worst-case roster/points stats. **Exclude `userTid` from tail metrics** in any audit, or report it separately.
- **Match composites are z-normalized within each competition.** A weak league reads as average in its own matches; cross-league surfaces (the Cup) must pool participants into a *shared* baseline (`simThrough`'s `cupMatchData`) or the weak club gets normalized back up to parity.
- **Composites bucket by SLOT, not natural position (`rollupComposites` takes `SlottedPlayer[]`, `engine/positionFit.ts`, 2026-08-12).** The team's shape comes from its formation, so every group and weight keys off the slot a player occupies; his own `pos` only decides what it *costs* him to be there (`familiarityPenalty`, in raw rating points: `POSITION_ADJACENT_PENALTY` 6 / `POSITION_FOREIGN_PENALTY` 16 / `POSITION_KEEPER_PENALTY` 35, all in `engine/constants.ts`). Before this, groups were built from `p.pos` and the slot was forgotten after selection, so **moving a defender up the pitch made your defense better** (he stayed in the defensive group at full strength and simply left the attacking one) and `control` had the same inverted sign. `MatchPlayer` now carries `slot`; a substitute **inherits the slot of the man he replaces** (via a *copy*, never mutation — `TeamMatchData` objects are shared across every match built from one `leagueMatchData` call, e.g. `season.ts` builds it once for all 380 fixtures, so mutating a slot would leak into unrelated matches). `slotPlayed` tracks the played slot for the box score, which is built from the *original* roster arrays where a sub still carries his bench slot. Attribution weights, `computeMatchRating`, and every "who's the keeper" lookup follow the slot too. **The load-bearing consumer is the substitution logic, not the XI** — measured, starters are 99.2% exact-fit and 0% foreign, but the bench was putting a player in a foreign slot on **37% of all subs** (a striker replacing a tired centre-back was the single most common swap) because `pickReplacement` was exact-pos-or-anyone. It now maximizes `benchValue - familiarityPenalty(slot, pos)`, and `worthSub` gates on the same penalized value; **those two must stay on one number**, or the sim makes swaps it then punishes. Result: foreign subs 37% → 0.2%, and ~19% fewer subs overall (holding a tired starter on beats wrecking the shape). Chase-the-game subs pass `reshape` to `commitSub` so the arriving attacker plays *his own* position (a genuine shape change, one fewer defender) rather than being stranded in a defensive slot. Also closes the documented `pickReplacement` GK gap: an outfielder forced into goal is now penalized instead of silently leaving `keeping` at a neutral 0.5 while counting as an outfielder. Pure function of attributes, **no shared-`rng` draw**, so stream order is untouched — but composite values change, hence results change, hence the `touchStats.test.ts` scoreline hash was rebased. Measured over 20 seeded seasons: champion pts 79.20 → 80.55, and *variance fell* (champion sd 5.24 → 3.77, bottom sd 6.49 → 3.99), since fewer matches are decided by a side dismantling its own shape late. **Dynasty-audited** (`scripts/slotChurnAudit.ts`, 15 seasons × 2 seeds) for the obvious risk — that punishing thin squads sharpens the strong/weak gap into a procession — and it went the *other* way: distinct champions per league 8.0/8.1 → 9.4/9.3, dominant club's title share 33.3%/31.7% → 28.3%/23.3%, champion pts flat (77.9/78.1 → 78.1/77.4), ovr drift still ~0 (anti-inflation intact), D2 ceiling unchanged within noise. Title races got *more* open, because a side can no longer stumble into a lopsided shape that its raw quality doesn't justify.
- **Secondary positions are DERIVED, never stored (`core/players/positions.ts`, `COVERABLE` in `engine/positionFit.ts`, 2026-08-13).** A player also plays any slot he can cover where his OVR there beats his own by at least `SECONDARY_POSITION_CUTOFF[pos][slot]`. A secondary is an **exact fit** (`fitTier` returns 0), so it waives `familiarityPenalty` entirely *and* makes him a first-choice `selectXI` candidate for that slot — a 74 winger who really does play full-back now takes the slot off a 66 full-back, where before fit was strictly by listed position. Threaded onto `MatchPlayer.secondary` because the derivation needs core's per-position OVR model and the engine can't import core; `benchValueAt` is the single sub-side caller, so `worthSub`/`pickReplacement` stay on one number by construction. Pure, **no rng draw** (stream order untouched), no persisted field, no migration. Memoised in a `WeakMap` keyed on the **player object** — the core hands unchanged players through by reference, so a progressed player is a new object and misses the cache automatically; a pid key would go stale the season he develops.
  - **`COVERABLE` is the REVERSE of `ADJACENCY`, and getting it backwards is silent.** `ADJACENCY[X]` lists who can cover *slot X*; "where else can this player play" is the transpose. The table is **not** symmetric, so a forward lookup is wrong for exactly the pairs that matter and right everywhere else: a DM can cover at full-back but a full-back cannot cover in defensive midfield, and a winger can play up front but a striker is not thereby an attacking mid. Derived from `ADJACENCY` at module load so the two can't drift; a test pins the transpose and a second test pins the asymmetric pairs, so it can't quietly degrade into "same thing twice".
  - **One shared OVR threshold cannot work at ANY value — measured, and it was the first design.** How close a player rates one position along is a property of the position PAIR: CM/DM/AM share most of their OVR weighting, a striker's overlaps almost nothing. At a 3-point gap that gives **100% of CMs and 6% of STs**; there is no value where both are sane. `SECONDARY_POSITION_CUTOFF` is therefore per-pair, measured to admit `SECONDARY_POSITION_RATE` (0.15) of each position's players. Regenerate with `scripts/secondaryPositionProbe.ts` after any change to the OVR weights, the adjacency table or the rate.
  - **Versatility rises over a dynasty and then plateaus; the fresh-world calibration ships.** Rostered share with any second position: fresh 35.4%, then 45.5 / 51.5 / 53.6 / 54.7 / 54.9 / 54.8 at seasons 5/10/15/20/25/30 — flat from season 20, an equilibrium rather than a ratchet. Cause is `growthDamping` compressing a player's strongest skills, which flattens his profile; note a *uniform* rating gain cancels exactly, since every OVR weight row sums to 100. **Not the free-agent tail** — that was the first hypothesis and it is wrong, rostered squads drift the same. Recalibrating on the season-15 plateau was tried and **rejected**: it leaves a new save at 9.3% (3% of wingers), i.e. no utility players in the seasons a new player actually sees.
  - **Candidates are ranked by `ovrAtSlot`, not `p.ovr`, and this is a correctness requirement rather than a refinement.** `selectXI`/`bestFit` break fit-rank ties by rating; using a player's own-position OVR compares a winger's *winger* rating against a striker's *striker* rating and then plays the winner up front. Measured, that cost team `finishing` 0.4736 → 0.4576 and goals/game 2.60 → 2.53, because versatile wingers were taking striker slots on a rating they don't carry into them. Ranking by his rating **at the slot he'd fill** restores it (finishing 0.4652) and is the only comparison that means anything. Same reasoning applies to any future ranking of a player for a slot he doesn't list.
  - **The rate is a difficulty lever, not decoration.** A secondary waives the familiarity penalty, so letting it run high dissolves the positional discipline slot-aware composites exist to enforce. That is the number to watch if these constants are retuned.
- **A player's listed position can CHANGE over his career (`changedPosition` in `core/players/positions.ts`, `RatingsSnapshot.pos`, 2026-08-13).** Decided once per offseason inside `progressPlayer`, after the rating step (he trains as what he is) and before ovr/potential are computed (so both are recomputed at the new position). Pure, **no shared-`rng` draw**, and the draw *count* is unchanged either way — `stepRatings` and `estimatePotential` both draw independently of position — so stream order is untouched; a test pins it. Conversions only fire in the offseason, so the single-season `touchStats` hash is **not** rebased this time. `RatingsSnapshot.pos` is a new persisted field; `migrate.ts` backfills it to the player's current position, which is **exact rather than a guess** — nothing could change a position before this existed, so every historical snapshot really was taken at the one he holds today.
  - **The SUSTAINED window is the load-bearing gate, not the margin.** Measured, **5.9%→8.0% of rostered players change which position they rate highest at every single season** (`scripts/positionChangeProbe.ts`), so an instantaneous "play your best position" rule would relabel ~600 players a year and the badge would mean nothing. `POSITION_CHANGE_SEASONS` (3) demands the same winner N seasons running. It is also the *inflation* control, for the same reason: best-of-N is a maximum over noisy quantities and so sits systematically above any fixed pick, and requiring persistence strips out the noise half of that bias.
  - **The window counts only snapshots stamped at his CURRENT position, which buys the cooldown for free.** Right after a conversion his history at the new position is empty, so he cannot move again until he has served a fresh window. This is what stops a borderline player oscillating between two positions and minting OVR on every leg — measured, **3 round trips against 497 changes over 20 seasons**. Don't "simplify" this to the last N entries regardless of position; that reopens the pump.
  - **A fresh world is already correctly listed, and the backlog is built by development rather than aging.** At generation, mean best-position gain is 0.15 OVR and *zero* players clear a 6-point margin — generation picks a position then rolls ratings for it. Over a dynasty the gap accumulates, and by age band it runs 0.37 / 0.70 / **0.74** / 0.60 / 0.51 across ≤20 / 21-24 / 25-28 / 29-32 / 33+: it peaks in the mid-20s and *falls* for the oldest players. So the intuitive story ("physicals decline first, so the winger drops to full-back") is **measurably wrong** — a uniform rating loss cancels exactly, since every OVR weight row sums to 100. The cause is `growthDamping` compressing a player's strongest skills during growth years, the same mechanism that raises versatility over a dynasty.
  - **Measured against `origin/main`, 20 seasons × 3 seeds** (`scripts/positionChangeAudit.ts`, run on both sides — main reads 0 conversions and is a valid control): rostered mean ovr **51.66 → 51.94 (+0.28)**, tier-1 **53.80 → 54.10 (+0.30)**. Per seed the tier-1 delta is +0.06 / −0.09 / +0.94, straddling zero on two of three, so it is **small and partly seed noise rather than zero** — worth stating honestly, since league mean ovr already drifts ~+4 over 25 seasons on main for unrelated reasons and this adds a few percent on top. Rate settles at **0.6-0.9% of rostered players per season**, ~5% of the pool ever converting over 20 seasons, and **zero in season 1** (nobody has the history yet).
  - **Wages are the cost, and the finance column is where this would fail first.** Wages are cubic in ovr, so conversions are money: mean wage bill **17.2M → 18.2M (+5.8%)**. Minimum AI budget is higher on two seeds and lower on one (9.8 vs 5.7, 14.2 vs 8.2, 6.7 vs 12.5) with **no deficits on either side** — that spread is seed noise, not an effect. **Don't read a single seed here as an improvement; an earlier draft of this entry did exactly that from seed 1 and a third seed contradicted it.**
  - **The position-mix risk is real in principle and absorbed by roster management in practice.** `COVERABLE` is asymmetric and the flows are lopsided — W→AM and CB→DM dominate, and releasing the raw backlog at a 3-point margin would swell AM from 8.0% to 10.5% of the pool while draining CM and FB. It doesn't happen because `trimRosterSurplus` and composition-weighted youth intake hold squads *at* `ROSTER_COMPOSITION`: measured, the rostered mix is exactly on target after 20 seasons on **both** branches. A conversion therefore creates churn (a surplus at one position, a hole at another) rather than drift. That the mix holds is also proof the free-agent pool can still supply every position.
  - **News volume is gated (`NEWS_POSITION_CHANGE_OVR`, 72).** The user's own players are always reported; elsewhere only established players are, for the same reason AI free-agent churn is kept out of the aggregate feeds.
- **Composite rollup is position-weighted + star-concentrated (`rollupComposites`, `COMPOSITE_STAR_CONCENTRATION`, 2026-07-21).** `attack`/`defense`/`control` no longer flat-average their position group: each is a position-weighted mean (who drives the phase counts most — ST/W for attack, CM/DM for control, CB for defense) *blended toward the group's single best player* by `COMPOSITE_STAR_CONCENTRATION` (0.3), so an elite individual resists being averaged down by weak teammates ("stars carry their phase"; a balanced XI beats a lopsided higher-OVR one). `finishing` (own shot-share weighting) and `keeping` are deliberately left alone. **Pure function of attributes — no shared-`rng` draw**, so RNG stream order is untouched; it only changes composite *values*, hence match results, hence the `touchStats.test.ts` scoreline hash was rebased a second time (intended, not a touch-attribution regression). Dynasty-audit champion churn before raising the concentration (interacts with league z-norm spread).
- **Shot conversion blends team + individual (`SHOOTER_FINISH_WEIGHT`, 2026-07-20, `simMatchDetailed` only).** `resolveShot` takes a `finishAdj` = the finisher's own skill *relative to his team's average* (shooting for shots, heading for corner headers), added to the team finishing composite for `onTargetP`/`saveP` only — **never xG** (xG stays the team-blind "average attacker" baseline, so goals-vs-xG reveals finishing). Centered on the team average, so it *redistributes* a team's goals toward its best finishers without inflating league scoring; a lone elite finisher on a weak side now genuinely stuffs the sheet (the fast composite-only `simMatch`/montecarlo path is untouched → benchmark gates unaffected). Side effect: the season top scorer rises into the mid-30s (m3-top-scorer gate widened 32→36). Rebased the `touchStats.test.ts` scoreline hash once (intended outcome change, not a touch-attribution regression).
- **Every league match runs on its own seeded stream (`leagueMatchSeed`, `simThrough.ts`, 2026-08-18).** Matches used to share the matchday's `rng` in fixture order, so a match's result was a function of every match simmed before it that day and **no single match could be re-run in isolation** — re-simming one desynced every later fixture. Now seeded off `hashInts(lid, season, matchday, home, away, LEAGUE_MATCH_STREAM=41)`, which buys two things: a result no longer depends on fixture order, and one match is independently reproducible. **The second is the load-bearing one** — it is what lets the live match viewer re-run a single match (with, later, a substitution the user made while watching) without touching the rest of the matchday. `leagueMatchSeed` is **exported so callers derive the seed rather than duplicating the recipe**. Cost, paid once: pulling matches out of the shared stream shifts every draw after them, so results differ from the pre-change baseline going forward (saves aren't damaged — their history is data). **The `touchStats.test.ts` scoreline hash did NOT need rebasing**, for the same reason the suspensions entry below documents: that baseline runs `simSeason` (`core/season.ts`), a test-only harness on a separate code path that was deliberately left alone so it keeps guarding `simMatchDetailed`. The gates that *do* cover this path — `simThrough.test.ts`, `m3-top-scorer`, `m4-multiseason`, `m4-multiseason-integrity`, `benchmarks` — are distributional, and all passed unchanged, which is the expected result: probabilities didn't move, only which draw landed where.
- **Determinism boundaries:** cup rounds and decorative touch-attribution (`passes`/`crosses`) each run on their own seeded streams so they can't perturb league match results — league scorelines stay bit-identical to a fixed baseline hash (`touchStats.test.ts`; the baseline was rebased once for the finishing change above).
- **UI conventions:** no emoji in UI (real icons = hand-written inline SVG, see `AwardIcons.tsx`); player-facing prose is casual/second-person, sentence-cased, no em-dashes.
- **Seasons display as years, and the start year is per-save (`meta.startYear`, 2026-08-23).** A season is a 1-based counter everywhere in the sim; `ui/format.ts`'s `seasonYear` is the only thing that turns it into a year, and which year season 1 lands on is now the player's choice on the New League screen. **Cosmetic only** — nothing in core, the engine or persistence reads it, and the field is optional with absent meaning the 2026 old saves have always shown (so no `migrate.ts` change). The offset lives as **module state in `format.ts`**, set by `LeagueContext`'s `commitLeague` — the single funnel every league (loaded, created, imported, switched away) passes through — rather than threaded to the ~90 `seasonYear` call sites, half of which are render helpers with no league in scope. The consequence to know: **anything rendering a season for a save that is not the active one must use `seasonYearFrom(startYear, season)`**, not `seasonYear` (`/leagues` sidesteps this by listing raw season numbers).
- **Crash visibility (2026-07-25):** `ui/components/ErrorBoundary.tsx` wraps the `<Outlet />` in `Layout.tsx` **keyed by `location.key`** (a page crash keeps TopBar/Sidebar mounted so the user can navigate away, and moving route remounts a clean boundary) plus an outer one in `App.tsx` for the routes outside `Layout` (`/leagues`, `/new-league`). `posthog.init` sets **`capture_exceptions: true`** (`main.tsx`) and the boundary also calls `captureException` itself, because React swallows the error on its way to unmounting. Before this, *any* throw blanked the whole app with the reason only in the console, and error tracking had **zero** issues recorded ever — a crash report could never be more specific than "it crashed". Gotcha for testing: **server rendering does not run error boundaries** (React re-throws to the caller), and there's no DOM test env in this repo, so `test/ui/errorBoundary.test.tsx` pins our half of the contract (`getDerivedStateFromError` + the fallback render) rather than a live catch. `test/ui/transfersRender.test.tsx` is the render harness pattern for a page (mock `useLeague`, wrap in `MemoryRouter`, `renderToStaticMarkup`) — a throw there surfaces as a test failure.

## Feature ledger (post-M6, all shipped)

Each entry: what it is / where it lives / gotchas.

**Manager career (the user's club can change mid-save)**
- **`meta.userTid` is no longer fixed for the life of a save (2026-08-23).** `core/manager/` adds board confidence, job offers and sackings, all resolved at the offseason boundary. The reassignment itself was always trivial — every one of the ~198 `userTid` consumers reads it live, so the AI starts managing the club you left and stops managing the one you joined on the next read. **The load-bearing part is `switchClub`'s handover**, because several `StoredTeam` fields are *user-only by convention* and an AI club that inherits one populated is in a state nothing unwinds.
  - **The academy is the one that silently breaks things.** `academyRoster` is a user-only holding pool: AI clubs never promote from it, never field those players and never release them — yet the offseason's season-start charge sums `[...roster, ...academyRoster]` and `freeAgentCull` counts them as rostered. Left behind they are permanent zombies: paid, uncullable, unable to ever play again. `switchClub` graduates them onto the senior roster on ordinary `contractTerms` (rng-free), letting the next `trimRosterSurplus` sort out the surplus.
  - Also cleared on the way out: `starters`→null, `transferListed`/`moreMinutes`/`scoutingObserved`→empty, `nextScoutingSpend`=`scoutingSpend`, plus **only that club's** formation re-picked via `chooseBestFormation`. Re-running `assignAIFormations` over the world instead would re-pick 300-odd clubs' shapes at a moment nothing else in the sim does, changing their match results as a side effect of the user changing jobs. `ensureUserRosterSafety` runs once on the departing club, since it only ever protects `userTid`. League-level `negotiations`/`inboundOffers`/`loanListings`/`loanRejections` are dropped (all implicitly "the user's"); `activeLoans` deliberately survive (club-owned contracts).
  - **Arriving fogs the new squad** (`reconcileScoutingObserved({}, roster, season)`) — falls out of the existing scouting model rather than being special-cased, and reads exactly right: you know their ratings, not their ceilings.
  - **Runs at the offseason transition in `simThrough`, beside `initInternationalCampaign`, not inside `simOffseason`.** It judges the season just finished (wants that final table and nothing after it), and it must be answerable *before* the offseason runs so a manager who moves manages the **new** club's summer. Pure state, **no shared-`rng` draw** — offers use their own `hashInts` stream (`MANAGER_OFFER_STREAM` 970), so the `touchStats` scoreline hash and the M1 standings gate are untouched (verified).
  - **Confidence is a running 0-100 balance, not a "last N seasons" rule** — legible to the user, and it lets goodwill be *banked*, so an overachiever survives one bad year and relegation is never an automatic sacking. Judged on **finish vs the club's standing**, never vs its current squad — see the next bullet. Deliberately **not** built on `deriveLeagueContexts`'s `stature`: that is the transfer AI's view, and coupling to it would let a market retune silently change who gets sacked.
  - **Expectations must not be settable by the manager, and the first model got this wrong (user catch, 2026-08-23).** `deriveExpectations` originally ranked clubs by `computeTeamRating`. Squad quality is the one variable the manager fully controls, so tearing the team down lowered the bar with it: sell everyone, finish next-to-last with the worst squad in the league, and the board reads it as *beating expectations*. It rewarded sabotage. **Standing is now built only from what a transfer window cannot touch** — recent finishes (`MANAGER_EXPECTATION_W_HISTORY` 0.7, dominant because they are the most direct statement of what a club is) and hype (0.3), each normalized within the competition. **There is deliberately no money term, and two attempts at one were removed** (code review, 2026-08-23): bank balance alone is *backwards*, since spending the kitty is the normal thing a manager does and emptying it moved a mid-table club's bar six places easier while it fielded a stronger squad; balance-plus-wage-bill fixes buying and selling (each just moves value between the halves) but not **releasing**, where wages fall with no fee arriving, so a teardown still dragged the bar down — caught by the teardown test itself. Self-harming is not the same as impossible, and the model exists so that *no* sequence of transfer decisions moves the bar. Cost: a suddenly-rich club is not expected to improve until it actually does, which is the right way round for a board that judges results. Squad rating survives only as the season-1 bootstrap, blended out by `historyCoverage` as real results accumulate — and that is the squad the manager was *handed*. Two traps: **(a)** a past finish is meaningless without its division, so `seasonStanding` converts it to a percentile and scales tier 2 by `MANAGER_EXPECTATION_TIER2_WEIGHT` (0.35), or a promoted second-division champion carries a "1st" into the top flight and is expected to win it; **(b)** `reviewSeason` must pass `league.seasonHistory` *excluding the season being judged* — it gets this for free since a season is appended during the following offseason, but any new caller must preserve it, or the bar moves to match the result it is judging. `test/core/manager.test.ts` pins the teardown case directly.
  - **Harshness has two axes.** In-world `demand` blends club-rank-within-league with league-strength-within-world (asymmetric: a demanding board damps rewards and amplifies penalties). Globally, **`DifficultyProfile.boardPatience`** (easy 1.7 / normal 1 / hard 0.75 / brutal 0.55) scales the whole verdict — the one difficulty knob with **no world effect**, so it needs no `difficultyProbe` recalibration.
  - **`MANAGER_CONFIDENCE_SWING` was sized against measured variance, and the first guess was 1.9x too harsh.** `scripts/managerTenureProbe.ts` judges **every AI club as if it were the user** over N seasons and reports sackings per 100 club-seasons per difficulty. Judging the *actual* user club is useless here: it is unmanaged in a headless run, so it rots and would report "the board fires everyone" against any tuning whatsoever. Measured over 2552 club-seasons: an ordinary season lands within **±0.158 of a division** (p25-p75, ~±3 places in a 20-club league), a bad one about **-0.368** (p10). At the first-guess swing of 130 a single p10 season cost ~68 against a starting 65 — one bottom-decile year all but ended a career — and normal difficulty sacked a manager every 8 seasons (12.5 per 100 club-seasons, median tenure 3, only 119/320 surviving 8 seasons). Now 70. Re-measured after expectations moved onto club standing (which is noisier than squad rating, since results vary more than ratings do — p10 -0.42 vs -0.37): normal lands at **7.6 per 100 club-seasons — one sacking per ~13 seasons**, median tenure 5, 163/320 surviving 8 seasons; easy 2.3, hard 11.5, brutal 15.0. (Dropping the money term moved these by under 0.2 — it was contributing almost nothing to the distribution while offering an exploit channel, so removing it was free.) Re-run the probe after touching either constant or any `boardPatience`; note the figures describe **competently-managed AI clubs**, so they are the baseline a human over- or under-performs against, not a prediction of one player's tenure.
  - **`MANAGER_CONFIDENCE_RECOVERY` (0.12) exists because the probe exposed a dead end, not to soften the numbers.** Confidence only ever moved on over/underperformance, so a manager at 20 who then finished *exactly* to expectation every season stayed at 20 forever, permanently one bad year from the sack with no route back. Each season now drifts 12% of the way back toward `MANAGER_START_CONFIDENCE` **before** the verdict, which cuts both ways on purpose: a long-banked 100 also decays, so a title six years ago stops being a permanent shield.
  - **There is no unemployed state, by design** — every page assumes a user club, so a sacked manager's offer list is guaranteed non-empty (`generateJobOffers` drops the band filter rather than return nothing) and he must accept one. `ManagerState.sackingEnabled` is the user-facing "never sack me" switch (user call, 2026-08-23); offers still arrive so moving clubs stays available.
  - Reputation is **derived** from `ManagerStint[]` (`managerReputation`), never stored, so the formula can be retuned without rewriting careers. The stints themselves store raw results because the board judges at the end of a season *before* it is appended to `seasonHistory` — deriving would need a special case for exactly the moment it matters. Migration backfills **confidence 100** (the board never watched those seasons; an upgrading dynasty must not be one bad year from a sacking) and reconstructs titles/trophies from `seasonHistory`/`cupHistory`/`shieldHistory`/`domesticCupHistory` so an established save arrives with the reputation it earned; `overperformance` stays 0, being unreconstructable without past squad ratings.

**Roster & tactics**
- **Starting XI** — user drag-drops between XI and bench *and* between two XI slots, persisted as `StoredTeam.starters` (11 pids, `null`=auto). `resolveXI` (`core/lineup/resolveXI.ts`) falls back to `selectXI` auto-pick when invalid. Only the user's club sets `starters`; AI always auto-picks. **The swap rule is `core/lineup/swapStarters.ts`, not the page** — `Roster.tsx` used to reject any drag where both ends were on the same side with the comment "nothing to swap", which was true only while composites bucketed by natural position; since they bucket by **slot** (2026-08-12), a starter-to-starter drag is a genuine tactical move, so that guard was lifted (2026-08-14) and only the bench-to-bench case is a no-op. The keeper rule is **not** re-derived there: `swapStarters` builds the candidate array and asks `isValidStarters`, so there is one definition of "an outfielder may not stand in the GK slot" and a rejected swap returns `null` (leave the lineup alone) rather than writing an invalid array that `resolveXI` would silently replace with an auto-pick.
- **Formations** — 16 shapes in `FORMATIONS` (`core/lineup/formations.ts`), `StoredTeam.formation` (default `4-3-3`). A real tactical lever: the match sim rolls up composites from the XI each club's formation fields (`teamFormation`/`teamSlots`). AI clubs auto-pick their strongest shape (`chooseBestFormation`, refreshed end of each transfer window via `assignAIFormations`; never the user's). The user can opt into the same pick via a **"Best XI"** button on Roster (`autoPickBestXIAction` in `LeagueContext`, runs `chooseBestFormation` on the user roster + clears `starters`). `PitchField.tsx` + `pitchLayout.ts` render per-formation layouts; every UI surface derives from `FORMATION_IDS`, so adding a shape needs only the slot array + its layout.
  - **A shape must be a distinct slot multiset, and the obvious additions aren't (2026-08-15, when 7 shapes were added).** Composites bucket by slot and nothing in the sim knows where a slot is *drawn*, so two shapes with the same slots are the same team: **4-1-4-1 is exactly 4-3-3** (GK/CB2/FB2/DM/CM2/W2/ST) and **4-2-4 is exactly 4-4-2** — adding them would only add ties for `chooseBestFormation` to break. A test pins distinctness. The corollary is that back-3 vs back-5 can't be carried by wing-back height (no such axis); it's carried by the midfield band instead — 3-4-3 fields CM2 where 5-2-3 fields DM2, 3-5-2 fields CM2+AM where 5-2-1-2 fields DM2+AM.
  - **Order is load-bearing**: `chooseBestFormation` breaks ties by `FORMATION_IDS` order, so 4-3-3 stays first (it's the default, and the "11-man roster ties to 4-3-3" test depends on it) and new shapes append.
  - **Measured before shipping** (`scripts/formationSpreadProbe.ts`, **4 seeds** × season 3, 319 AI clubs each): the risk is a new shape whose slots happen to match `ROSTER_COMPOSITION` winning everywhere and making every club play alike. It went the other way on every seed — all 16 shapes get used, and the most common shape's share *fell* (25.7→19.4, 20.7→16.6, 20.4→16.0, 18.5→13.5), with 29.8–33.9% of clubs switching shape for +0.145 to +0.203 raw ovr per starter. **The baseline itself moves ~7 points across seeds, so quote the range, not one draw** — seed 1 happens to be the highest of the four, and an earlier version of this entry generalised from it alone. The probe also reports a **slot-adjusted** figure because `chooseBestFormation` ranks on **raw `p.ovr`, not `ovrAtSlot`** (pre-existing), so a shape can in principle win the pick by fielding a strong man in a slot foreign to him and then play worse; measured, the two track on all four seeds (adjusted +0.134 to +0.193, never more than 0.011 below raw) and 1.9–2.8% of clubs end up marginally worse than their legacy pick. Re-run the probe before adding more shapes — a gap opening between those two numbers is the signal that the raw-ovr ranking needs to become slot-aware.
  - **Dynasty-audited** (`scripts/slotChurnAudit.ts`, 15 seasons × **4 seeds**, run on both this branch and its merge-base — the script is byte-identical on both sides). The risk was the same one the slot-aware composites change was audited for: a shape lever that sharpens the strong/weak gap into a procession. It doesn't. Title churn is **flat-to-better and straddles zero per seed** (distinct champions per league 8.13 → 8.54 on the mean, per seed +1.37/0.00/−0.62/+0.88; dominant club's title share 31.5% → 28.8%, per seed −6.7/+0.8/+1.7/−6.7) — so "no procession" is what the data supports, **not** "title races opened up". Anti-inflation holds (mean ovr drift over 15 seasons 0.00 → 0.15, against the ~+4 over 25 seasons main already carries for unrelated reasons; two seeds sit at +0.3-0.4 where the baseline was ~0, so it is small rather than literally zero). D2 ceiling unchanged (45 → 44 over-threshold AI player-seasons across the four seeds).
  - **The one systematic effect is champion points, down on ALL FOUR seeds** (77.82 → 77.34, per seed −0.65/−0.53/−0.29/−0.43). That direction is the mechanism working as designed: every club gets a marginally better XI, not just the strong ones, so the champion's margin over the field narrows. It is worth knowing because the **M1 standings gate (`simThrough.test.ts`, champion 78-94 pts) already sits near its floor by construction** and is noisy over its 5-season sample — the gate passes here, but roughly half a point of its headroom is now spent. **Re-measure that gate over ≥15 seasons, not its own sample, before adding more shapes**; a further shape batch pushing champion points down again is the thing that would fail it.
- **"Extend all"** (`core/contractRenewal.ts`, `ui/components/ExtendAllButton.tsx`, 2026-08-21) — one click re-signs every one of the user's players whose deal is in its final year. `renewalsDue(league, group)` answers *who and what it costs*, `extendAllContracts` re-signs exactly that set; the button label is built from the former so it can't promise something the latter doesn't do. Four things worth knowing: **(a) scoped per surface** (`"senior"` Roster / `"academy"` Academy / `"loanedOut"` Loans) rather than one global button, because a loan moves the pid onto the loanee's roster — a loaned-out player is on **no** list but the Loans page, so a single Roster button would either miss him or silently reach players that page doesn't show. **(b)** Terms are each player's **age-based default** (`contractTerms` with no override), so anyone wanting a hand-picked length must be extended individually first; the Division 2 holdouts `wouldRefuseExtension` names are excluded and surfaced as a separate count in the banner, since they wear the same "Final year" badge and nothing re-signs them. **(c)** One `mutate`, not a loop over `extendContractAction` — every mutate writes the whole save, so N calls would be N IndexedDB writes; `extendContracts`/`extendAcademyContracts` (`contracts.ts`) do it in **one pass that keeps untouched players by reference**, which the split-storage dirty-set diff depends on. **(d)** `renewalsDue` walks the player pool, so all three pages hold it behind a `useMemo` keyed on `league` — on Roster it lives inside the existing `derived` memo, because that render body runs **once per dragover event** (see the comment there). No persisted field, no migration, no rng draw.
- **ROSTER_CAP** (30, `core/constants.ts`) blocks user FA signings/buys when full; youth intake/AI FA unaffected (AI trimmed to 25 each offseason).
- **"More minutes" flag** — user flags bench players via `StoredTeam.moreMinutes` (pids; user-only, `setMoreMinutes` in `core/lineup/moreMinutes.ts`, Roster bench-row toggle). Carried through `simThrough`→`leagueMatchData` onto each bench `MatchPlayer.minutesBoost`; in-match, a flagged player gets a `SUB_MINUTES_BOOST` ovr credit in the sub decision (helps him win the "who comes on" pick and clear the bench-quality gate) plus a dedicated boost-driven sub path in `attemptSub` that subs him for the weakest on-pitch player at his position. A nudge, not a force — the gate still blocks a clearly-worse flagged player. Migrated (backfills `[]`).

**Jump forward N seasons, club on autopilot** (`core/autopilot.ts`, `LeagueStore.aiManagedSeasons`, 2026-08-19)
- **The whole feature is one substitution: `meta.userTid` is swapped for `AUTOPILOT_TID` (-2) on a working copy.** Every AI system is already written as "each club except `userTid`" — market, free agency, renewals, `trimRosterSurplus`, `assignAIFormations`, `enforceDivision2Ceiling`, `protectedStarPids`, `financeScaleFor`, the difficulty levers — so pointing `userTid` at nothing drops all of them onto the user's club, which is exactly what "the AI takes over" means. **No branch was added to `simThrough`/`simOffseason`, so RNG stream order for ordinary play is untouched** and a jumped season is what that world would have produced with the club under AI control all along. Any future carve-out that reads something *other* than `meta.userTid` to identify the user's club silently exempts it from the jump; `autopilot.test.ts` catches that by asserting the AI actually traded on the club's behalf.
- **The sentinel must never reach disk** (a save carrying it has an owner who manages no club), so `jumpSeasons` restores the real tid before returning and the whole jump commits in **one** write at the end. **-2, not -1**: -1 is `FREE_AGENT_TID`, a live value in `CompletedTransfer.fromTid`/`toTid`.
- `beginAutopilot` clears the user's `starters`/`transferListed`/`moreMinutes` and the league-level `negotiations`/`inboundOffers`/`loanListings`/`loanRejections`. **Clearing `starters` is the load-bearing one** — `resolveXI` keeps a stored array as long as it still *resolves*, so leaving it has the "AI" fielding the user's eleven for a decade, minus whoever got sold.
- `endAutopilot` repairs the two things that are user-club-only and so froze during the jump: `reconcileScoutingObserved` (kept first-seen for players who were already there, stamped at the return season for arrivals → new signings come back fogged, which is the honest reading) and `ensureUserRosterSafety` (a no-op in practice — the AI leaves a trimmed 25 — but it is the guarantee the club can field a keeper).
- **One worker command for the whole jump, not one per season** (`{type:"jump"}` + `jumpProgress` in `worker/protocol.ts`): the league is `structuredClone`d across the boundary twice total instead of twice per season. Each step seeds itself exactly as the equivalent button click does (`lid*1000 + played.length` / `lid*1000 + season`), so jumping N seasons and clicking through N seasons land on the same world.
- **Measured ~16-19s per season** on the 320-club world (~10s matches + ~7s offseason), hence `MAX_JUMP_SEASONS` 25 and a progress overlay rather than a spinner. UI: `JumpSeasonsForm` (Dashboard card, confirms in place) → `jumpSeasonsAction` → `JumpOverlay` (progress, then a per-season recap derived from `computeClubHistory`). `aiManagedSeasons` is persisted (migrated to `[]`) purely so the recap and any later history surface can say which seasons the user didn't pick the squad for — nothing else in the save records it.
- Known consequences, all deliberate: a relegated user club **is** swept by `enforceDivision2Ceiling` during the jump, its players are buyable by AI clubs, and academy players whose stipend contracts expire are released with nobody to re-sign them (`extendAcademyContract` is user-only).

**Match data & stats**
- **Box scores** — `PlayerMatchLine`/`SeasonStats`. **Match Rating** (`engine/matchRating.ts`, FotMob-style 0-10, position-weighted, damped by minutes). `minutesPlayed` reconstructed from event clocks. `tackles`/`interceptions` split (`pickInterceptor`). Decorative `passes`/`crosses`/`foulsCommitted` attributed post-sim on a separate rng stream (scoreline-invariant). `avgRating` rolled into `SeasonStats`.
- **Assists key off `MatchPlayer.passing`, and event attribution is NOT scoreline-inert (2026-08-22).** The engine carried no passing attribute at all, so `pickAssister` had to weight its draw by `dribbling` — an assist was in effect a dribbling stat. Measured over a simmed league season, that left a creative midfielder's passing essentially unrelated to his assist count (**r = 0.077**, slope +0.005 per 10 points) while dribbling carried it (r = 0.32); keying off `passing` ((shortPass + longPass) / 2) lands **r = 0.307** and drops dribbling's spurious grip to 0.076. Volume is untouched by construction — `pickAssister`'s 25% no-assist roll means league assists are ~0.74x league goals either way (0.735 → 0.736), so this moved *who* is credited, not how much. `scripts/assistProbe.ts` measures it. **The gotcha that generalizes to any attribution change: assists feed `computeMatchRating`, match ratings feed `subPriority` and the bench-quality gate, and substitutions change who is on the pitch** — so "who gets the stat" is a real feedback path into results, and the `touchStats` scoreline hash was rebased for it even though the rng draw count is identical. Don't assume an attribution-only change is safe; `passes`/`crosses`/`foulsCommitted` are inert only because nothing reads them back.
  - **Related, unfixed: some attributes drive OVR (hence wages/value/team rating) but feed NOTHING on the pitch.** A full-back's `speed` (15% of his OVR) and `crosses` (12%) are both dead — `speed` is not on `MatchPlayer` at all, and `crosses` appears only in the `attack` composite, whose group is ST/W/AM/CM, so a full-back's never counts. Centre-back `speed` (6%) likewise. The check: an attribute is live only if it reaches `MatchPlayer` (`core/league/matchPlayers.ts`) or sits in a composite's skill list for a group that actually contains that position (`attack` = ST/W/AM/CM, `defense` = CB/DM/FB, `control` = every outfielder).
- **Suspensions** (`core/suspensions.ts`, 2026-08-16) — cards were simulated from M5 on but expired at the final whistle; `applySuspensions` turns them into league bans (`SUSPENSION_*` in `constants.ts`: 5 yellows → 1 match, second yellow → 1, straight red → 3, **longer-of not sum** when both land together). `SeasonStats` gained `yellowCards`/`redCards`, and `Player` gained optional `suspension` + `yellowCount` (running tally toward the next accumulation ban, distinct from the season total, `-= THRESHOLD` on trigger so a surplus booking carries). Structural notes: **(a)** it is the disciplinary twin of `applyInjuries` and is called beside it once per matchday — the global one-per-matchday tick is *exact* rather than approximate only because every competition is a 20-club round robin, so every club plays every matchday; a competition of another size would silently over-serve bans. **(b)** A ban earned by this matchday's cards skips this matchday's decrement, or the sending-off would partly serve itself. **(c)** **Bans are league-only by design**, which is both realistic and what keeps the blast radius small: `leagueMatchData` gained an optional `unavailable` predicate and *only* the per-competition league call passes `isSuspended` — `cupMatchData` and `nationMatchData` deliberately don't, so a banned player still plays the cup. Cup cards are aggregated onto `CupPlayerLine` as before and carry no ban. **(d)** Reads box-score *lines*, not events, because the line already separates a second yellow (`yellowCards >= 2` + a red) from a straight red. **(e)** **Zero rng draws** — cards are already rolled inside the match, so stream order is untouched. Availability does change who plays, hence composites, hence results, so a scoreline rebase was *expected* here — and **the `touchStats.test.ts` hash did not move, for a reason worth knowing**: that baseline runs `simSeason` (`core/season.ts`), a one-shot harness that computes `leagueMatchData` **once for the whole season** and never re-derives it per matchday, so it has never modelled injuries either and cannot see suspensions. The corollary is that **the scoreline baseline does not guard this path at all**; the gates that do are the `simThrough` ones (`m3-top-scorer`, `m4-multiseason`, `m4-multiseason-integrity`), all green with bans live, while `m1-table-spread` is on `simSeason` and is likewise blind to it. **(f)** Cleared every offseason alongside the injury heal (`clearSuspension`, step 2). **(g)** `suspension`/`yellowCount` are optional and deliberately **not** backfilled (absent = clean record); past seasons' `yellowCards`/`redCards` backfill to 0 rather than being reconstructed, since archived cups have discarded the box scores that would make it uneven. **Rate, measured, and then raised** (`scripts/suspensionProbe.ts` on a 16-competition season, `scripts/cardRateSweep.ts` for the fast single-league version). Nothing had ever checked the booking rate, because cards had no consequence to make it matter; measured, the engine booked **1.42 yellows / 0.098 reds per match** against a real top flight's ~3.5-4.5 / ~0.15-0.25. `YELLOW_GIVEN_FOUL` was therefore raised **0.11 → 0.18** (2026-08-16, user call), landing **2.28 yellows / 0.181 reds** — about half the gap closed, with reds now inside their real band. Four things to know before touching it again: **(a) reds rise with roughly the SQUARE of it**, since a second yellow needs two bookings on one player (second-yellow dismissals 68 → 166 in the sweep while straight reds held at ~40), which is why `RED_STRAIGHT_GIVEN_FOUL` was left alone — the real red band is reached on second yellows alone and raising both overshoots. **(b) Cards cost goals indirectly**: every card calls `bumpEvent()` and stoppage is `STOPPAGE_SECONDS_PER_EVENT` per event, so a busier card sheet lengthens matches — measured at **+0.0105 goals/match** (3.0132 → 3.0237), inside seed noise, but it is the channel that breaks a benchmark if this goes much higher. **(c) Ban load scales super-linearly**: 1102 → **2497** bans/season across 320 clubs (3.4 → 7.8 per club, 1.03% → **1.93%** of appearances missed), because accumulation bans need five hits on one player (485 → 1223). **(d) The remaining shortfall is in FOULS, not cards per foul** — at 13.0 fouls/match the engine already books a higher *share* of its fouls than referees do, so going further means `FOUL_BASE`, which also moves free kicks and penalties. Rebased the `touchStats.test.ts` scoreline hash (the draw *count* is unchanged — `cardRoll` is drawn on every foul either way — but the branch taken moves, so more men are sent off and matches run marginally longer). UI: Dashboard ban list, `SuspensionBadge` on Roster/PitchField, profile header + per-season YC/RC columns, Leaders boards, God Mode "clear suspension". Deliberately **not** added to `ALL_TIME_STAT_KEYS` — that set widens every `ArchivedPlayer` row and `RETIREE_ARCHIVE_LIMIT` has already been cut twice to pay for row width.
- **Live match viewer** (`ui/components/LiveMatchOverlay.tsx`, `ui/live/*`, Dashboard "Watch Next Game", 2026-08-18) — the user's match replayed a minute at a time, with the rest of his division's scores and a live table on a rail. **It re-simulates nothing.** `MatchEvent` already carries the countdown `clock` it happened at, so watching is replaying a recording, which is what makes it safe to drop into an otherwise bit-deterministic sim. Three layers, each testable alone: `live/liveMatch.ts` (pure — `eventMinute`/`eventsThrough`/`scoreAtMinute`/`statsAtMinute`/`scoresAtMinute`/`liveTableRows`), `live/useMatchPlayback.ts` (the clock; **ticks once per MATCH minute, not per frame** — ~90 state updates, since the screen re-derives feed/stats/rail on every tick), and the overlay. Gotchas: **(a) the matchday is committed only when the viewer closes** (`simLiveAction` parks it in the existing `pendingResultRef`, `finishLiveMatch` saves) — abandoning it means the matchday didn't happen, and re-simming reproduces it exactly since the worker seed derives from `lid`+`played.length`. That deferral is **the seam for in-match substitutions**: re-run the matchday with a forced-sub list and commit *that*, so no resumable engine is ever needed (everything before the sub minute comes out bit-identical). Paired with `leagueMatchSeed` above; neither is much use without the other. **(b) xG and possession are deliberately absent from the live strip** — neither is on `MatchEvent` (xG is on the whole-match `PlayerMatchLine`, possession is one full-match tick ratio), so showing them live would mean inventing a number we only know the final value of. They stay at full time. Don't "fix" this without adding a real per-minute series. **(c)** Event rendering is shared with the box score via `components/matchEvents.tsx` (extracted, not copied) so one event can't read two ways; the live feed is **newest-first** while the box score stays oldest-first, which is the one deliberate divergence. **(d)** Turnovers are never shown — they are **81% of all events** (~133 of ~164 per match, measured), i.e. a line every 33 seconds; the "Every chance" toggle switches between all shots (~31/match) and key events only. **(e)** Rewatch of any stored match is free from the same component (BoxScore "Watch it back"), and is how to exercise the viewer without simming. **(f)** `simming` covers the viewer, so it blocks other actions the way the sim overlay does — its league is simmed but uncommitted. **International is still a follow-up.**
- **Cup ties are watchable, and the awkward part is that a cup matchday is an ordinary league matchday too** (`ui/live/liveCandidates.ts`, 2026-08-18). `src/core/schedule.ts` has no cup awareness, so on matchdays 3/7/11/… a qualified club plays its league fixture *and* its cup tie; `liveCandidates` returns both (cup first, the order `simThrough` plays them) and `LiveMatchPicker` asks which to watch — a user call, chosen over queueing both. Both are played either way; the unwatched one keeps its box score. **The cup stores the user's match in four different shapes** and all four are handled: `leaguePhase.matches`, `playoff.ties`, a first leg still held on `koLegs`, and a finished tie on `ties`. **The last one needs splitting** — `resolveTwoLeggedTie` stores `[...leg1.events, ...leg2.events]` on ONE box score with both legs counting down from the same 5400, so replaying it raw would cram 180 minutes onto a 90-minute clock. `splitTwoLeggedEvents` cuts at the single point the clock jumps back up. **This works only because extra time contributes no events** (it updates player lines only), so nothing follows leg 2 — verify that still holds before touching `playExtraTime`. **No schema change and no migration**, which is why this was preferred over storing each leg's box score (that would also have to be stripped by `archiveCup`). Leg 2's events use the reversed orientation, so it is shown with the clubs swapped — which is where it was actually played. Verified against real engine output: 6 of 6 two-legged ties in a simmed season split back to exactly the per-leg scorelines the engine recorded in `tie.legs`. The rail carries the other cup matches that day; the table slot takes the **Swiss league-phase table** on LP matchdays (recomputed per minute from `leaguePhaseTable` with that round's matches at their live score) and is **null for knockout rounds**, which have no table — hence `tableAtMinute` being a nullable function the caller supplies rather than the overlay computing standings itself. Gotcha when writing fixtures: **`isSwissCup` is just `!!cup.leaguePhase`**, and a real cup keeps its league phase all season, so a synthetic `CupState` with `leaguePhase: null` silently gets the *legacy* round names (Round of 16 rather than Quarter-finals).
- **Player Profile stat tables are generated from a column list** (`ui/playerStatColumns.ts`, 2026-08-21) — the league and cup tables on `/player/:pid` share one `StatColumn[]` describing every stat, so headers, cells, the per-90 reading and the **Career** footer all come out of one definition per stat. Three things worth knowing. **(a)** `StatRow` is *structural*, not `SeasonStats | CupStatLine`: a cup line records a strict subset (no xG, passing or cards) and an archived cup has already deleted the box scores those would come from, so the gap is unfillable for past seasons, not merely unwired. Absent fields stay `undefined` through `sumStatRows` — summing them to 0 would turn "this competition never recorded passes" into a career total of zero passes. **(b)** Every column is a pure function of one `StatRow`, which is what makes the career row correct rather than merely convenient: ratios and `avgRating` are re-derived from the *summed* components, so a career figure is volume-weighted instead of an average of averages (`Rtg` reads `ratingSum / (ratedAppearances ?? appearances)` — cup lines only rate appearances with minutes). **(c)** Which blocks appear is keyed off what the player has *recorded*, not his `pos` alone (`statColumnScope`), so a converted keeper keeps his save columns and a keeper carries no permanently-zero shooting block. The two derived differentials were checked for a systematic bias before shipping (they'd be worthless if everyone read positive): league-wide goals/xG is **1.021** and 44% of 10+-appearance keepers post positive goals prevented, i.e. both are genuinely two-sided. Note the render tests can only reach the *open* tab (tab state, no DOM env), so `playerProfileColumns.test.tsx` covers the league table alone — the cup table's correctness rests on the shared column list plus `playerStatColumns.test.ts`.
- **Multi-season history** — `Player.stats[]` is append-only (never pruned), so Leaders browse any past season for free. `LeagueStore.seasonHistory` stores each completed season's final table + champion + awards (Standings had no other persisted history — `league.played` is wiped each offseason). Leaders "All Seasons" adds Career vs Single-Season scope.

**Awards & history**
- **End-of-season awards** — `core/awards.ts` (`computeSeasonAwards`, pure/re-runnable). POTY, Golden Boot, Team of the Season. Formulas layer explicit stat weights + an `ovrBonus` (via `ovrDuringSeason`, reads `Player.hist` not present-day ovr) on top of `avgRating`. `/awards` page; Dashboard "Advance" navigates there post-offseason.
  - **`TOTS_SLOTS` is the award XI's own slot list, NOT `FORMATIONS["4-3-3"]` (2026-08-22).** `GK CB CB FB FB DM CM AM W W ST` — still a 4-3-3 in shape, but the midfield trio is DM-CM-AM. The shipped 4-3-3 had **no AM slot at all**, making an attacking midfielder structurally ineligible: he could win POTY and never appear in the XI. Measured (`scripts/totsSlotProbe.ts`, 6 seasons × 2 seeds × 16 comps): *every* AM POTY winner missed, 14/14, two thirds of all misses; POTY-in-XI 88.5% → **95.3%**. 4-2-3-1 was the alternative and is worse (93.2%) — it buys the AM slot with a CM slot, so CM misses go 1 → 5. **Four consumers must stay on one list or a slot mislabels a player**: `awards.ts`, `worldAwards.ts` (World XI), `frivolities/honours.ts` (`XI_SLOTS`, the all-time award XI, which keys off stored slot *index*), and `Awards.tsx`/`pitchLayout.ts` (`TOTS_LAYOUT`, index-aligned coordinates — a length mismatch silently misplaces a slot rather than throwing; a test pins it). Decoupling from `FORMATIONS` is deliberate: a showcase XI needn't be *fieldable*, so a tactical retune must not reshape an award.
    - **Letting a slot take a player who *covers* it (as a real Team of the Year does) was built TWO ways and rejected both times.** Same-world comparison: this list **91.7%** POTY-in-XI, shipped exact-match 82.8%, flat engine `ADJACENCY` 86.5%, real per-player `secondaryPositions` **75.0% — below the baseline it was meant to beat**. Both cover-rules wreck the XI identically: **CB takes 39-41% of all slots, W falls 18.2% → under 1%**. Cause: **`totsScore` is a *within-position* statistic and exact matching is the guardrail that keeps it valid.** Tackles/interceptions pay DEF 0.03 vs FWD 0.01 on stats defenders collect in far greater volume — measured on one league, the *fifth-best* CB (13.13) beat the *best* winger (9.13) by 4 points, against an adjacency penalty of 0.36 (`POSITION_ADJACENT_PENALTY × AWARD_OVR_WEIGHT`). **The tell is that `secondaryPositions` is the better rule by construction** (per-player, gated on his rating at that slot, and `COVERABLE[CB]` can't reach the wing) **and still scored worst: eligible-player count was never the binding constraint, the score gap was.** A real fix means normalizing `totsScore` per position first — a design change, not a slot edit. Greedy slot-order was *also* suspected and cleared: an optimal max-weight assignment scored identically (85.9% both, off-position slots 59.8% vs 59.2%), so don't build the solver. The probe keeps both cover-rules so the rejection stays reproducible.
    - **Changing this list SHIFTS THE RNG STREAM, so dynasties are not bit-identical across it.** `teamOfSeason` feeds `isProtectedStar`, and `runAITransferMarket` skips a protected pid (`ai/transferMarket.ts:119`) *before* that candidate's jitter draw — so a different XI means a different draw count, hence a different world from the next season on. Inherent to TOTS gating the market; true of *any* change to this award, not of this one specially. Two consequences: a pre/post scoreline-hash comparison is meaningless here, and **the probe's baseline row is only a baseline on an UNMODIFIED tree** — rows *within* one run share worlds and are comparable, but a "shipped" row measured on a tree already carrying this change reads 82.8%/91.7% against the true 88.5%/95.3%.
    - **Stored history is never recomputed** (`migrate.ts` only computes awards for a season that has *none*), so seasons played before this keep a second CM at index 7, which `XI_SLOTS` now labels AM. One slot, older seasons only, ages out. Recomputing isn't sound — retirees are gone from the pool, so a rebuild would re-pick every old XI from survivors. Documented in the Manual rather than migrated.
    - **Measure on `origin/main`, not the local checkout.** The first pass here was run on a tree 38 commits stale and reported a 76.0% baseline; `positionGroup` had since moved AM from MID to FWD (2026-08-14), which cut AM POTY wins and made the true baseline 88.5%. The *structural* finding survived, the magnitude did not.
- **Worldwide awards — Ballon d'Or + World Team of the Year + Goalkeeper/Defender of the Year** (`core/worldAwards.ts`, `computeWorldAwards`, pure/re-runnable/rng-free) — the whole world judged as one field, stored as `SeasonHistoryEntry.world` (`WorldAwards{ballonDOr: WorldAwardEntry[10], worldTeamOfYear, goalkeeperOfYear?, defenderOfYear?}`), surfaced on `/awards`'s **World** tab (per-competition awards move under a "By league" tab) and in Player Profile honours. Score = domestic POTY/TOTS score **+ a league-strength correction** + Continental Cup + international + league title, each part kept on the entry so the UI can show *why* he won.
  - **The league-strength correction is the load-bearing bit.** Match ratings z-normalize *within* each competition, so an uncorrected worldwide award goes to whoever plays in the weakest league (dominating weak opposition scores identically). `leagueStrengthOffsets` adds `(comp mean ovr − world mean ovr) × WORLD_AWARD_LEAGUE_STRENGTH_WEIGHT` (0.05). Ovr is the yardstick precisely because it's the one player number that *isn't* normalized. It's a **unit conversion, not a difficulty knob** — 0.05 is the empirical rating-per-ovr slope inside a league; inflating it over-corrects and makes a strong league's mid-tabler outrank a weak league's best. Tier 2 needs no special-casing: its mean drags its own offset down.
  - **Cup ratings take no correction** — cup matches normalize against the whole pooled 20-club field (`cupMatchData`), making them the only directly cross-league performance number the sim produces. Cup run bonus is keyed by `cupRoundsFromFinal` (`cup/cup.ts`, counts *backwards* from the final so Swiss round 0 = QF and legacy round 0 = R16 don't collide), pro-rated by appearances so a bit-part player doesn't collect a winner's share.
  - **`WORLD_AWARD_CUP_MULTIPLIER` is 1.0, and the intuition that says it should be higher is measurably wrong.** It shipped at 1.5 on "cup goals are rarer, so worth more". They aren't: only elite attackers on the best 20 clubs play the cup, so its per-game scoring rate *matches* the league's (same player, 13 goals in 8 cup games vs 25 in 38 league games), and a premium double-counts. At 1.5 (with rating weight 0.5, run bonus 0.6) the cup component spanned 0-3.1 against a league component spanning 2.4 — nine games outweighing thirty-eight — and 2 of 8 audited seasons crowned a player with a *below-6.8-average* league season. Now 1.0 / 0.2 caps the cup's *individual production* term. Measured effect: winner's median world-ovr rank 259 → 123, and the 85-ovr rank-2 player correctly beat the 73-ovr rank-408 cup runner. **Residual, known and accepted:** the winner is ~top-100 of ~4,200 who played rather than top-20, because the shared `AWARD_OVR_WEIGHT` (0.06) is deliberately small so a big statline can edge out a higher-ovr player — the same trade the per-league POTY makes. Raising it would change the existing league awards too, so it wasn't touched unilaterally.
  - **Team achievement is weighted separately from individual cup production, and deliberately much higher (2026-07-27, user call).** `WORLD_AWARD_LEAGUE_TITLE_BONUS` 0.3→**0.8**, `WORLD_AWARD_CUP_RUN_BONUS` [0.35,0.2,0.1,0.05]→**[1,0.55,0.3,0.15]**, `WORLD_AWARD_WORLD_CUP_BONUS` 0.6→**1.4**. Sized by an explicit exchange rate against `POTY_GOAL_WEIGHT.FWD` (0.08): title ≈ 10 goals, cup ≈ 12, World Cup ≈ 17 — the intended hierarchy is World Cup > Continental Cup > league. **Raising these is not the same risk as raising `WORLD_AWARD_CUP_MULTIPLIER`**: a run bonus is uniform across a squad (modulo `involvement` pro-rating), so it can only move the award *between* clubs, never inflate a player above a better team-mate. The failure mode to watch is therefore "the award became a prize for being on the best team", measured as winner's world-ovr rank. Measured at the time, *before* `WORLD_AWARD_OVR_WEIGHT` existed, over 20 seasons (2 seeds × 10): winner won his league 55%→**65%**, wins the Continental Cup **40%**, World Cup winner in **2 of 5** tournament years; cost was winner's median world-ovr rank 61→108. **Those trophy rates were then partly given back by `WORLD_AWARD_OVR_WEIGHT` below — see its sweep for the numbers that actually ship.**
  - **`WORLD_AWARD_OVR_WEIGHT` (0.14) is an EXTRA ovr term applied by the world awards only**, stacked on top of the `AWARD_OVR_WEIGHT` (0.06) already inside `potyScore`/`totsScore` (2026-07-27, user call). Deliberately a *second* constant: the shared one also drives the per-league POTY / Golden Boot / Team of the Season, so raising it would silently retune three shipped awards to fix a fourth. Principled as well as convenient — every other input is z-normalized within its competition, making ovr the only cross-league-meaningful number, the same property `leagueStrengthOffsets` relies on. **It trades directly against team achievement, and the trade is inescapable:** at 0.14 the winner's median world-ovr rank is **8** (mean 31, worst 150, from 108/210/882), but Continental Cup wins fall 40%→**15%**. Scaling the team bonuses up ~1.8× to compensate restored trophies *and put the rank straight back to median 61* — both levers reorder the same ranking, so raising them together just cancels. The full sweep table lives on the constant. **Do not "fix" the cup rate by raising the team bonuses; that has been measured and it cancels.**
  - **The Ballon d'Or is structurally a striker award — a formula property, not a tuning accident, and only partly mitigated.** Its base is `potyScore`, which contains **no defensive stats at all** (tackles/interceptions/saves live only in `totsScore`), so a CB's entire case is `avgRating` + the ovr terms. The higher per-goal weights for defenders (0.14 vs a striker's 0.08) can't compensate, because they multiply a stat defenders barely accumulate: a striker's 26 goals are worth 2.08 points while `avgRating` across the whole winner pool spans just 6.75–7.49. Before `WORLD_AWARD_OVR_WEIGHT` the split was **75% ST and 0% CB/DM/CM/GK — no defender, holding mid or keeper ever reached the top 10**; at 0.14 it is **45% ST / 30% AM / 20% W / 5% FB**, i.e. raw quality is now the only route in for a non-attacker. **Resolved 2026-08-24 by NOT touching this formula** (user call): rather than give the Ballon d'Or defensive terms, keepers and defenders got awards of their own (next bullet). The Ballon d'Or's arithmetic is byte-identical, so no save's past winners moved. The World XI is unaffected either way (fixed slots off the balanced `totsScore`).
  - **Goalkeeper of the Year + Defender of the Year (2026-08-24)** — `positionAward` in `worldAwards.ts`, ranked shortlists of `WORLD_POSITION_AWARD_SHORTLIST` (5) on `WorldAwards.goalkeeperOfYear`/`defenderOfYear`. **Scored on `worldTotsParts` — the same number that picks the World XI's slots — not on a new formula**, so the Goalkeeper of the Year *is* the World XI keeper **by construction, not by tuning**: `positionAward` takes the max over the GK group and `pickWorldTeam` takes the max over GK-slot candidates, which is the same set and the same score (both apply the qualified-first rule identically). Same argument makes the Defender of the Year always one of the World XI's back four. Measured 100%/16 seasons, but the proof is the reason, not the sample — and see the trophy-multiplier bullet for how nearly this was lost. GK pool = the `GK` group, defender pool = `DEF` (CB+FB, user call; DM stays in MID). Ties break on score → `avgRating` → pid, deliberately **not** the Ballon d'Or's goals+assists, which is meaningless for a keeper.
    - **The three worldwide awards now share `worldAwardParts`**, which takes a base score and a pair of cup weight columns and adds every cross-competition term (strength, extra ovr, Continental Cup, international, league title, domestic cup). Ballon d'Or passes `potyScore`+POTY weights, both position awards pass `totsScore`+TOTS weights. **That is the entire difference between them.** The refactor preserves left-to-right float association, so Ballon d'Or output is bit-identical (45 existing award tests unchanged).
    - **Only ever compares a group against itself, and that is correctness, not scoping.** `totsScore` is a *within-position* statistic (see `TOTS_SLOTS`' note): it pays a defender 0.03/tackle against a forward's 0.01 on a stat defenders collect in far greater volume. Any future "best outfielder" award built on it would be measuring nothing.
    - **`WORLD_TOTS_TROPHY_MULTIPLIER` (3, 2026-08-24, user call) scales every part of the score EXCEPT `league`** — Continental Cup, international, league title, domestic cup — **inside `worldTotsParts`, i.e. for every award on the `totsScore` base: the World XI and both position awards.** The Ballon d'Or (on `potyScore`) is untouched. **The problem it solves is dilution, not a missing term:** trophies were already there at full Ballon d'Or weight, but `totsScore` pays 0.03/tackle and 0.03/interception, so 200 of each is 12 points of a ~21-point score and a league title's 0.8 is under 4% of it — against ~16% for the same title on a striker's ~14-point Ballon d'Or.
      - **It is also the fix for the weak-league drift below — but by a narrower mechanism than it looks, and the first version of this note got it wrong.** The multiplier does **not** touch ovr or `leagueStrengthOffsets`: both sit inside `league`, the one part deliberately left alone, so if anything it makes them a *smaller* share of the total. The whole effect comes from the two multiplied terms that are cross-league-meaningful by themselves — the **Continental Cup** run (weak leagues' clubs rarely go deep) and the **international** campaign (weak nations rarely win). The other two, league title and domestic cup, are *league-relative* (Belgium's champion wins Belgium as surely as England's wins England) and contribute nothing to it. Corollary worth holding onto: diluting ovr is precisely *why* the keeper's median ovr rank slipped 3 → ~8 — one lever, both effects.
      - **Applying it at the shared base rather than at the awards is the load-bearing detail, and it was got wrong first.** It shipped for a few hours on the two position awards only, leaving the World XI on the plain score — which looked like the conservative choice (don't retune a shipped award) and wasn't: the XI slot then went to the best performer while the award went to the best performer who *also won things*, so the Goalkeeper of the Year stopped being the XI's keeper **about two thirds of the time** (17% and 50% agreement measured), on two panels of the same page. **A correction that belongs to a shared base has to be applied at the base, or everything built on it quietly stops agreeing.** Fixed by folding it into `worldTotsParts`; the by-construction agreement above is restored and re-verified at 100%.
      - **Measured, 2 seeds × 6 seasons, against the same runs' Ballon d'Or at 10/12 big-four winners:** keeper winners from the big four **12/16 → 11/12**; defender **9/16 → 9/12**; defender winners from Belgium/Turkey **5/16 → 1/12**; defender score from tackles+interceptions **50% → 37%**; defender's worst ovr rank **112 → 25**. Proportion check on the same run — share of the winning score from beyond his own league: Ballon d'Or **16% / 15%**, defender **20% / 18%**, keeper **29% / 24%** (2 seeds), i.e. about **1.2x** the yardstick for the defender award and **1.7x** for the keeper, so the defender lands just above the yardstick and the keeper well above it (a keeper's `totsScore` carries far less volume, so the same tripled trophies land on a ~16-point score against a defender's ~24; a per-group multiplier is the honest fix if that ever wants evening up). Cost: the keeper's median ovr rank among keepers **3 → ~8**, which lands it on the Ballon d'Or's own standard (median 8) — the same trophies-vs-ovr-rank trade `WORLD_AWARD_OVR_WEIGHT`'s sweep documents, and it cannot be won on both axes at once.
    - **Lowering the `totsScore` counting-stat weights instead of multiplying trophies was measured and REJECTED (2026-08-24, `scripts/totsWeightProbe.ts`).** It is the structurally better fix (it lifts ovr and rating, where the multiplier squashes them), but `totsScore` also picks every league's Team of the Season, and **a TOTS place turns out to be how 62% of all protected stars get onto the list** (30.5 of 49.2 per season have ovr < 80). Measured 4 seeds x 6 seasons, pooled over all 24 season-measurements: protected stars **48.0 -> 55.2 (+15%)**, TOTS-carried **+30%**, defenders among them **+55%** — a real shift to a tuned difficulty lever, and the only consistent number in the whole exercise. Against that, the award gain is small and mixed: defender rank mean **19.1 -> 15.6**, keeper rank mean **6.0 -> 8.6 (worse)**, big-four winners essentially flat (96%/75% already). **A smaller multiplier is worse than none** — on identical seeds x1.5 gives worse defender winners than x1, because once the weights are sane, ovr carries the signal and trophy weight re-dilutes it. **Methodology warning:** an earlier 2-seed pass reported the keeper improving 8.5 -> 3 and drove a wrong recommendation; two seeds is 12 numbers spanning ranks 1-138, and the noise exceeds every effect except the protected count. Pool the season-measurements; never take a median of per-seed medians.
    - **`WORLD_AWARD_TROPHY_STRENGTH_WEIGHT` (0.06, floor 0.25, cap 2, 2026-08-24, user call) scales the league title and the domestic cup by how strong the league that awarded them is** — `clamp(1 + ovrDelta * weight)`, applied in `titleComponent`/`domesticCupComponent` and therefore to **all three worldwide awards including the Ballon d'Or**. Those two are the only *league-relative* trophies (every country crowns a champion regardless of standard), which is exactly the gap the trophy multiplier's note identifies as contributing nothing to league strength; the Continental Cup and international campaign are contested between leagues and correctly take no scale. The **floor is for the domestic cup, not the title**: a tier-2 league title scores 0 anyway, but a tier-2 club really can win its domestic cup, and a second division sits far enough below the world mean to drive the raw scale negative — turning a trophy into a penalty. `leagueStrengthOffsets` now returns the **raw ovr delta** and callers convert (rating units for the match-rating correction, this scale for trophies), so there is one measure of league strength rather than two.
      - **Measured, 2 seeds × 6 seasons: real but narrow.** 2 of 12 keeper winners changed, both toward stronger leagues (Portugal → England on one seed); **0 of 12 defender winners and 0 of 12 Ballon d'Or winners moved**. Beyond-league score share rose ~1-3 points. The reason it is narrow is structural and worth knowing: **the scale only bites on players who actually won a title**, and most weak-league award winners never won theirs — so this correctly prices a weak championship without touching the weak-league drift, which has a different cause.
    - **The weak-league drift is NOT caused by weak leagues inflating the counting stats — measured and disproved (`scripts/leagueVolumeProbe.ts`, 2026-08-24).** That was the standing explanation here and it was wrong; every observation behind it came from award *winners*, who are maxima. Across the whole population, tier-1 mean tackles+interceptions **per appearance** runs England 4.021, Germany 4.037, Belgium 4.114, Turkey 4.172 — a correlation with league strength of −0.60 but a **spread of only 3.8%**, worth ~0.17 points a season against an ~11-point production term. **Individual** variation dwarfs it: award winners spanned 305 to 430 defensive actions, a 3.75-point spread, against the ~2 points of ovr advantage a strong league confers. So a per-league scale factor on the stats would correct ~4% of the problem; the only thing that would work is normalizing the production term *within position across the world*, which can be done inside `worldAwards.ts` alone and so would not touch the per-league Team of the Season or the sim.
    - **Normalizing the production term within position was BUILT, measured and REVERTED (2026-08-24, user call).** This is the fix the bullet below asks for, so read this before building it again. It scored `totsProduction` (the counting-stat part of `totsScore`) as standard deviations from the mean at the player's own `pos`, worldwide, **inside `worldAwards.ts` only** — so unlike the rejected reweight it left the per-league Team of the Season, the protected-star list and the rng stream untouched by construction. It is a genuine trade, not a win. Same seed, same everything else (seed 3, 6 seasons): defender ovr rank **median 14 → 20, worst 37 → 144**, against CB/FB winners **5/1 → 2/4** and shortlists **25/5 → 18/12** (the CB/FB fix reproduced on every seed tried: 24/6 and 28/2 also became ~18/12). Weak-league winners dropped out too. So it does fix the positional imbalance and it costs winner quality, and the user chose quality.
      - **Two candidate causes were each ruled out with a run, so don't re-try them:** the production weight is not the lever (1.0 measures identically to 1.5 — same median, same winners), and neither is the trophy multiplier (×2 gives median 21 against ×3's 20 on the same seed). Dropping to **×1 is much worse** (median 64, weak leagues back, full-backs overcorrected to 4 of 6), which is the evidence that `WORLD_TOTS_TROPHY_MULTIPLIER` is doing real work as a proxy for *playing at a good club* rather than merely weighting trophies.
      - One config is worth knowing about if this is revisited: normalization at ×2 landed the beyond-league score shares almost exactly on the Ballon d'Or's (**14% / 17% / 20%** for Ballon d'Or / keeper / defender) with CB/FB at 3–3 — the best-calibrated arrangement seen, though its ovr rank was no better.
    - **Known, still only partly fixed: the defender award rewards volume of defending, not quality of it.** Tackles/interceptions are raw counts and are **not** z-normalized the way match ratings are, so `leagueStrengthOffsets` (which only shifts the rating term) cannot correct them. Measured 2 seeds × 8 seasons (`scripts/positionAwardAudit.ts`): **50% of the winner's score came from tackles+interceptions** (37% after the multiplier), winner's ovr rank among defenders **median 16, worst 112** (against the keeper award's median 3, worst 19), the two weakest leagues took 5 of 16 winners (1 of 12 after), and CBs took 14-15 of 16 against FBs' 1-2 (10 of 12 after). **This is pre-existing and the trophy only surfaces it** — before the multiplier, the winner was by construction the same man the World XI's back four was already being built from. (Audit gotcha: read the winner's position off `entry.awardWinners`, not the live pool. Players are reclassified over a career, so a present-day lookup reported a **DM** winning a defenders' award, which `positionGroup` makes impossible — DM is MID.) A real fix means normalizing `totsScore` within position, which would retune every Team of the Season, so it is its own change.

- **Frivolities** (`core/frivolities/`, `/frivolities`) — BBGM-style all-time lists, seven tabs on one page (GOAT / Awards / Records / All-Time Leaders / International / Player Bios / Club Records). Every derivation is **pure, read-only and rng-free**: `careers.ts` (`allCareers` flattens live `Player`s *and* archived retirees into one `CareerRow`, so no list can quietly cover only the living), `records.ts` (best/worst team seasons, peak ovr, career + single-season leaders, biggest fees), `bios.ts` (age extremes, per-nationality breakdown, one-club men, name tallies — **current pool only, deliberately**: "who's the tallest player" is a question about the league you're managing now), `clubs.ts` (trophy cabinet, title droughts, transfer spend), `honours.ts` (the Awards tab — see below), `stats.ts` (`ALL_TIME_STAT_KEYS` + `totalsOf`/`bestSeasonsOf`, the shared career-aggregation layer), `leaders.ts` (`allTimeLeaderBoards`), `international.ts` (`allTimeInternationalBoards`/`cappedNationalities`). Gotchas: **(a)** team seasons rank by **points per game**, not raw points — league sizes differ between competitions, so raw points would rank the biggest league's clubs above better seasons in smaller ones; **(b)** a season is filed under its `compsByTid` snapshot, never the club's *current* competition, or promotion/relegation misfiles a D2 title as a D1 one; **(c)** both `records.ts` and `clubs.ts` skip a transfer whole if **either** side is `FREE_AGENT_TID` or it's a loan — the two surfaces must agree on what counts as a purchase (a test caught them disagreeing); **(d)** Records deliberately carries only what All-Time Leaders *can't* — team seasons, peak ovr, seasons-played and transfer fees — since every plain stat board is reachable there; **(e)** the trophy cabinet sorts by `totalTrophies` because that's the column it leads with (ranking by league titles under a "Total Trophies" heading reads as a bug); **(f)** the **International** board ranks `caps`/`intlGoals`/`intlTitles` off `CareerRow` and is deliberately **not** folded into `ALL_TIME_STAT_KEYS` — those are `SeasonStats` league stats with a career total *and* a best-single-season figure, whereas an international record is three running counters on `Player.intl` with no per-season lines surviving archival and no "best season" to rank; sharing the key set would mean faking half of `StatTotals`/`BestSeasons` for every career. It is the board that depends most on the retiree archive (an all-time top scorer is nearly always retired), and it inherits `allCareers`' senior-league-appearance filter, so a capped player who never played a club game is absent; **(g)** **roster continuity was deliberately left out** — no per-season roster is persisted, and rebuilding it from `Player.stats` counts every retired player as a departure, making the past look permanently more turbulent than the present.
- **Awards record book** (`core/frivolities/honours.ts`, Frivolities → Awards, 2026-08-14) — every *individual* honour (Ballon d'Or / World XI / POTY / Golden Boot / TOTS) counted per career, per club and per country, plus every stored Ballon d'Or shortlist entry ranked by score ("most dominant seasons", expandable into the entry's league/cup/intl/title parts), a roll of honour, and youngest/oldest winners. `computeAwardTrivia` is **one pass over `seasonHistory`**; the per-player counts reuse `goat.ts`'s `computeHonours` so the two boards can't disagree about the same trophy, and the UI re-ranks in place with `sortAwardRows` rather than recomputing per selector change. Gotchas: **(a)** the **whole `world.ballonDOr` top-10 is persisted**, which is the only reason a runner-up/third/shares/streak board is possible — every other consumer reads `[0]` alone; shares (win 1.00 … tenth 0.10) are scored against *today's* `BALLON_DOR_SHORTLIST`, so changing that constant rescales past seasons. **(b)** Club attribution differs per award: a Ballon d'Or carries its own `tid` on the entry, everything else needs club-per-season off `CareerRow.seasons` — the same squad-membership rule `playerHonors.ts`/`goat.ts` attribute titles with, never the present-day club. That lookup is built **only for pids that won something**; the full map is every squad membership of every career (six figures on a long dynasty) against a few hundred that are wanted. **(c)** Team trophies are deliberately *not* counted here (GOAT and Club Records already do), so every ranking key is an individual award. **(d)** An award pid the save no longer knows — a retiree below `isArchiveWorthy` — keeps its row under a `Player <pid>` placeholder (same convention as `records.ts`'s fee board) but can't be filed under a club or country. **(e)** `CareerRow` gained `born` for the age boards: age is `season - born` at the time he won it, never his age today. **(f)** The **club all-time XI** (`awardXIForClub`, rendered on the same `pitchLayout` 4-3-3 the Awards page uses) is derivable *only* because `teamOfSeason`/`worldTeamOfYear` are index-aligned with `FORMATIONS["4-3-3"]` — the slot a pid sits at **is** the position he was picked in, so the XI is a record rather than an invented ranking. Slots fill greedily by `GOAT_WORLD_XI_WEIGHT`/`GOAT_TOTS_WEIGHT` (reused so the two boards can't disagree on what a worldwide place is worth) with **one slot per player**: a man picked at two positions across his career would otherwise print twice in one XI, which reads as a bug. An unfilled slot stays empty rather than taking the nearest approximation.
- **GOAT rankings** (`core/frivolities/goat.ts`, default tab) — `playerGoatRanking`/`teamGoatRanking`, a **first-draft, taste-based formula** whose every weight lives in the `GOAT_*` block in `constants.ts` and is meant to be argued with. **Feeds nothing in the sim.** Player score = peak + prime + longevity/rating + awards + trophies + production, returned as `components: GoatComponent[]`, each carrying the `GoatTerm[]` (`count`/`weight`/`points`) behind it, so a row expands to its full arithmetic; the table generates its columns *from* `components`, which is what stops a component counting toward the score without appearing (that shipped once). **Rounding happens once per component, never per term** — a term must show exact `count x weight` or a reader sees "24 x 0.15 = 4" and stops trusting the board — while whole-number components still sum exactly to the whole-number score, so columns always reconcile with the total and the ranking can't display out of order; `prime` (area under his career ovr curve above `GOAT_OVR_BASELINE`) is weighted to out-earn `peak` over a long career, which is the distinction the formula exists to make. Club score = trophies (dominant) + consistency (top-4 finishes, top-flight seasons, and per-season ppg surplus over `GOAT_TEAM_PPG_BASELINE`, halved in tier 2 so dominating a division you shouldn't be in isn't a case). Gotchas: **(a) known positional bias, documented not fixed** — the Ballon d'Or/POTY carry no defensive stats (see the world-awards notes), so the player board tilts to attackers; the position-slotted TOTS/World XI terms are the counterweight and are weighted above their rarity for that reason. A real fix means giving those awards defensive terms. **(b)** `computeHonours` derives every award and trophy from `seasonHistory`/`cupHistory` **by pid**, one pass over history (not a lookup per player — that's quadratic on a long dynasty), so it works identically for the living and the archived. **(c)** League/cup titles need club-*per-season*, which is why `ArchivedPlayer.seasons` (`{season,tid,ovr}`) exists: snapshotting an honour *count* at retirement instead would put retirees on a separate code path **and** silently lose a title won in the player's final season, since offseason step 3 runs before that season's awards/champions are computed.
- **All-Time Leaders replaced Stat Leaders' "All Seasons" scope (2026-08-04).** `/leaders` is now per-season only — its `Scope`/`careerTotals`/all-seasons branches are gone — and the career + best-season boards live on Frivolities instead. **The move is a correctness fix, not just tidying:** Leaders reads the live player pool, and retirement deletes from it, so its career board silently meant "career totals among the living"; `allTimeLeaders` reads `allCareers` and so covers retirees. Two deliberate behaviour changes: **(a)** it ranks the **whole world**, not one competition — a career crosses tiers and countries, and an archived retiree keeps no competition history; **(b)** single-season scope shows **one row per player** (his best), where Leaders listed every season as its own row — a retiree only keeps his best season, and keeping them all is precisely the save-size blowup the archive avoids, so one-row-per-player is the only rule that reads the same for the living and the retired. `avgRating` uses `RATING_LEADER_MIN_CAREER_APPEARANCES` (career) and the new `RATING_LEADER_MIN_SEASON_APPEARANCES` (single, a *flat* floor because these boards span competitions with different season lengths and a retiree carries no games-played denominator). **The tab opens on a BBGM-style grid of top-`ALL_TIME_OVERVIEW_LIMIT` (10) cards, one per stat, each opening its full `ALL_TIME_LEADER_LIMIT` (30) board (2026-08-20)** — which is why `allTimeLeaderBoards` exists and the old per-stat `allTimeLeaders` doesn't: the grid needs all fourteen boards, and gathering `allCareers` (a walk over every living player *and* the retiree archive) per board would pay for that walk fourteen times. Every board goes through the same `rankCareers`, so a card and the board it opens can't disagree. **The International tab got the identical treatment in the same change** (`allTimeInternationalBoards`, `INTL_OVERVIEW_LIMIT`, three counters, country filter applied once above the grid), and both grids share `BoardCard`/`CardGrid`/`BackToGrid` in `Frivolities.tsx` so they can't drift into two different-looking things. Two shape constraints worth keeping: the card *header* is the click target rather than the whole card, because the rows carry player links and a `<button>` can't legally contain them; and cards drop the "Retired" badge the full boards keep, since a badge on a name wraps every row it lands on at card width. **Rows for the user's own players are highlighted** (BBGM does this) via the existing `.team-highlight` class Standings/Power Rankings already use for his club, on cards and full boards alike (`RankTable` gained an optional `highlight` predicate). The test is `isUserPlayer`: `clubs.includes(userTid) || tid === userTid` — `clubs` is *appearances*, so it means "played for you" past or present, which is the question an all-time board asks; the `tid` half is there because a just-signed player with no league game yet is shown wearing the user's crest and would otherwise read as a bug.
- **Retiree archive** (`core/players/archive.ts`, `LeagueStore.retiredPlayers`) — the permanent career record the all-time lists read, since `simOffseason` step 3 **deletes** retirees from `players` outright. Distinct from `players/retirements.ts`'s `RetiredPlayer` (a per-season farewell notice capped at `RETIREMENT_NOTABLE_LIMIT`, attached to one `seasonHistory` entry) and deliberately not merged with it. **Volume is the whole design constraint:** measured 661 retirees *per offseason* on a 240-club world (~66k rows/100 seasons ungated — the 88 MB save shape again), of whom only 351 ever made a senior appearance and 16.5 ever peaked at ovr 70. Two defences: a quality gate (`isArchiveWorthy`: ≥1 senior appearance **and** (`RETIREE_ARCHIVE_MIN_PEAK_OVR` 70 **or** `RETIREE_ARCHIVE_MIN_APPEARANCES` 200)) and a hard `RETIREE_ARCHIVE_LIMIT` (**20,000** as of 2026-08-22, was 2000 — see the schema-v3 entry under "Split player storage" for why the old value was bounding *write latency* rather than disk, and `scripts/archiveGateProbe.ts` for the ~270-a-season rate it is sized against) that prunes by **career score, not age**, so a long dynasty keeps its season-3 legends and drops its season-97 journeymen. **Honours are NOT stored** — every award is already on `seasonHistory[].awards`/`.world` keyed by pid, so they stay derivable forever. *Derivable is not the same as resolvable*: the award survives, the man it points at does not, which is what `SeasonHistoryEntry.awardWinners` exists to fix (next bullet). `peakOvr` reads `hist` (retirement rolls *after* progression's final decline, so `player.ovr` is a rating he never played at); best-single-season goals/assists *are* stored, being unreconstructable once the stat lines go. Row shape is `seasons: ArchivedSeason[]` (`{season,tid,ovr}` per season played — raw data, deliberately not a snapshot of derived honours; see GOAT gotcha (c)) + `totals: StatTotals` + `best: BestSeasons` (every key in `ALL_TIME_STAT_KEYS`, each best carrying `{value, season, appearances}` so the rate-stat floor applies to retirees too) — generic rather than a handful of named fields, so a new leaderboard stat needs no archive change. That widened the row ~3×, which is why `RETIREE_ARCHIVE_LIMIT` came **4000 → 2500 → 2000** (the second cut paid for the per-season line) to hold the same save-size budget. Pure/rng-free → sim results bit-identical. Migrated to `[]`; old saves' pre-existing retirees are unrecoverable (deleted without a trace) and the UI says so.
  - **Retirees are clickable and have a career page (2026-08-11).** `/player/:pid` falls back to the archive when the pid isn't in `players` and renders `ui/pages/RetiredPlayerProfile.tsx` instead of "Player not found" — so *every* historical link works, which was the point of keeping the record in the first place. Two shared pieces make that hold everywhere rather than on one page: **(a)** `computeArchivedHonors` (`core/playerHonors.ts`) — the honours walk is now parameterised by "which squad was he in that season" (`Player.stats` vs `ArchivedSeason`), so living and archived players share one derivation and can't drift (same reason `goat.ts`'s `computeHonours` exists as its sibling; the two still must agree). **(b)** `usePlayerRefs`/`PlayerRefLink` (`ui/components/PlayerRefLink.tsx`) — pid → name/nationality across the pool *and* the archive, used by every surface that used to print `Player 4821`: News Feed, Transfers, Finance, Club History, World Cup scorers, Season Preview's farewell list. **Cached in a `WeakMap` keyed on the `LeagueStore` object, not `useMemo`** — it renders once per row on lists of dozens, and a per-instance memo rebuilds the ~6000-entry map for every one of them; the context hands out a fresh league object per commit, so identity is the right key. The page deliberately shows *less* than a living profile (no attributes, no per-season stat lines) rather than faking it, and a retiree below `isArchiveWorthy` still renders as an unlinked name — callers must keep their fallback.
- **Award winners carry their own names (`core/awardWinners.ts`, `SeasonHistoryEntry.awardWinners`, 2026-08-21).** Every award is stored as a bare pid (`playerOfSeasonPid`, `goldenBootPid`, `teamOfSeason[]`, `world.ballonDOr[].pid`, `world.worldTeamOfYear[]`), and a pid stops resolving the moment retirement deletes the player and the capped archive declines to keep him. Measured across four real saves, winners resolving to *nobody*: **11 seasons 0/11 Ballon d'Or and 8/176 (5%) league POTY; 32 seasons 0/32 and 152/512 (30%); 100 seasons 30/100 and 1,177/1,600 (74%)**. The league POTY goes first and worst because it is per competition — a second-division or weak-league winner is exactly the modest career `isArchiveWorthy`/the archive-score prune drops first — while the Ballon d'Or lasts longer only because its winners are elite. `snapshotAwardWinners` copies name/nationality/pos/`ovrDuringSeason`/`SeasonStats.tid`/born for every pid a season's awards name, at **offseason step 3.65**, off `league.players` (still the pre-progression, pre-retirement pool both award passes scored). Pure, no rng draw, so sim results are bit-identical. **Measured cost: 190 winners = 18.5 KB/season on the 16-competition world, ~1.8 MB per century** (14.5% of a season-history entry) against a save already 12.9 MB after one season; `scripts/awardWinnerSize.ts` re-measures it. **The obvious alternative, exempting winners from the archive prune, does not scale and was rejected on arithmetic**: 16 competitions × 13 places is up to 229 pids a season, 10-20k over a century, against a `RETIREE_ARCHIVE_LIMIT` that was 2,000 rows at the time (20,000 since 2026-08-22). Three consequences. **(a)** Read order everywhere is career → archive → snapshot; `frivolities/honours.ts` also *stands a `CareerRow` up from the snapshot* for a decorated player the save has otherwise forgotten, or the "most decorated careers" board silently omits most of its own winners — those rows carry empty `totals`/`best` and are built **only** inside `computeAwardTrivia`, never mixed into `allCareers`, where a row of zeroes would land on every statistical leaderboard. It is also what makes a forgotten winner's award credit his club and his country, which a bare pid could not. **(b)** A snapshot-only winner has **no profile page**, so `PlayerRef.linkable` / `AwardSubject.linkable` are false for him and his name renders unlinked; `Frivolities`' `PlayerCell` now gates on `linkable`, not on mere existence. **(c)** `migrate.ts` backfills past seasons from the live pool then the archive — complete for a young save, partial for an old one, and **it must run**: this is the one thing that genuinely cannot be reconstructed later, so migrating freezes the loss where the save currently stands. It never refreshes an entry that already has the field (anything missing then is missing now; deletion runs one way). **`loadLeague` writes that backfill straight back to disk** (`namedAwardWinners` alongside `shrankOnLoad`) — the one migration whose result must be persisted rather than left in memory, since every other backfill recomputes identically next load while this one copies names off players the next offseason deletes for good. Fires once per save, since afterwards every entry has the field.
- **The name table: the archive's cap was the bug, and splitting the row fixes it at the source (`core/players/playerNames.ts`, `LeagueStore.playerNames`, 2026-08-22).** `ArchivedPlayer` answers "what was his career" — totals, a best season per ranked stat, a line per season — which costs **2,204 bytes** and is why `RETIREE_ARCHIVE_LIMIT` capped it at 2,000 when this was written. "What was his name" is a different question with a different shape: five fields, **82 bytes measured**, wanted for *every referenced pid* rather than the best 2,000 careers. Conflating them is what made a long save forget itself — at season 101 the prune bar had risen to **peak ovr 79** and 78% of historical pid references resolved to nobody. `extendPlayerNames` writes a row at retirement for each retiree the surviving history still points at; `playerNameIndex` is the read side, wired into `usePlayerRefs`, `Awards`' `subjectResolver` and `honours.ts`'s `identity()`. Measured over a simmed dynasty (`scripts/playerNameProbe.ts`): **nameless references 0 in every season**, table ~**300 rows / 21 KB per season** (~4 MB at season 159), against an archive already 448 KB by season 9. Pure, no rng draw, appended after everything else, so sim results are bit-identical. Four points worth keeping. **(a) Only retirees need a row, and the asymmetry is load-bearing**: `cullFreeAgentPool` deletes its victims' transfers, news events and cup lines *along with them*, so a culled nobody strands nothing; retirement deliberately keeps those records, which is exactly why the name has to be kept too. **(b) Bounded by construction, never by a cap** — a row exists only for a pid something references, so the table cannot outgrow the records pointing into it. A fixed cap is precisely what `RETIREE_ARCHIVE_LIMIT` does and it is the bug; the economics agree, since names are ~5% of the cost of the ~900 KB/season of history that references them. **(c)** It is a name, not a career: `linkable` stays false and there is no profile page. **(d) Forward-only.** `migrate.ts` backfills `[]` and deliberately reconstructs nothing — the live pool, the archive, the farewell lists and the award snapshots are all read directly by the UI already, so copying them in would duplicate rows that resolve anyway and still name nobody new. Same one-way door `awardWinners` documents.
- **The farewell lists are a fourth name source, free and retroactive (`farewellIndex`, `core/players/retirements.ts`, 2026-08-22).** `awardWinners` above stops the loss *going forward*; it does nothing for a save that has already lost its winners, because `migrate.ts` can only backfill from the pool and the archive — the two places that already resolve. Measured on the real 100-season save: the backfill moves named award places **30.2% → 30.2%**, i.e. nothing. Its whole value is freezing the current 30% before the next offseason takes more of it. What *does* recover ground is `seasonHistory[].retirements.notable`, which has been copying name/nationality/pos down since long before either field existed and was never read as a name source. Folding it in as the last tier of `usePlayerRefs`, `Awards`' `subjectResolver` and `frivolities/honours.ts`'s `identity()` recovers, on that same save: **award places 30.2% → 34.9% (+1,056), transfer rows 21.7% → 24.8% (+9,323), news events 22.2% → 26.7% (+11,343), cup stat lines 26.9% → 33.5% (+2,268)** — verified by `scripts/farewellRecoveryCheck.ts`, which also asserts no reference *stops* resolving. **Read-only and derived, so there is no schema change and nothing to migrate** — an old save gets these names back on load. Bounded by `RETIREMENT_NOTABLE_LIMIT` a season (~1,500 entries per century), so the index is cheap to build per league object. Two gotchas. **(a)** A farewell row records his **final** season, so its `ovr`/`tid` describe a different season from any earlier award — `AwardSubject.ovr` is therefore `number | undefined` and the Team-of-the-Season chip shows no rating rather than a confident wrong one; `honours.ts` takes the name and leaves `born` null instead of deriving it from his retirement age. **(b)** It is a name, not a career, so `linkable` is false — and **that flag must be tested, not the ref's existence**: `SeasonPreview` gated its farewell table's profile link on `refOf(pid)` being truthy, which was already wrong for award-snapshot pids from the previous bullet and became wrong for every retiree once this tier landed (an existing test caught it). The remaining ~65% on that save is genuinely unrecoverable: nothing ever wrote those names down.
- **Career honours on a Player Profile** — `core/playerHonors.ts` (`computePlayerHonors`, pure/derived, no schema change), the sole source of the profile's "Awards & Trophies" pills. Individual awards (Ballon d'Or, World XI, POTY, Golden Boot, TOTS) are stored by pid so they need no attribution; a **league title is a team honour and must be attributed**, and the gotcha is *what you attribute it with*. It reads `Player.stats[season].tid` — `accumulateStats` (`simThrough.ts`) opens a stats row for **every player on either roster** each matchday (not just those who appear, verified against a simmed season), so that row is the game's only per-season squad-membership record, and it's the same signal `clubHistory.ts` attributes award pids with. It must **not** use `teamForSeason`: that walk guesses at seasons before a player's first recorded transfer and falls back to his *present-day* club, which handed every arrival the club's whole back catalogue of titles — including seasons before he was generated (the bug this replaced). Known limitation, shared with open decision #4: `stats.tid` is the club he *finished* the season at, so a winter arrival at the champions is credited and a winter departure isn't.
  - **Sibling of `frivolities/goat.ts`'s `computeHonours`, and the two must agree.** They exist separately for a real reason — this one takes a live `Player` for one profile, that one makes a single pass over history for *every* career including archived retirees, who have no `Player` at all — but they answer the same question and a divergence shows up as a profile and a GOAT row disagreeing about the same trophy. `goat.test.ts` pins them together for a living player; change the attribution rule in one and fix the other.

**Squad development**
- **Youth Academy** (user's club only) — `StoredTeam.academyRoster`, flat stipend wages (`academyContractTerms`). Actions in `core/freeAgency.ts` (`signToAcademy`/`promoteFromAcademy`/`releaseAcademyPlayer`). `ensureUserRosterSafety` auto-promotes to `ROSTER_SAFETY_FLOOR` (18) each offseason so the user's unmanaged roster can't drop below 11 and crash the engine. `/academy`, `/incoming-talent` (youth prospects), `/free-agents` (older FAs). AI youth still goes straight to roster.
- **Dynamic academy attraction** — recent within-division finishing rank shifts youth-intake quality (`core/players/academyForm.ts`). **Zero-sum by construction** (one club's + is another's −), so it can't reopen the inflation ratchet.
- **Youth base has a soft floor — the flat offset underflowed at weak clubs (`youthGenerationBase`, `players/youth.ts`, 2026-08-17).** `academyBase - YOUTH_BASE_OFFSET` is a *flat* subtraction (34) against an `academyBase` spanning **18.8–63.0**, so it went **negative for 73 of 320 clubs** (as low as −15.2). Every rating then generated below zero and clamped to `RATING_MIN` (1), which yields not a weak player but a **destroyed** one — an ST with speed/passing/dribbling/positioning all 1, plus survivors only where the `star`/`H` tiers or the base-independent `ABS` tier landed above the floor. Measured, one offseason on a fresh world: **472 of 1268 new youth (37%) at OVR 0–15, 98% of them released to free agency the same offseason** (`trimRosterSurplus` ranks by ovr, so they are always the worst at their position). Surfaced by a user save with a 16-year-old ST at **OVR 9**. Fix is a **softplus soft floor**, and the shape is load-bearing: **(a)** `YOUTH_BASE_OFFSET` is a swept anti-inflation constant (40-season mean flat — see its comment), so healthy clubs must be untouched: at the shipped FLOOR=1/SOFTNESS=1 the lift at raw base 6.3 and 11.3 is **0.00** and only 110 clubs move at all. **This is the trap:** a first attempt at FLOOR=4/SOFTNESS=5 looked smooth but lifted **295 of 320 clubs by a mean of +3.67 points** — only 73 are broken, but 275 sit below raw base 20 — which raised end-of-dynasty OVR 1.3-3.1 in *every* league (big four included, via their own tier 2 and the upward drain) and took the solvency audit from 1 failing seed to 4. Anchor "healthy" at raw base < 0, not at some comfortable-looking number. **(b)** A *hard* `Math.max` floor makes every club below the cut generate **identical** youth, erasing the academy gradient exactly where the country ladder is most fragile. **(c)** A proportional offset changes every club and would require redoing the sweep. **(d)** The intended senior→youth gap is ~33 OVR (measured 31.8–33.8 across the healthy range) and that gap is simply **unavailable** to a club whose seniors average 29.4 — the scale bottoms out — so it *must* compress at the bottom; softplus does that smoothly and stays strictly monotonic. Result: the weakest club in the world goes from youth OVR min/mean/max **1/4.1/9 → 5/13.5/25** vs its seniors averaging 29.4, and the strongest club is **bit-identical** (base 29.00, 30/40.1/52). Audited (`scripts/weakLeaguesAudit.ts`, 20 seasons x 4 seeds, run per-seed): ladder OK every seed, mean rung gates pass, and **4/4 seeds solvent where main is 3/4** (main deficits on seed 2 at -£2.0M). **Accepted cost:** clubs between `academyBase` ~18.8 and ~25.5 now generate near-identical youth, so `ACADEMY_FORM_SWING` (added to `academyBase` *before* the transform) has less bite down there. **No rng draw** — pure arithmetic on `academyBase`, so stream *order* is untouched; generated values move, so multi-season baselines shift (single-season `touchStats` is unaffected — youth intake is offseason-only). Separately known and NOT fixed here: `trimRosterSurplus` is ovr-only, so **112 youth with POT ≥ 70 are released every offseason**; making it potential-aware is a deliberate follow-up, and it **must not land before this fix** or weak clubs retain OVR-2 players on the senior roster instead of flushing them.
- **Youth intake position mix** — `generateYouthIntake` draws each prospect's position weighted by `ROSTER_COMPOSITION` (not uniform), so the pipeline matches roster demand (CB/FB/CM 4 slots each get more prospects than DM/AM's 2). Single rng() draw via a precomputed CDF, so RNG-stream *count* is unchanged (only the mapped position moves) — but generation *values* shift, so this is not byte-identical to pre-weighting saves; `generateWorld` is untouched (it never runs youth intake). Note the low-slot positions (DM/AM, 2 each) still structurally leak their *good* surplus into free agency — a club can only house 2, so a prime 3rd gets trimmed — which is why the `/free-agents` list caps per-position on its unfiltered view (see Free agency).
- **Team Rating** — `core/teams/teamRating.ts` (`computeTeamRating`), XI (equal weight) + geometrically-decayed bench, not a flat roster mean. OVR + POT. Shown on Standings (current only) and user's Roster header.

**Free agency**
- **FA transfer hold** (`core/freeAgency.ts`, `faTransferLocked`) — `signFreeAgent` stamps `Player.faSignedSeason` = the season the signing takes effect (offseason signing → `season+1`, mid-season → `season`). While `league.season <= faSignedSeason` the user can't sell him: `inboundOfferCandidates` skips him, and Roster shows "Can't sell yet (just signed)" instead of List-for-Transfer. Kills the buy-a-free-agent-and-flip-him exploit. Optional field, absent on old saves (= unlocked); preserved through progression/`executeTransfer`.
- **Free moves are recorded as transfers** (`FREE_AGENT_TID` = **-1**, `core/transfers/negotiation.ts`) — a free-agent *arrival* is logged as a fee-0 `CompletedTransfer` whose `fromTid` is this sentinel (not a real tid). Load-bearing because club-by-season history is **reconstructed from `league.transfers` alone** (`teamForSeason` in `PlayerProfile.tsx`; also the OVR chart's club colors) — before this, ~19% of all rostered players displayed the *wrong current club*, since an unrecorded free arrival left them attributed to whatever club their last **paid** move landed at. Written by `signFreeAgentAction`, `signToAcademyAction` (academy = a free arrival at the club; promotion academy→senior needs none, same club) and `runAIFreeAgency` via `offseason.ts` step 4. Gotchas: **(a)** departures into free agency are deliberately *not* recorded (would double the log for no display gain — every surface asks "which club in season N", which a release doesn't change); the one lying case, sign-then-cut in the same offseason, is filtered at offseason step 6.47. **(b)** `teamForSeason` must never seed pre-history from the sentinel — a player can sit on a roster for years with no record at all, so seasons before his first record fall back to his present club. **(c)** AI free churn is ~1-2k signings/season, so it's kept out of aggregate feeds (News Feed, per-window transfer lists, Season Preview top transfers) — the user's own free signings still show. **(d)** Any UI rendering a raw from/to tid must go through `clubDisplayName` (`ui/format.ts`) or the sentinel renders as "Unknown"/"Team -1". **(e)** No shared-`rng` draw, so sim results stay bit-identical; no migration (old saves just keep their pre-fix history).
- **AI FA quality poaching** (`runAIFreeAgency`, second pass) — after filling positional shortfalls, each AI club (worst-first) poaches the single best remaining FA that upgrades a position it's already at target depth in (→ composition+1); `trimRosterSurplus` later keeps the best and releases the now-weakest, so the strongest FAs drain out of the pool before the user shops it. Contract length drawn from a **separate seeded stream** (not shared `rng`) → youth generation stays bit-identical.

**AI General Manager** (replaces rule-scripts with emergent evaluation; full brief in the user's "AI GM Philosophy" doc)
- **Evaluation core** — `core/ai/clubContext.ts` (`deriveLeagueContexts`: squad strength/age/depth + league-normalized **ambition**/**frugality** scalars, *derived from state, not stored*) and `evaluate.ts` (`valueToClub` layers positional-need/timeline/affordability on `trueTransferValue`; `perceivedValueToClub` adds scouting-noise scaled by frugality). Normalization is scoped **within each competition** — *except* `stature` (see below), which is deliberately world-wide.
- **Buy-side vs keep-side valuation (`ValuationSide`, 2026-08-08) — load-bearing, was the single worst realism bug.** A club must not price its own players with the buy-side formula: that formula asks *how much would he upgrade us*, so a club's own best player at a position scores **zero** (he *is* `posBestOvr` — he's measured against himself), the depth term reads *surplus* because he's one of the bodies, and affordability marks him down again for a purchase that isn't happening. Net effect: **the worse a club was, the more it valued a star**, so a superstar's own club was always his *lowest* valuer and he was permanently cheap + available. Measured on a real world: an 85-ovr player's own club (squad 75.0) valued him at **$132M** against a $350M market, while the five highest bidders were the *weakest* clubs alive (a squad-51.9 side valued him at **$538M**). `keepValueToClub` fixes it counterfactually — "how far would we fall back without him": incumbent = `posSecondBestOvr` (new `ClubContext` field) when he's the club's best, depth counted as `depth-1`, **no affordability**, and timeline takes `max(prime, youth)` so a win-now club can't write off its own 21-year-old. Used for every *reservation* price (`runAITransferMarket`, `inboundOffers`, both `loans.ts` sites). **Renewals deliberately stay buy-side** — `AI_RENEWAL_MARGIN` is calibrated against those numbers, and keep-side values re-sign essentially everyone and *starve free agency* (measured: `runAIFreeAgency` signed nobody at all). Revisit only with `AI_RENEWAL_MARGIN` retuned in the same change.
- **Player will (`core/transfers/playerWill.ts`, 2026-08-08)** — the missing *other half* of a transfer. Every valuation is a club's view; nothing represented whether the **player** wants the move, which is why stars poured downhill. Football has no salary cap to justify a star at a small club (basketball does — cap space genuinely sends stars to small markets), so this supplies the constraint. `ClubContext.stature` ([0,1], squad strength vs an **absolute** band blended with hype — the one normalization that is *not* per-competition, because "is this a step up" is a global question and the biggest club in a weak league is still small). `moveAppeal` scales a **buyer's** valuation by how much the player likes the destination, weighted by `statureSensitivity` (a ≤62-ovr squad player is indifferent; a ≥78 star weighs it fully); a big enough step down is a flat `refusesMove`. `settledMultiplier` scales a **reservation** up for a player who just arrived, decaying over `PLAYER_SETTLED_SEASONS` — `joinedSeasons` derives arrival from `league.transfers` (loans/loan-returns excluded), so **no persisted field and no migration**. **Pure functions, zero rng draws**, and both market gates sit **after** the jitter draw (same rule as the Division-2 guard) so RNG stream order is untouched. Applies to the **user identically** (`refusesMoveToClub` in `makeTransferOffer`/`acceptCounterOffer`/`recommendedTransfers`/world search's `notForSaleReason`) — exempting the user would just hand them the exploit.
- **AI↔AI market** (`core/ai/transferMarket.ts`) — a player's reservation is his value to his current club; he moves to whoever values him enough more to clear it and afford the fee. Guardrails: min-surplus, per-window buy/sell caps, depth floor, cash reserve. Runs once per window. **There is deliberately no availability screen — protection is by price, not veto (2026-08-11).** `AI_MARKET_AVAILABILITY` used to skip any player whose keep-side reservation exceeded his club-blind market value; those quantities aren't commensurable, and keep-side is *built* to exceed market for a club's own best player, so of 239 clubs the number whose best player could ever be offered was **zero**. That shut off the upward drain of talent that counteracts `growthDamping`, and the strength ladder inverted outright — England finished *below* Portugal over 20 seasons on shipped main. An irreplaceable player is now protected by a high reservation the buyer must clear, not by exclusion. **Any replacement prune must bound the best possible buyer valuation against the reservation; comparing to market value reintroduces the bug.** Cost of having no prune: one market run is ~52ms → ~357ms on the **240-club** world it was measured on (`scripts/marketTiming.ts`), in the worker. **It scales worse than linearly with world size, so re-measure after adding a country rather than reusing the number** (it was also originally mislabelled "320-club" here): the pre-filter was the only early-out ahead of the O(teams) buyer loop, so cost grows with candidates × clubs. **Measured on the 16-competition/320-club world: ~1611ms per run, 560 deals** — 4.5× the 240-club figure for a 1.33× club count. At two windows a season that is ~3.2s per season against ~0.1s when the filter existed, roughly **9% of a season-cycle's sim time** (~34s) versus well under 1% before. Still in the worker, so it does not block the main thread, but this is now the strongest argument for a *sound* replacement prune — which must bound the best possible buyer valuation against the reservation, never compare to market value. Full diagnosis: `docs/transfer-mobility.md`. **Need-buy path** (`AI_NEED_BUY_*`, `hasPositionalGap` in `evaluate.ts`): the normal `AI_MARKET_MIN_SURPLUS` gate only fires on *bargains*, which left cash-rich clubs banking money while a position went unfilled. When a buyer has a genuine positional gap there (understaffed vs `ROSTER_COMPOSITION`, or a weak startable hole this player upgrades), its required surplus margin drops to `AI_NEED_BUY_MIN_SURPLUS` (0 = pay a fair price, no discount) and it frees up part of its frugality-driven reserve (`AI_NEED_BUY_RESERVE_RELIEF`, never below `AI_MARKET_RESERVE_FRACTION_MIN` → no deficit). Elites stay unbuyable (priceless-star premium is in valuation, untouched); it only routes affordable, already-available squad players to clubs that need them (a move, not a creation → no inflation risk). **The need-buy path is not an exception — it is 92-93% of all executed deals, and that is load-bearing (measured 2026-08-12, `scripts/needBuyMarginProbe.ts`).** `hasPositionalGap`'s understaffed branch tests `posDepth < ROSTER_COMPOSITION`, a *stocking* target that sums to 25 against squads trimmed to 25, so a squad not distributed exactly to target is short somewhere and essentially every club always is. That reads as a loose predicate; it was tightened two ways and **both were rejected**. Depth (a hole = "cannot field the position", half the target — which is also `keepsDepthFloor`'s threshold) hit its target cleanly, 92%→34% with the ladder green on all four seeds, and put **2 of 4 seeds into deficit** (Belgium −£2.7M s16, Turkey −£1.9M s17) where main has none: Belgium lost a third of its *sales* but two thirds of its *income*, because a strong club buying a weak league's star qualifies via *understaffed* (it is strong everywhere, so the weak-starter branch never fires for it) and depth is quality-blind, so it cut the valuable upward sales along with the filler. A quality gate instead (a shortage counts only if the player addresses it) was principled and **inert**, 92.3%→91.5%, since a buyer only bids on players it already rates. **The generalisation, which outlives this predicate: the weak leagues run on transfer receipts** — Belgium's 20 clubs take ~£1.1bn in a *single window* against ~£800M of base income for the whole league across a season (`BASE_SEASON_BUDGET` × `COUNTRY_BUDGET_SCALE`) — so **anything that reduces market volume lands on the same tripwire**, including the sound buyer-loop prune wanted for performance, a need-to-sell term, and a floor on `AI_NEED_BUY_MIN_SURPLUS`. Two process notes: **deal count is the wrong yardstick, receipts into the poor leagues is the right one** (dropping a hundred £1M filler deals is harmless, dropping a few big upward sales is not, and counts can't tell them apart — the probe prints receipts by league for exactly this); and **the finance column fails first, not the ladder** — the change that bankrupted two seeds passed every ladder check, so watching only strength would have shipped it. Full diagnosis: `docs/transfer-mobility.md`.
- **Inbound offers for the user's players** (`core/transfers/inboundOffers.ts`) — symmetric negotiation (`respondToAsk`), persisted in `LeagueStore.inboundOffers`. `/incoming-offers`. **List for Transfer** (`StoredTeam.transferListed`) lowers a buyer's surplus bar.
- **World player search** (`searchWorldPlayers` in `core/transfers/recommendations.ts`, "Search all players" panel under Recommended Transfers on `/transfers`) — free-form name/filter search over *every* club's roster (no ovr-band/budget/variety cap), ranked by ovr, capped at `PLAYER_SEARCH_LIMIT` (60), empty with no constraint. Each row carries a `forSale` flag mirroring `makeTransferOffer`'s sale gates (loan/rollover-departure/protected-star/depth-floor) so the UI explains an unbuyable player instead of silently no-op'ing the offer; buyable rows reuse the same `NegotiationControls`/`makeOfferAction` as the recommended list. Pure UI+read layer — no new engine gates, so the difficulty levers (depth floor, protected stars, priceless-star pricing) hold unchanged.
- **Contract renewals** (`core/ai/renewals.ts`) — final-year AI players renewed if value ≥ salary × margin (offseason step 0). Sell-at-peak/replace-aging are emergent (no separate mechanic).
- **News Feed** (`/news`) — all league transfer activity + player accomplishments. Accomplishments (`core/newsEvents.ts`, hat-trick/standout/goal-milestones/position-change) detected at sim time into append-only `LeagueStore.newsEvents` (can't be derived retroactively). Timeline merge in `ui/newsFeedTimeline.ts`. **Removing an event type means migrating it out of existing saves** (the feed is append-only, so old rows survive and would render a blank label) — see the generational-talent removal under Extremism.
- **Power Rankings history** — snapshots captured every 5th matchday + finale into `LeagueStore.powerRankingHistory` (`core/teams/powerRanking.ts`).

**Finance**
- `budget` is a **cumulative running balance**, never reset to base — light spending compounds. Bounded by `budgetCap(tier, hype)` (`core/finance/budget.ts`): hype-scaled ceiling between `MAX_BUDGET_FLOOR` and `MAX_BUDGET`, ×`financeScale` per country/tier. Banking past the cap destroys the excess (never causes a deficit).
- Wages: cubic in ovr (`seasonSalaryForOvr`, `core/contracts.ts`), charged **up front** at season start (`chargeSeasonStart`); season-end `settleSeasonEnd` handles prize + hype − scouting only. Mid-season acquisitions charge full season salary at acquisition.
- **Value scale retuned to the game's own economy (2026-08-08).** `VALUATION_OVR_COEFF` 56_000→**32_000** and `VALUATION_ELITE_COEFF/EXPONENT` 11_000_000/2.5→**1_200_000/2.0**. The old curve was pinned to real Premier League *fees* while `BASE_SEASON_BUDGET` is $88M (a real club turns over several times that), so a "realistic" $120M fee cost ~1.4 seasons of a club's entire income vs ~0.2 for the real deal it copied — every transfer was proportionally ~8x the real market. Worse, the elite term **saturated**: at ovr 80 it alone was $352M, so *every* player ≥80 priced identically at the `MAX_TRANSFER_VALUE` clamp and (via `AI_MARKET_FEE_FLOOR_FRACTION` 0.5) every elite deal opened at $175M. Measured: **42 fees ≥$100M per season**, whose median subject was ovr 75 / age 22. New base+elite curve: 65≈$21M, 70≈$32M, 75≈$48M, 78≈$59M, 80≈$86M, 83≈$134M, 85≈$186M, 87≈$241M — a real gradient, clamp reserved for the freak. Also `AI_MARKET_AVAILABILITY` 1.05→**0.95** (above 1.0 a club shopped players it rated *above* market, the opposite of "surplus") — **that tightening was reverted by deleting the constant outright on 2026-08-11; it inverted the strength ladder. See the AI↔AI market entry above and `docs/transfer-mobility.md`.** **Gate for any future change here: `scripts/marketRealismAudit.ts`** (star churn, downward moves, ≥$100M count, club solvency, FA-pool size). Beware the coupled constants — lowering values makes renewals *less* likely (value vs `salary × AI_RENEWAL_MARGIN`) and shrinks loan/`AI_MARKET_MIN_VALUE` eligibility.
- **Capped values + "protected star" not-for-sale gate** — the load-bearing **difficulty lever** (money buys a good squad, not a great one). Two parts: (1) an accelerating elite premium above `VALUATION_ELITE_THRESHOLD` (76 ≈ the top of a league) in `trueTransferValue` makes the real difference-makers expensive, but every value/asking price is **clamped at `MAX_TRANSFER_VALUE` ($350M)** so quoted fees stay believable — no more billion-dollar tags. (2) The genuine best players are removed from the market entirely rather than priced into the stratosphere: `core/transfers/protectedStars.ts` `isProtectedStar`/`protectedStarPids` withhold any AI player who was *best-in-world last season* (`ovr ≥ PROTECTED_STAR_OVR` 80, **or** won POTY/Golden Boot/a Team-of-the-Season place) **and** whose club finished **top-`PROTECTED_STAR_TOP_FINISH` (4)** of a **tier-1** league last season. Wired into `makeTransferOffer`/`acceptCounterOffer` (user buys), `recommendedTransfers` (hidden from targets), and `runAITransferMarket` (AI↔AI, via a `protectedPids` set passed by the caller). The gate is **data-driven off a completed-season record**, not the live league, because the offseason summer market runs *before* the `seasonHistory` entry is appended — that caller (`offseason.ts`) builds the record from the freshly-computed `standings`/`awards`/`compsByTid`; regular-season/winter callers use `lastCompletedSeason(league)`. The **user's own club is never gated** (you always control your sales). Note a global player-quality nerf can *not* substitute for gating the market, because match composites z-normalize league-wide quality away (proven — it left title-win rates unchanged).
- **Finance page** (`/finance`) — pure display of budget/hype, scouting slider, settlement breakdown, wage bill, transfer history, league-wide table.

**Difficulty** (`DIFFICULTIES` in `constants.ts`, `LeagueStore.difficulty`, 2026-08-17)
- Four levels (easy/normal/hard/brutal) chosen on `/new-league`, **fixed for the save's lifetime**, migrated to `"normal"` for old saves. `normal`'s profile is every lever's identity value or the shipped constant, so an existing dynasty is provably unchanged (pinned by `difficulty.test.ts`).
- **Every lever is user-club-only, and that is a hard constraint rather than a convenience.** AI↔AI trading, the country strength ladder and the anti-inflation equilibrium are one tuned system. The specific trap: widening the protected-star gate *world-wide* on the hard levels is the obvious implementation and would cut AI↔AI deal volume, which lands straight on the documented tripwire (the weak leagues run on transfer receipts; the last change that reduced deal flow put 2 of 4 seeds into deficit with every strength check green). Because nothing reaches the AI, **no difficulty change needs a dynasty audit** — that property is worth preserving.
- Five levers and their seams: **money** — `financeScaleFor` (`finance/budget.ts`) is the *one* seam, wrapping `financeScale` and multiplying for `userTid` only; it must scale income **and** the savings ceiling, since `clampBudget` would otherwise destroy an easy level's bonus. **Academy** — an intake-time addend beside `academyFormModifiers` in `offseason.ts`, **never** written into `StoredTeam.academyBase` (promotion convergence would drag it back toward the competition centre and roster-import realignment would permute it onto another club). **Buy price** — `reservationPrice`'s new `priceScale`, whose single call site is `makeTransferOffer`, plus `scoutedValue` on the two buy-side display surfaces; both still clamp at the unscaled `MAX_TRANSFER_VALUE` so no level quotes a fantasy fee. **Market access** — `ProtectedStarBar` on `isProtectedStar`/`protectedStarPids`, defaulting to the shipped constants; only the four user-facing call sites pass `userProtectedStarBar(difficulty)`. **Fog** — a `fogScale` on `potentialFog` (half-width *and* clearing time), purely informational, no rng draw.
- **Opening budget scales the post-wage SURPLUS, every later season scales income.** Deliberately asymmetric: scaling the base allocation at creation starts a Brutal save at an expensive club already in the red before the user has made a decision, whereas a post-wage figure is positive by construction. From season 2 on `chargeSeasonStart` takes the scale normally and going broke becomes a consequence of how the club is run.
- **Going broke is reachable by choice, not by construction, and that's the calibration.** Measured (`scripts/difficultyProbe.ts` + the wage curve): a mid-table generated squad costs ~£18M/season against £88M base income, so nobody starts in trouble; but a 30-man squad averaging ovr 75 costs **£88.6M**, i.e. break-even on normal and a **~£18M/season deficit on hard** (£70.4M income), ~£36M on brutal. Beware measuring this in a headless audit — the unmanaged user club rots to academy stipends and understates its wage bill ~5×, which made the squeeze look far too weak on the first pass.
- Bankruptcy is survivable and already half-implemented by existing code: `makeTransferOffer` gates on budget so you simply can't buy, and `clampScoutingSpend`'s `Math.max(budget, 0)` switches scouting off, which widens the fog. Both are surfaced (Finance in-the-red alert, Dashboard warning); there is still **no debt mechanic** and open decision #2 is unchanged.
- **Difficulty diverges the rng stream** (it changes what the user can afford), so two levels on one seed are different worlds and cross-world counts are not comparable. `difficultyProbe.ts` therefore applies all four bars to a *single* simmed world; a probe that sims each level separately will report a moving AI-side count and look like a leak that isn't one.
- Copy gotcha: on hard levels a player can be unbuyable by the user while still moving between AI clubs, so the not-for-sale reason switches to **"Not available to you"** rather than claiming his club won't sell (`protectedStarReason` in `recommendations.ts`).

They're now separate params; the strength spread is still drawn and shuffled **once** and both bases derive from it, so rng consumption is unchanged and — since `competitionAcademyOffset` falls back to `strengthOffset` — leaving it unset reproduces the old behaviour exactly. It works: measured on `scripts/customWorldProbe.ts`, a league generated 1.87 OVR *below* its neighbour finished 1.44 *above* it after 3 seasons on academies alone, and it is safe to set because `academyBase` is fixed-at-generation by design (it's the anti-inflation anchor, so setting it picks an equilibrium rather than opening a ratchet). **The control was cut because a second 0-20 slider beside Strength made the player do arithmetic to work out which way their league was pointing** — the mechanic was fine, the affordance wasn't. If it comes back, make it a *direction* ("rising / steady / fading") and derive the offset, rather than a second absolute scale. The field, the accessor, the generation split and their tests all stay; `newLeagueEntry` simply leaves it unset.
  - **Continental slot counts are per league, which forced the Shield's offset to be derived.** `CupFormat.strongOffset`/`weakOffset` were constants duplicating the Cup's slot counts ("change one and you must change the other"). That breaks the moment a league sets its own count, so `cupOffsetForCompetition` now sums the slots of every competition above it in `CONTINENTAL_ORDER` — fields butt up exactly, can't overlap or gap, and inserting a third competition shifts everything below it automatically.
  - **`isValidCupFieldSize`/`largestValidCupField` (`constants.ts`) — a real crash this exposed.** The league-phase draw needs the field to split into 2 pots that are *each even* (intra-pot rounds are perfect matchings within a pot) and big enough for `CUP_LEAGUE_PHASE_GAMES/POTS`, plus ≥ `CUP_LP_DIRECT_QF + CUP_LP_PLAYOFF_TEAMS`. `drawLeaguePhase`'s own guard **omitted the even-pot condition**, and `cupPlan` only checked the minimum — unreachable while every field was 24/16, but a custom world producing 23 qualifiers threw inside `simOffseason`. `cupPlan` now trims to the largest buildable size and `qualifyCupTeams` slices **after seeding** (drops the world's weakest qualifiers, not an arbitrary league's). Shipped world still lands on 24/16 exactly, so nothing there changed.
  - **Per-league roster import (`retargetRosterFile`, `leagueRosterFiles`).** An added league's divisions did not exist when any roster file was authored, so nothing in a file can name them and `resolveRosterSlots` would skip every competition as unrecognised. `retargetRosterFile` rewrites a file's `match` values onto one league's division names **positionally** (first competition → tier 1), the same rule clubs already follow onto slots; `WorldEntry.rosterSources` holds the files and `leagueRosterFiles` retargets them at build time, **not** at pick time, because the division names follow the country name and the player can rename the league after loading. The result is folded through `combineRosterFiles` → `applyRosterFileToNewLeague` like any other import, so slot resolution, the picker preview and crest suppression are shared (`activeRoster = roster ?? leagueRoster` in `NewLeague`). Retargeting is non-mutating and drops (with a warning) any competition past the league's division count. The world-wide `?roster=1` flow is unchanged and stays mutually exclusive with the world editor.
  - **Slider anchors are measured, not extrapolated (`scripts/strengthAnchorProbe.ts`).** Generates every strength rung 0-20 in one world so they're directly comparable, and reports division mean OVR, best/worst club rating and best player per rung. Confirms ~0.94 OVR per point and gives the cross-league anchors the Manual and the settings guide quote (e.g. strength 9 → best club ≈ 67, about a mid-table big-four side; strength 20 → best club 54, below *every* big-four club).
  - **Division count (1 or 2) and size (even, `MIN_DIVISION_TEAMS` 8 to `MAX_DIVISION_TEAMS` 20) are per league (2026-08-22).** `Competition.teamCount` + `competitionTeamCount`; `LeagueSpec.divisions`/`d1Teams`/`d2Teams`. **`Tier1Pair.d2` is now nullable** and `partnerOrNull` is the non-throwing lookup — a one-division country has no tier 2, so `computeCountrySwaps` returns no swap for it and `generateWorld` stops after its tier-1 block. `worldTeamSlots`/`countryClubRanges` **no longer take team counts** (they derive them per competition), which is why the club-identity lookup had to be country-anchored first: a one-division country shifts every later country's tids by a whole division.
    - **A smaller division SPREADS across the fixed 38-matchday grid rather than finishing early** (`spreadOverSeason` in `leagueState.ts`): round r of R maps to `round(r * SEASON_MATCHDAYS / R)`. At R=38 that is the identity, so **the shipped world is untouched** (pinned by the `touchStats` hash and a test asserting matchdays 1..38 exactly). Spreading is what keeps the rest of the calendar meaningful for a short season — the winter window still opens mid-season, deadline day still has games left, the run-in still lines up with the continental finals. `MAX_DIVISION_TEAMS` is 20 because 2(n-1) ≤ 38 and `matchdayToMonth` **throws** outside the grid; going past it means moving the cup matchday tables too.
    - **Blank matchdays broke the injury/ban tick, exactly as CLAUDE.md warned they would.** Both count in MATCHES and both decremented once per matchday for *everyone*, which is exact only while every club plays every matchday. `applyInjuries`/`applySuspensions` now take a `played(pid)` predicate; `simThrough` builds it as **"who did NOT play"** so free agents (on no roster, no fixtures to attach to) keep ticking on the global clock as before, and the shipped world's set is empty. Both default to "everyone played", so no other caller changed.
    - `updateHype` takes the club's own division size — finishing 8th of 8 has to score like bottom, not like 8th of 20. Defaults to `NUM_TEAMS`.
  - **Club identities are anchored to a country, never to a tid.** `CLUBS` is indexed by tid, so switching a country off (or adding one ahead of another) shifts every later country's tids and a tid lookup hands Spain's clubs England's names. `clubIdentitiesFor(country, count)` (shipped block, else `generateClubIdentities` from `teams/clubNames.ts`) is shared by `assignIdentities` **and** the new-league picker — they must derive names the same way or the save renames every club on open. The generator is deterministic from `(country, count)` on its **own** seeded stream, which is what lets the picker preview an added league before a world exists.
- `worldCompetitions()` = **16 competitions / 320 clubs**: England, Spain, Italy, Germany (equal siblings) + **France, Portugal, Belgium & Turkey (deliberately weaker + poorer)** via `COUNTRY_STRENGTH_OFFSET`/`COUNTRY_BUDGET_SCALE` (`constants.ts`). Weakness is invisible in a country's own matches (per-competition z-norm) — it bites only in finance (selling leagues) and the Cup (shared baseline).
- **Strength ladder is compressed, not literal (2026-08-08).** Offsets France 5 / Portugal 10 / Belgium 11 / Turkey 12 follow the real UEFA five-year coefficient *ordering*; the real gaps below France are only a few coefficient points, so mapping them literally would put Belgium ~17 and Turkey ~30 and generate unplayable squads. Each offset point ≈ **0.94 OVR** off a league's starters (measured). **`COUNTRY_BUDGET_SCALE` MUST stay monotonic with `COUNTRY_STRENGTH_OFFSET`** (France .7 > Portugal .5 > Belgium .45 > Turkey .4) — **a richer league climbs the ladder over a dynasty, so a weaker-but-richer league overtakes a stronger-but-poorer one.** Measured, not theoretical: Belgium/Turkey generate within 0.9 OVR of each other (a near-matched pair that isolates budget from everything else), and at Belgium .35 / Turkey .5 the ladder **inverted by 2.23 OVR over 20 seasons** — Turkey, generated weakest, finished *above* Belgium. Real squad values do invert here (Belgian Pro League €0.98B < Süper Lig €1.27B while Belgium outranks Turkey on the pitch); that is deliberately **not** modelled — the engine can't hold "weak but rich", and the ladder is load-bearing while the flavour isn't. **Gotcha when measuring this:** comparing leagues with very different starting OVR (England vs Portugal) hides the budget signal entirely behind progression's mean-reversion — an earlier attribution run did exactly that and wrongly concluded money was a weak lever. Compare near-equal leagues.
- **Weak-league solvency holds, and an AI wage-affordability gate was built for it and then removed as provably inert (2026-08-11).** History worth keeping, because the same fix will look attractive again. A deficit was reported, a `staysSolvent` gate was added to every AI buy path (transfer/loan/free agency) to project the next season-start charge with the incoming salary on the books, and it was measured "near-neutral, deficits 0 → 0". **All three of those measurements were taken on a market that could not sell a club's best player** (the `AI_MARKET_AVAILABILITY` bug — see the AI↔AI market entry). Once that was fixed, re-measurement showed: (a) *with* the gate, on the pre-fix market, **4 AI clubs still went negative on seed 1** (worst −£5.96M, first at **season 12**) — the gate never prevented the thing it was for, and the "0 → 0" claim survived only because it had been re-validated with a **5-season** spot check after the fee rescale; (b) on the fixed market, deleting the gate changes **nothing that matters**: 0 deficits across 4 seeds either way, and on 3 of those 4 seeds the entire 20-season dynasty comes out **byte-identical**. Identical output is a *proof* of zero firings on those seeds, not a coincidence — RNG stream order is load-bearing and a declined signing skips a contract-length draw, so one firing moves every downstream number. **It is therefore inconsequential rather than literally inert, and the distinction was nearly missed:** seed 3 *does* differ (France→Portugal +0.24 → +0.31), i.e. the gate fired there at least once and still prevented no deficit. An earlier version of this entry generalised "byte-identical" from the two seeds it had been measured on into a claim that the gate never fires at all; a fourth seed contradicted it. **Measure the seed you are about to generalise from.** **The real mechanism was never wages:** with the market shut, a club could not sell its best (and highest-paid) player, so wage bills ratcheted with no relief valve — which surfaced as insolvency in the finance column and a collapsing ladder in the ratings column, one cause with two symptoms. **Before rebuilding this gate, first check whether the market can still shed wages.**
  - **Margins, measured.** Opening budgets have real headroom: poorest club £15.8M (Belgium, seed 1) / £12.6M (Turkey, seed 2), via `scripts/genBudgetProbe.ts`. The thin point is *after season 1 is played* — £0.01M / £0.06M (Turkey) — driven by in-season spending, and it is the AI market's cash reserve that holds it above zero.
  - **The structural asymmetry is real even without a gate**: `financeScale` multiplies *income* (`BASE_SEASON_BUDGET`, prize payouts, hype revenue) while `seasonSalaryForOvr` is country-independent. Weak leagues stay solvent because `COUNTRY_STRENGTH_OFFSET` hands them cheaper squads *and* the market keeps draining their expensive players upward — nothing links those knobs, so re-check solvency after any change to either.
  - **Two audit methodology bugs found on the way, both fixed and both worth remembering:** (a) `weakLeaguesAudit.ts` sampled the budget only at generation and at the end while reporting "min AI budget over dynasty", so a mid-dynasty dip read as solvent — it now samples both points every season; (b) sampling *only* after `simOffseason` misses the true minimum, which lands **post-season** (after the winter window, before season-end settlement), not post-offseason.
- **Adjacent weak rungs are NOT separately resolvable across a dynasty.** Portugal/Belgium/Turkey are one offset point apart (≈0.9 OVR) and ~40% of that erodes, so they end within a few tenths (measured seed 1: 49.6 / 49.6 / 49.3) and their mutual order coin-flips on seed noise. The audit therefore gates *ordering* plus block-level spreads, **not** per-rung magnitudes — asserting the latter would be asserting precision the design doesn't have. If rungs ever need to be individually resolvable, widen to 2-point offset steps rather than tightening the audit.
  - **Order is gated at two scales, and the split is load-bearing (2026-08-11).** The audit used to state all of the above and then gate adjacent-rung order *per seed* at 0.5 — a tolerance **below the noise it had just described**, so it contradicted its own header and failed on seed choice alone. Measured 4 seeds × 20 seasons: Portugal→Belgium `+0.24 −0.44 +1.51 +1.75` (mean +0.77), Belgium→Turkey `−1.33 +0.48 −0.45 +0.06` (mean −0.31) — straddling zero with ~±1 OVR of spread. So a single seed now only catches a **gross** inversion (`SEED_INVERSION_TOLERANCE` 2.0) while a **systematic** one is caught on the **mean across seeds** (`MEAN_INVERSION_TOLERANCE` 1.0), where noise averages down; both real failures (the 2.23 budget inversion, the 2.5 market inversion) are present on every seed and so fail both gates. `SEEDS` therefore defaults to **four**, and the script says so when run with fewer than three, because a mean of two draws is not worth gating on. **Don't "fix" a red adjacent rung by tightening the per-seed tolerance — that is the bug this replaced.**
  - **The block spreads got the same split (2026-08-13), after the per-seed `MIN_END_SPREAD` floor false-failed a healthy main.** France→Turkey measured 0.97 against a 1.0 per-seed floor while its cross-seed mean sat at 2.91. Measured 8 seeds × 20 seasons per build, per-seed noise on that spread is ~±1.4 OVR — a healthy pre-#217 build lands **−1.11** on seed 7, an outright end inversion, on a build whose seeds 1-4 all cleared the floor. So the per-seed check now only resolves a **gross** end inversion (reusing `SEED_INVERSION_TOLERANCE`) while the magnitude is gated on the mean (`MIN_END_SPREAD` 1.0); BIG4→weakest gets the same treatment (per-seed `MIN_SPREAD` 3.0 for gross collapse, new **`MEAN_MIN_SPREAD` 4.0** against healthy means of 5.9-6.2). **A 4-SEED RANGE IS NOT A VARIANCE ESTIMATE** — seeds 1-4 alone read as "#217 doubled the spread" (range 1.67 → 3.76) and seeds 5-8 alone read the opposite; on all 8, post-#217 is *tighter* (sd 1.22 vs 1.47) and stronger (mean 2.81 vs 2.05). Before attributing a variance change to a PR, run fresh seeds on **both** builds; the first comparison measured its own sample and its conclusion was withdrawn.
  - **The audit could silently sim one season fewer than it reported** (fixed 2026-08-13): `simThrough` halts before the user's cup final and `simOffseason` **silently returns the league unchanged on any phase but `"offseason"`**, so a dynasty whose unmanaged user club reached a final just stopped advancing (1 seed of 8). The season loop now resumes `simThrough` until the phase actually flips. Generalizes past this script: **any headless harness that pairs `simThrough` with `simOffseason` must check the phase moved**, since neither call throws.
- **Country strength gaps erode ~43% over a 20-season dynasty, and it's `growthDamping`, not the market (2026-08-08).** Measured by attributing drift to its only two sources (ovr changes *only* in progression, so retained players' mean change is pure progression and the remainder is pure churn): progression gave England +4.06 vs Portugal +7.53 — a **3.47 OVR relative lift for the weaker league** — against churn's 0.55. Cause: `growthDamping` throttles positive growth above a **global, absolute** `GROWTH_DAMPING_START` (65), so a league sitting under that line grows undamped while the big four are throttled. **Do not "fix" this by making the threshold league-relative** — that hands every weak league its own elites, which is the inflation the equilibrium exists to prevent; `GROWTH_DAMPING_END`/`FLOOR` were swept against a 30-season × 3-seed audit to land D1's 80+ population at 8-16 and re-verified over 100 seasons. `scripts/weakLeaguesAudit.ts` now **asserts a minimum surviving gap per rung** (and exits non-zero) rather than mere rank order — the old ordering-only check passed cleanly while the England→Portugal gap fell 9.6 → 5.5.
- `generateWorld()` — one rng pass; England block is byte-identical to the old England-only generation, and each country is generated in table order so appending one never perturbs an existing country's players (verified: adding Belgium/Turkey left all six prior leagues' generated OVR identical). `createLeagueState` uses it for all new saves; old saves stay at whatever country set they were created with (never re-run generation). `CLUBS` = 320 fictional identities (no real clubs — trademark caution). New-save UI has a country picker (`NewLeague.tsx`); Customize Teams editor is competition-scoped.
- **Per-league nationality tables must exist for every home country** (`LEAGUE_NATIONALITY_WEIGHTS`) — a missing country silently falls back to *England's* table. Source percentages routinely over-sum (the supplied Belgian list totalled 116.5%, the Turkish 130.7%); since the engine normalizes to the table total, feeding them raw understates the domestic share badly (Turkey would land 36.7% domestic instead of 48%). **Scale the foreign block so the domestic share lands on its stated value.** New nationalities named only by a new league's table go in **`UNLISTED_NATIONALITIES`**, never `OTHER_NATIONS` — `TAIL_BASE` is built from `NATIONALITIES` + `OTHER_NATIONS` only, so the latter would re-weight the "Rest of the World" tail draw for every league in every existing save (Belgium needed none; Turkey added Bosnia-Herzegovina/Gambia/Albania).
- **Per-league nationalities** — `LEAGUE_NATIONALITY_WEIGHTS` (`core/players/nationalities.ts`), real top-flight breakdowns; drawn on each player's isolated identity sub-stream (RNG-safe). Youth intake is country-aware.

**Promotion/relegation & the second division**
- New leagues generate a full tier-2 division per country; an N-up/N-down straight swap each offseason (`core/promotion.ts`, `computeCountrySwaps`/`applyCompetitionSwaps`, per-country). A swapped club's `academyBase` converges gradually (`stepAcademyBaseConvergence`); finance scale switches immediately.
- **N is per COUNTRY, not per save (`Competition.promotionSpots`, 2026-08-25)**, set on a league the player *adds* in World setup and resolved through `competitionPromotionSpots`; absent → `PROMOTION_RELEGATION_COUNT` (3), which is what every shipped country plays and what every existing save keeps. **Optional field on `Competition`, so there is no `LeagueStore` field and no migration** — the same fallback pattern as `strengthOffset`/`teamCount`, and the reason it is modelled this way: World setup only exposes per-league knobs for *added* leagues, so a world-wide setting would have been the wrong shape for the one place it can be edited (the first cut of this shipped as a save-wide picker and was reverted, user call). Written onto **both** divisions of a country by `buildCompetitions` (built from one spec together, so they can't drift). Two gotchas: **(a) 0 is a legitimate value and `slice(-0)` is `slice(0)`**, i.e. the *whole* table, so a closed pyramid would relegate every club in the division — `computeCountrySwaps` returns early at `n <= 0` rather than trusting the slice, and the accessor maps non-finite values to 0 for the same reason; **(b)** the accessor clamps to both divisions' `teamCount` and the swap clamps again to the actual table lengths, since a division can be as small as `MIN_DIVISION_TEAMS` while the picker offers up to `MAX_PROMOTION_SPOTS` (6). Nothing else in the sim reads it — the swap is the whole mechanic — so no audit or equilibrium is involved, but a big count churns tier 1 harder and leaves `enforceDivision2Ceiling` more relegated squads to sweep.
- **`enforceDivision2Ceiling`** (`core/ai/divisionCeiling.ts`) — the load-bearing anti-drift mechanic. Every offseason, any AI-controlled tier-2 player ≥ `DIVISION_2_REFUSAL_OVR_THRESHOLD` (70) is *deterministically* reassigned to a needy tier-1 club **in his own country** (zero fee, releases the receiver's weakest if capped). Runs twice (after promotion/relegation, and after the summer market). **Its workload dropped sharply on 2026-08-08** (61→18 sweep moves in the `offseason.test.ts` fixture) because the market no longer sells good players into tier 2 — worth knowing because the sweep's collateral (releasing a capped receiver's weakest man) was the *only* source of free agents in the very first offseason, so that test now plays a second season to reach steady state. This holds "D2 strongest ≤ D1 average" flat across 100-season dynasties — probabilistic approaches did not (relegation doesn't route through any market decision). `wouldRefuseExtension` (`core/ai/breakoutRefusal.ts`, now a flat ovr≥threshold check) is kept for **user-facing** purposes only (Roster "Wants a move to Division 1" badge/Extend-block; surfacing rival stars as buyable). The user's own club is never swept.
- Market/loan **prevention guards**: a tier-2 club never buys/bids-on/is-loaned an over-threshold player (guards placed *after* jitter draws, per RNG-order), so the game stops manufacturing illegal D2 residents and the sweep only cleans up structural cases (relegated squads, homegrown breakouts).

**Continental Cup** (`core/cup/`) — **Swiss league phase + knockout** (all new cups)
- **20-club field**, qualified by league position (not OVR): strong (big-four) leagues send top 4, weak (France/Portugal) leagues send top 2 (`CUP_STRONG/WEAK_LEAGUE_SLOTS`). **Skips season 1** (no prior table → `cup===null`). Cross-cut by a **shared normalization baseline** (`simThrough`'s `cupMatchData` now pools the whole 20-club field) so weak clubs read as genuinely weaker. `LeagueStore.cup`/`cupHistory`, `/cup`.
- **League phase** (`core/cup/leaguePhase.ts`) — one combined table, each club plays `CUP_LEAGUE_PHASE_GAMES` (6) games. The draw (`drawLeaguePhase`) splits the seeded field into `CUP_LEAGUE_PHASE_POTS` (2) strength pots and builds the schedule **directly as 6 edge-disjoint perfect matchings** (guarantees once-per-round; a build-then-color graph may not be 1-factorable), giving each club 3 opponents from each pot, no same-league pairings, an Eulerian home/away split. Runs on its own seeded rng per round (`LEAGUE_PHASE_STREAM` offset) so league scorelines stay bit-identical. Table tiebreak: pts→GD→GF→wins→seed (no head-to-head, Swiss-unreliable).
- **Split** (`splitLeaguePhase`): top `CUP_LP_DIRECT_QF` (4) → straight to QF; next `CUP_LP_PLAYOFF_TEAMS` (8, ranks 5–12) → single-leg **playoff** (5v12…) for the last 4 QF places; rest (13–20) eliminated. `seedKnockoutFromLeaguePhase` seeds the `CUP_KO_SIZE` (8) bracket when the LP completes.
- **Knockout** is format-aware (`isSwissCup`/`koRoundsOf`/`koRoundMatchdays`/`koLegMatchdays`/`koPrizeByRound`/`koFinalRound`): Swiss = QF→SF→Final (3 rounds). **QF/SF are two-legged, home-and-away, decided on aggregate** (`CupState.twoLegged`, true for all newly-built cups; final and playoff always single-leg). Level after regulation (90' single-leg, or aggregate after both legs) → extra time → shootout; LP games can draw. **The two legs are played on separate matchdays** (`CUP_KO_LEG_MATCHDAYS` = `[[29,31],[33,35],[37]]`: QF legs 29/31, SF 33/35, Final 37). Flow (`playKnockoutLeg`, dispatched by `dueCupLeg` → `{round, leg, twoLeg}`): the first-leg matchday plays all first legs (`playFirstLeg`, plain 90') and holds them in `CupState.koLegs` (no prizes, no bracket advance); the second-leg matchday resolves each held tie on aggregate (`resolveTwoLeggedTie` plays leg 2 with the host swapped, sums scorelines, ET/shootout if level), appends the finished `CupTie`, clears `koLegs`. `mergeLines` folds both legs' box scores into one so cup stats/UI see a single tie line; `CupTie.legs` carries the two 90' scorelines for display. Safe to spread across matchdays because cup matches don't carry fatigue/injuries between each other (own per-matchday composites); the home/away swap + doubled sample is what reduces cup-vs-domestic variance (single-leg knockouts between good teams are near coin-flips — measured, stronger club advance rate ~64%→70% at a strong-favorite edge). Each leg runs on its own seeded stream (`hashInts(lid,season,round,30,leg)`), so the league match stream is untouched. **`simThrough` halts before the user's final** (Dashboard warns; the single-leg final's matchday is unchanged at 37). Prizes: participation (LP) + playoff-win + per-KO-round (prize-only, credited when the tie finalizes). Cup stats live on each tie's `BoxScore` (LP matches carry their own `boxScore`), separate from `SeasonStats`; Player Profile Cup tab. The user's Schedule page lists their cup fixtures (LP/playoff/each KO leg) alongside league games.
- **Legacy cups** (pre-Swiss saves, `leaguePhase===null`): old 16-team straight bracket + `CupPlayIn` kept alive only so an in-progress old cup finishes; `migrate.ts` backfills `leaguePhase`/`playoff` to null and `twoLegged` to false (so any cup already in progress finishes single-leg; the next built cup is two-legged). New cups (built each offseason via `buildCupState`) are always Swiss + two-legged. Matchday layout — two-legged Swiss: LP `[3,7,11,15,19,23]`, playoff `27`, KO legs `[[29,31],[33,35],[37]]`; single-leg Swiss (old in-progress saves): KO `[31,34,37]`; legacy bracket: `[8,16,26,34]`.

**Continental Shield** (2026-08-19) — the second continental competition, the Europa League to the Cup's Champions League. **Structurally the Cup with different numbers**: everything that differs lives in `CUP_FORMATS` (`constants.ts`), keyed by `CupState.competition` (`"continental" | "shield"`) and read through `cupFormat(cup)`. State is `LeagueStore.shield`/`shieldHistory`, built and archived beside the Cup in `simOffseason`, advanced by the same `advanceCompetition` path in `simThrough`. Page is `/shield` — the *same* `Cup` component with a `competition` prop.
- **Field: strong leagues' 5th–6th, weak leagues' 3rd–4th = 16 clubs.** The `rankOffset` is **per league strength** (`strongOffset`/`weakOffset`), because the Cup takes four places from a strong league and two from a weak one, and the Shield must start where the Cup stops *in that league*. That is the whole disjointness guarantee, and it is what makes the rest cheap.
- **Both competitions share the Cup's matchdays** (LP 3/7/11/15/19/23, playoff 27, KO legs 29/31, 33/35, 37) — sound *only* because the fields are disjoint, and it's what the real midweek calendar does. No calendar work, and no fatigue interaction (cup matches already build their own per-matchday composites).
- **A 16-club field needed no change to `leaguePhase.ts`**: two pots of 8 against 3 games per pot ✓, and `splitLeaguePhase` lands exactly (4 direct QF / 8 playoff / 4 out).
- **Every cup rng stream is salted per competition** (`CupFormat.streamTag`, continental **30** = the literal it shipped with, shield 70; plus a separate `drawSeed`). Two cups in the same season on the same matchdays would otherwise draw *identical* streams round for round. Any third competition must take its own tag.
- **Each competition pools its own normalization baseline.** Pooling the two fields together would measure Shield clubs against Cup clubs, which is the comparison neither makes.
- **Prizes ≈ 40% of the Cup's** (`SHIELD_PRIZE_*`): champion ~£19.5M vs the Cup's ~£48M. Deliberately clear of the Cup's tiers so finishing 5th and winning the Shield can't out-earn finishing 4th and going out of the Cup's league phase.
- **Held as its own `LeagueStore` field, not a list of cups** — `cup` has ~30 readers across sim and UI and a list turns every one into a lookup. Revisit only if a third competition arrives.
- **Deliberately NOT wired into the worldwide awards.** `worldAwards.ts` reads `ctx.cup` only, so Shield matches score zero there (exactly what already happens to every non-Cup player; their league seasons still count in full). The cup component is delicately balanced — `WORLD_AWARD_CUP_MULTIPLIER` is 1.0 for measured reasons and the team bonuses trade directly against winner's world-ovr rank — so adding an unmeasured second competition is the move those comments warn against. Needs a `scripts/worldAwardsAudit.ts` run before it goes in.
- It *is* wired into club history, the Frivolities trophy cabinet and both GOAT boards (`GOAT_SHIELD_TITLE_WEIGHT` 8 vs the Cup's 25; `GOAT_TEAM_SHIELD_TITLE_WEIGHT` 40 vs 150), a profile honour pill via `playerHonors.ts`'s `HonorCups.shieldHistory`, and `freeAgentCull` scrubs its box-score lines like the Cup's.
- **Merged with domestic cups (#244) on 2026-08-20; the two were built in parallel and touch the same dozen integration points.** They compose cleanly, and the two facts that make that true are worth keeping: the domestic tie stream is `0x0d0d` against the Shield's tag 70 (so no stream collides), and `DOMESTIC_CUP_MATCHDAYS` `[5,9,13,21,26,36]` is disjoint from the continental calendar (so a club can hold all three at once and never double-book). A club's trophy total now counts league + Cup + Shield + domestic + tier 2; **a treble is deliberately league + Cup + domestic and does NOT include the Shield** — the Shield is what you win instead of the Cup, so a "treble" containing it would be the wrong shape.
- Old saves backfill `shield: null` / `shieldHistory: []` and pick a Shield up at their next offseason (qualification needs a finished table), exactly as pre-cup saves did for the Cup. `scripts/shieldProbe.ts` verifies the whole thing end to end on a simmed world (field sizes, zero overlap, which places each drew from, distinct champions and scorelines).
- **Prize money is the Shield's ONLY channel into the world, and that was proved rather than argued.** Set every `SHIELD_PRIZE_*` to 0 and a 4-season dynasty comes out **bit-identical to `origin/main`** (same per-country mean OVR to 0.1, same rung gaps to 0.01, same min AI budget). So the Shield adds no rng-stream contamination, no fatigue, no availability effect — it plays its matches on salted streams and touches the league solely by crediting budgets. **Re-run that check after any change here**; it is cheap (two 2-minute runs) and it is the fastest way to catch a competition accidentally reaching into the league stream.
- **The ladder was audited against `origin/main` and shows no systematic effect** (`scripts/weakLeaguesAudit.ts`, 10 seasons × 4 seeds, the identical script run on both branches). Solvency holds on **8/8 runs**. The rung that looks alarming is Belgium→Turkey, and it is the documented coin-flip pair: shield `−2.04 / +0.51 / +0.12 / +2.04` against main `+0.51 / −1.07 / −0.66 / −0.10`, i.e. the **sign flips by seed on both branches** and the Shield's cross-seed mean (**+0.16**) is *better* than main's (**−0.33**). Block spreads likewise: BIG4→Turkey mean **5.10 vs 4.86**, BIG4→France **2.71 vs 2.10**, France→Turkey **2.39 vs 2.76** (all well clear of their gates). **Seed 1 alone reads as a gross inversion on the Shield branch and is noise** — the exact trap the audit's two-scale design (per-seed catches gross, mean-across-seeds catches systematic) exists to avoid, and a reminder that a 4-seed range is not a variance estimate. Caveat worth keeping: this is **10 seasons, not the documented 20**, so it is evidence of no *large* effect rather than a full dynasty clearance; `SEASONS=20 SEEDS=1,2,3,4` is the real gate if the prizes are ever raised.

**Domestic cups** (`core/domesticCup/`) — one open-draw knockout per country, both tiers, so a club can win the treble
- **One cup per country, contested by all 40 clubs** (tier 1 + tier 2), stored as `LeagueStore.domesticCups` (this season, one per country) and `domesticCupHistory` (archived at offseason rollover). Unlike the Continental Cup **nothing qualifies**, so cups run from **season 1** and `createLeagueState` builds them; the offseason archives the finished ones and builds next season's off the same `tablesByCompId` the Continental Cup uses. Reuses `CupTie` and `resolveCupTie` outright — a domestic tie and a European one are resolved by identical code.
- **Open draw, redrawn every round — so only the drawn rounds exist.** `DomesticCupState.rounds` grows one entry at a time: `advanceDomesticCup` records the played round and draws the next from `[...byes, ...winners]` (`drawPairings`, a Fisher-Yates shuffle, home = whoever comes out first). There is deliberately no bracket to render in advance, which is what makes it a domestic cup. Draw stream is `hashInts(season, compId, round, DRAW_STREAM)` — **no lid**, so a cup drawn at league creation (lid still 0) and one drawn in the offseason use the same rule; ties play on `hashInts(lid, season, compId, round, DOMESTIC_TIE_STREAM)`. Never the shared `rng`, so **league scorelines are untouched** (`touchStats` hash unchanged — that test runs `simSeason`, which has no cups at all).
- **The field isn't a power of two, and `prelimTieCount` is where that's handled.** 40 clubs → `totalRoundsFor` 6 and 8 preliminary ties: the **worst-ranked 16** play, the other 24 get byes, 32 remain. Ranking is `(tier played in LAST season, finishing position)`, so a relegated club outranks everyone already in tier 2 and a promoted one sits atop the tier-2 block — the only thing this ordering decides is who enters early. No tables at all (season 1, fresh import) → tid order, which is the tier-1 block then the tier-2 block. **An exact power of two must return 0 prelim ties** or a full opening round gets labelled "preliminary" (caught by a test).
- **Round identity is distance from the final, never the round index** — `domesticRoundName` and `domesticPrizeForRound` both key off `roundsFromFinal`, and `DOMESTIC_CUP_PRIZE_BY_ROUNDS_FROM_FINAL` is indexed `[0] = lifting it`. Same reason `cupRoundsFromFinal` exists for the Continental Cup: a cup with a preliminary round and one without must pay the same for a semi-final.
- **Composites pool the WHOLE country (both divisions), and this is load-bearing** — the identical lesson as `cupMatchData`. Composites z-normalize within a competition, so a tier-2 club measured against its own division reads as an average side and would meet a top-flight club as an equal. `simThrough` builds one `leagueMatchData` over all 40 clubs per cup matchday. Measured on a simmed season: **9 of 64 quarter-finalists were tier-2**, and all 8 champions were tier-1 — upsets happen without being cheap.
- **`DOMESTIC_CUP_MATCHDAYS` = [5, 9, 13, 21, 26, 36]**, every one clear of `CUP_LEAGUE_PHASE_MATCHDAYS`/`CUP_PLAYOFF_MATCHDAY`/`CUP_KO_LEG_MATCHDAYS` (a test asserts this), of deadline day, and of the finale. A smaller field takes the **last** n, so the final never moves. `simThrough` also **halts before the user's domestic final** (matchday 36), same as the Continental final on 37.
- **The cup pays NOTHING, and that is a measured decision — `DOMESTIC_CUP_PRIZE_*` are all 0.** It shipped with real prizes first (12M down to 0.25M per round, runner-up 3M, each ×`financeScaleFor` so a weak league could not out-earn a strong one). `scripts/weakLeaguesAudit.ts`, 4 seeds × 20 seasons, **against the same script run on the merge base**: the **ladder held** everywhere (per seed and on the 4-seed mean, so the financeScale scaling did its job) but **2 of 4 seeds went into deficit** — Belgium −£0.5M s20, Turkey −£1.4M s19 — where the baseline is solvent on all four. That is precisely the result that got the need-buy tightening rejected, and the documented failure shape: **the finance column fails first, not the ladder.** The audit cannot separate the two candidate mechanisms (a one-off prize converted into a permanent wage liability — both deficits land late — versus plain stream shift, since crediting a prize before the winter window moves every downstream AI market decision and the weak leagues already sit within ~£0.01M of zero at their thinnest). **At zero, `creditPrizes` is never reached, no budget is touched, and a dynasty is bit-identical to one with no domestic cups at all — verified, seeds 1 and 3 reproduce the baseline's 20-season numbers exactly, to every decimal.** That is what makes shipping the competition provably safe. Re-enabling is the two constants plus a tuning pass measured the same way; `domesticCupIntegration.test.ts` fails if you flip them without it.
- **Archived like the Continental Cup** (`archiveDomesticCup` folds every round's box scores into `statLines` and drops them) — 39 ties per country per season × 8 countries is a lot of box scores to keep forever, and save size is what freezes the game. `cupStats.ts` was refactored so both cups share `aggregateBoxScores`/`lineFromBoxScores` rather than growing a second copy. `freeAgentCull` scrubs both shapes; `migrate.ts` backfills `[]` and deliberately **does not** build a cup mid-season (half its matchdays are already gone) — an existing save gets one at its next offseason.
- **The Ballon d'Or pays for winning it — as a TEAM bonus only (`WORLD_AWARD_DOMESTIC_CUP_BONUS` 0.25, pro-rated over `WORLD_AWARD_DOMESTIC_CUP_FULL_INVOLVEMENT` 4 ties).** Added because the award already paid `WORLD_AWARD_LEAGUE_TITLE_BONUS`, so a double-winner was credited for one trophy and not the other; 0.25 ≈ 3 striker goals against a title's ~10, the intended hierarchy (World Cup > Continental > league > domestic cup). **No domestic cup goals/assists/ratings enter the award, and that is the load-bearing part**: those ratings z-normalize within one country, so they carry exactly the weak-league bias `leagueStrengthOffsets` exists to remove, and no correction is available for them (the Continental Cup escapes this only because `cupMatchData` pools its whole field). A uniform squad bonus has no such bias — it can move the award *between* clubs but never lift a player above a better team-mate, the same property that made raising the other team bonuses safe. `BallonDOrEntry.domesticCup` is **optional** so every persisted pre-feature entry still typechecks and reads as 0; `WorldAwardContext.domesticCups` likewise, so `migrate.ts`'s backfill scores old seasons exactly as before rather than re-ranking them on a trophy nobody played for. Second-tier winners count (unlike a tier-2 league title, which `championTidByCompId` excludes). **Measured** (`worldAwardsAudit.ts`, 3 seeds × 12 seasons, against the same script with the term removed — world awards feed nothing in the sim, so both runs play identical dynasties and only the ranking can move): winner's median world-ovr rank **69 → 68**, ST share **69% → 69%**, league-title rate **72% → 72%**, Continental-win rate 28% → 25%, mean score split league 12.45 / cup 0.95 / title 0.55 / intl 0.55 / **dcup 0.04**. It is a **tie-breaker-scale** term by design and flipped one or two winners in 36 seasons; the guarded metrics held. The audit now reports a `dcup` column and a "won domestic cup" rate — note that rate reads 0 on any build without the term, since it keys off the optional field, so it is not a before/after comparison on its own.
- **Treble** = tier-1 title + Continental Cup + domestic cup in one season, derived in `clubHistory.ts` (`ClubSeasonRecord.treble`, `ClubHistory.trebles`). Domestic titles also feed the Frivolities trophy cabinet, both GOAT boards (`GOAT_DOMESTIC_CUP_TITLE_WEIGHT` 6 / `GOAT_TEAM_DOMESTIC_CUP_TITLE_WEIGHT` 40 — deliberately the cheapest trophy: six games can win it), and **`playerHonors.ts` now credits cup wins at all**, which it never did — `computePlayerHonors`/`computeArchivedHonors` take an optional `HonorCups` and return `continentalCups`/`domesticCups` alongside `leagueTitles`, so the Continental Cup gained a profile pill in the same change.
- UI: `/domestic-cup` (country + season dropdowns, rounds as columns), a Domestic Cup stats tab on Player Profile, Schedule rows (`kind: "domestic"`), a Dashboard final warning, and the sim ticker — which needed `MatchdayProgress` to gain a `domesticTies: DomesticTieResult[]` argument (through the worker protocol), because a `CupTie` carries only a round *index* and the ticker had "Continental Cup" hardcoded.

**International football** (`core/international/`) — national teams, played entirely inside the offseason
- **Four-year cycle, watch-only** (`INTL_CYCLE_YEARS`=4, `qualifyingLeg`/`isTournamentSeason`). Keyed off `season % 4`: seasons 1/2/3 of a cycle each play one qualifying leg, season 4 (`% 4 == 0`) plays the `INTL_FIELD_SIZE` (**32**) team `World Cup` (8 groups of 4 → `INTL_KO_SIZE` (16) bracket, R16→QF→SF→Final reusing the Continental Cup's `seedOrder`/`resolveCupTie`). **Qualifying is ONE campaign drawn once (at the cycle's first qualifying offseason, `qualifyingLeg==0`) and played a leg at a time across the three offseasons** — the campaign persists on `LeagueStore.international.qualifying`, accumulating results, and its 32 qualifiers are computed (`computeQualified`) only when the third leg completes; the tournament offseason then draws the World Cup from them. Each leg is seeded independently off the campaign's start season + leg index (`playQualifyingRound`), so leg-by-leg play is deterministic. Squad pids are filtered to living players each leg (a 3-season campaign outlives some players named at draw — `leagueMatchData` would deref a retired pid otherwise). No user management of any nation — squads auto-pick (`selectSquad`: best 23, ≤3 GKs, fit players before injured; `chooseBestFormation`). `LeagueStore.international` (`{qualifying, tournament, history, qualifyingHistory, powerRankings, stage, stageInjuries}`).
- **The field is 32, and the binding constraint is nationality depth, not club count (2026-08-23, user call).** Raised from 16 once the world reached 16 competitions. Measured on a fresh 320-club world, stable across 3 seeds: 78 nationalities present, **44** clear `INTL_MIN_POOL`, and squad rating runs ~76 at #1, ~70 at #16, **~64 at #32**, then falls off a cliff to ~56 by #40 — so 32 is near the largest field this world fills with nations worth watching, and 40 would be padded. **The accepted cost is that qualifying means much less:** at 16 places, 28 of the 44 could miss out; at 32, only **12** can, and all of them are European or African. A confederation with no more nations than places plays *no qualifying matches at all* (`initQualifying` skips it), so South America (4 eligible), Asia (1) and North America (1) now qualify their whole membership — Asia and NA already did at 16. **Do not try to widen the field by lowering `INTL_MIN_POOL`**: dropping it to 15 adds ~5 nations (Mexico 16, Gambia 16, Kenya 15, Albania 15) that all rate below 56. The only real fix for the qualifying stakes is more league countries feeding deeper nationality pools.
- **`seedBracket` splits the draw into halves, and that was a real bug fix, not tidying (2026-08-23).** It used to emit each partner pair's two ties *adjacently* (`W(a) v R(b)`, `W(b) v R(a)`, then the next pair), which puts them together in the **next** round — so a group's two qualifiers met in the semi-final of a four-group tournament, and would have met in the quarter-final of an eight-group one, contradicting the function's own docstring. Mirror ties now go into a second accumulator appended after the first, which is also how a real bracket is laid out. **It changes results for existing four-group tournaments too** (the World Cup's old shape and the confederation cups' largest) — harmless because international matches take no draw from the shared `rng`, so no club result moves. Pinned by a test that asserts group-mates land in opposite halves at 2/4/8 groups.
- **The knockout is ONE repeating `"knockout"` stage, not one stage per round.** `IntlStage`'s `"qf" | "sf" | "final"` collapsed into it when the bracket gained a round, because bracket depth is a function of the field (4 rounds at 32, 3 at 16, and a small confederation cup's can be a single final) and hard-coding it means a new stage every time the field moves. `roundsRemaining` (`tournament.ts`, shared with the confederation cups for the same reason) reads the depth off the fixtures, and that is what names the round in the Dashboard button/headline and in Schedule's round picker — **never the stage name and never `KO_ROUND_NAMES` indexed directly**, or an old save's quarter-finals get labelled "Round of 16". `migrate.ts`'s `migrateIntlStage` maps the three old values onto it; an in-progress bracket therefore finishes at whatever size it was drawn.

- **Played in stages the user clicks through, *before* the offseason advances (`core/international/staging.ts`).** The campaign is *drawn* the instant the club season ends (in `simThrough`, at the offseason transition — `initInternationalCampaign` names squads + draws groups/bracket, fixtures unplayed) and then *played* one stage at a time (`playIntlStage`): a qualifying offseason plays this cycle's one qualifying leg; a tournament offseason is group stage → QF → SF → Final. (A qualifying campaign is drawn only in the cycle's *first* qualifying offseason; the next two resume the in-progress campaign for their leg — see the four-year-cycle bullet above.) `InternationalState.stage` (`"qualifying"|"groups"|"qf"|"sf"|"final"|"done"|null`) tracks progress; the Dashboard's "Advance" button is replaced by the stage buttons (`isIntlStagePending`) until it reaches `"done"`. `simThroughInternational` plays every remaining stage at once (the "sim through" button, and the headless-test path). **The gate is presentational, not structural** — `simOffseason` *opens* by calling `simThroughInternational`, so it always completes a campaign the user left unplayed. That's what the Dashboard's **"Skip qualifying"/"Skip the World Cup"** button relies on: it just routes to `/set-scouting` (the normal advance), plays nothing itself, and lands identical results because the stages own their seeds (equivalence test in `international.test.ts`). **Each stage owns its seed** (`GROUP_STREAM`, `KNOCKOUT_STREAM + round`), so click-through == one-pass == old bulk result — `runQualifying`/`runTournament` are thin composers over the very same stage functions (equivalence test in `international.test.ts`). Init is player-free and shared-rng-free; every match runs on its own `hashInts` stream (`QUALIFYING/GROUP/KNOCKOUT/DRAW_STREAM` tags), **never the shared `rng`**, so club results stay bit-identical (`touchStats` hash + `simThrough` gate unchanged).
- **Now runs entirely *before* `simOffseason`, so retirement falls *after* the tournament** — a player about to retire gets one last campaign, and (as before) one injured in May still misses it, because squads read end-of-season ratings/injuries. Caps/goals/assists are credited per stage (additive `CareerDelta`); the one-off `tournaments`/`titles` counters and the `history` summary land at the Final. `simOffseason`'s old step 1.7 is gone.
- **A nation = a synthetic club.** `nationMatchData` builds `LeagueTeam`s keyed by `nid` (index into the campaign's `squads`, stands in for `tid`) and pools the whole field into **one** `leagueMatchData` normalization baseline — mandatory, exactly like `cupMatchData`, or z-norm flattens every nation to parity. `simMatchDetailed` runs unmodified.
- **Eligibility + fieldability.** A nation enters if pool ≥ `INTL_MIN_POOL` (18) with ≥ `INTL_MIN_KEEPERS` (1) GK **and** has a confederation (`confederationOf`). The GK floor is a *correctness* requirement: `selectXI` fills a GK slot with an outfielder when none exists, corrupting the keeping composite. **44 of the 78 nationalities present clear the bar on a fresh 320-club world** — measured, identical on 3 seeds (`scripts/intlFieldProbe.ts`).
- **Confederations + slot allocation** (`confederations.ts`) — `CONFEDERATION_OF` maps every name-pool nation to one of 6 confederations (test-guarded: `international.test.ts` asserts no nation is missing). `allocateSlots` distributes the 16 places by largest-remainder **weighted by each confederation's count of *contender* nations** (the global strongest 16), floor 1, capped at nation count. Weighting by raw nation *count* was measurably wrong — Africa's 8 nations matched Europe's 24 for places while Europe held every strong side, filling the field with makeweights.
- **Qualifying is a three-leg round-robin** (`INTL_QUAL_LEGS`=3, `roundRobin(nids, legs)`), **one leg per qualifying offseason** — each fixture is tagged with its `leg` (0/1/2) at draw time (`IntlGroupMatch.leg`, optional for legacy saves → treated as 0), and `playQualifyingRound` plays the next unplayed leg via `playGroups(..., onlyLeg)`. A single round-robin left strong nations missing out on variance; three legs across three offseasons make a long, low-variance campaign that reads like real World Cup qualifying. Tournament groups stay single-leg (variance is the point). Serpentine group draw for qualifying (`serpentineGroups`), pot draw for the tournament (`potDraw`). `fillPlaces` walks group finishing positions (winners, then best runners-up via per-game-rate `rankAcrossGroups` since group sizes differ) so a confederation always fills its allocation.
- **Career record + injury carry-over; no rating/finance impact.** `Player.intl` (`IntlCareer`: caps/goals/assists/tournaments/titles, in `international/career.ts` to avoid an import cycle with `players/types.ts`) accumulated at sim time (`CareerDelta`), surfaced on Player Profile. **Nothing feeds progression or valuation** — cannot disturb the rating equilibrium. **Injuries do carry into the new club season** (`stageInjuries`, `collectInjured`, `carryIntlInjuries`): a knock in an international match sidelines the player for the opening weeks of the club season. Collected *post-hoc* from box-score injury events (never stamped mid-campaign → international match XIs/results are unchanged), held on `InternationalState.stageInjuries`, applied in `simOffseason` (step 3.05) **after** progression heals the club-season knocks, rolled on a dedicated seeded stream (`INTL_INJURY_STREAM`, never the shared `rng`). The rolled duration is reduced by `INTL_INJURY_OFFSEASON_RECOVERY` (2) — the summer break serves part of the recovery, so a short knock heals before kickoff and only a more serious injury carries, at a shortened spell. Note this is the *one* intended club-side effect: it changes club availability the following season, so multi-season league results after an international campaign are no longer bit-identical to a pre-feature baseline (single-season `touchStats` hash is untouched — `simSeason` never crosses an offseason). **Fatigue and value/hype bumps remain deferred** (would touch the equilibrium; need their own audit). Migrated: new arrays/`stageInjuries` backfill to empty, `Player.intl` absent = never capped.
- **"Light" archival + the National Teams section.** Only the *current* qualifying campaign and tournament are held in full; past editions collapse to compact self-contained summaries — **results, not box scores.** `IntlTournamentSummary` now carries final group tables (`IntlGroupTable`, nation-keyed via `groupTableSummary`) + every knockout scoreline (`IntlKnockoutResult`); `IntlQualifyingSummary` carries the qualifying group tables + qualifiers; both drop per-match box scores and squad lists (career totals on `Player.intl` are the lasting per-player record). `InternationalState` gains `qualifyingHistory`, `powerRankings` (an `IntlPowerSnapshot` — every eligible nation ranked by squad rating, taken each time a campaign is drawn in `initInternationalCampaign`), plus the existing tournament `history`. Archival happens at sim time: qualifying summary appended when qualifying finishes, tournament summary at the Final. Per-nation records (titles/finals/best-finish) are **derived**, not stored (`nationHistory.ts` `nationRecords`/`finishOf`). Old saves backfill the new arrays to empty and fill going forward (migrate.ts). UI: the **`/national-teams/*`** section (sidebar group, ordered *after* Team; `ui/pages/nationalTeams/`) — World Cup, Qualifying, **Rosters**, Schedule, Power Rankings, Stat Leaders (national teams + players filterable by country, off `Player.intl`), History. Navigation is sidebar-only (the pages carry no tab strip of their own). The old single `/international` page is gone (redirects to `/national-teams/world-cup`).
- **Rosters tab + per-campaign player record.** `Rosters.tsx` renders the live campaign's `NationSquad[]` — nation list sorted by squad rating, selected squad sorted by `sortByPosThenOvr` with the projected XI (`selectXI` off the squad's own formation) shaded. Squad pids missing from `league.players` are dropped, matching what `playQualifyingRound` feeds the sim (a 3-offseason campaign outlives some named players). **`IntlCareer.seasons`** (`IntlSeasonLine[]`, `career.ts`) breaks caps/goals/assists out per offseason played, `kind: "qualifying" | "tournament"` — surfaced as the Player Profile's third stats tab. Written by `applyCareerDelta`, which therefore takes `season`/`kind`; `season` is **threaded in from the caller** (`playIntlStage`/`simThroughInternational` gained a param) rather than read off the campaign, because a qualifying campaign's own `season` is the cycle's *start*, not the offseason being played. The squads-only call at the Final passes an empty delta and must not stamp empty rows — `mergeSeasonLine` only runs for players with a delta entry. Old saves backfill `seasons: []` (irreconstructable — archived campaigns hold no box scores); career totals stay the authoritative record. "Which campaign is current" is one shared helper (`liveCampaign` in `nationalTeams/shared.tsx`), used by both Rosters and Schedule: pending stage first, else **the more recent of tournament/qualifying by `season`** — "tournament if there is one" was stale, since a newly drawn cycle's qualifying outranks the previous World Cup. **Render volume is the qualifying schedule's gotcha:** a campaign is ~280 fixtures (39 nations, 7 groups, `INTL_QUAL_LEGS` legs), so Schedule filters to one round at a time by default (`currentLegOf` mirrors `playQualifyingRound`'s next-leg rule; "All rounds" opts back in), and `NationName` passes `tip={false}` to `Flag` — the tooltip only repeats the adjacent name and costs an absolutely-positioned shadowed span per flag (1674 → 186 flag nodes on that page).

**Confederation cups** (`core/international/confederationCup.ts`, `format.ts`) — the Euro / Copa América / AFCON, played inside the offseason alongside a World Cup qualifying leg
- **Cadence is additive, not a restructure.** They run in the offseason of the cycle's *middle* qualifying season (`isConfederationCupSeason`, `CONFEDERATION_CUP_QUALIFYING_LEG` = 1, i.e. `season % 4 == 2`), which is the real Euro/Copa offset from a World Cup. That offseason plays its qualifying leg **and then** the championships. Replacing the leg instead was rejected: it would drop `INTL_QUAL_LEGS` 3 → 2 and reopen exactly the qualifying variance those three legs exist to damp.
- **No confederation cup qualifying.** A field is the confederation's strongest nations at draw time (`buildSquads` is already sorted). A second qualifying campaign per confederation would multiply the ~280-fixture campaign qualifying already runs.
- **The format scales with the field, and it has to** (`format.ts` `TOURNAMENT_FORMATS`/`formatFor`): 16 → 4 groups of 4, 12 → 4 of 3, 8 → 2 of 4, 6 → 2 of 3, ≤5 → **one round-robin whose top two contest a final** (which is how Copa América was really played until 1975, so it reads as a format rather than a fudge). Every shape ends in a power-of-two knockout. `seedBracket` therefore takes its group count from `groups.length` and a `qualifyPerGroup` param instead of `INTL_GROUPS`/`INTL_QUALIFY_PER_GROUP`; a single-group tournament returns `[winner, runnerUp]` since there is no partner group to cross with. World Cup output is byte-identical (defaults preserved).
- **Measured world support is the reason three of six ship dark.** Every player is generated from one of the eight European leagues' nationality tables, so non-European nations exist only as imports. On a fresh world (seed 1): Europe **25** eligible nations, Africa **12**, South America **5**, North America **1**, Asia **1**, Oceania **0** (`INTL_MIN_POOL` 18 + ≥1 GK). So the Euro, AFCON and a small Copa are held; the Asian Cup, Gold Cup and OFC Nations Cup are defined, gated on `CONTINENTAL_MIN_NATIONS` (4), and light up on their own if a world ever supports them. **Don't "fix" this by lowering `INTL_MIN_POOL`** — that changes who enters World Cup qualifying, hence the confederation allocation, hence existing saves' results; and a pool under ~14 can't field 11 fit players, which `selectXI` does not guard.
- **They are played side by side and aligned on their finals.** One `"confederation-groups"` stage plays every championship's groups; each `"confederation-ko"` stage plays a round only in the tournaments whose `roundsRemaining` equals the deepest still running, so a 1-round Copa idles through the Euro's QF and SF and every final lands on the same click. Click count therefore matches a World Cup's. That alignment is also what lets the archive/credit step assume **all champions are decided on the same stage** (`playIntlStage`'s `"confederation-ko"` case credits squads + titles and archives in one pass) — break the alignment and that assumption breaks with it.
- **Each tournament owns its rng streams**, keyed by `confederationIndex` (draw 900+i, groups 920+i, knockout 940+i*10, +round). Sharing one would make each championship's results depend on the order the others were played in. Nothing touches the shared `rng`, so club results stay bit-identical; `playTournamentGroups`/`playTournamentRound`/`playKnockoutRound` gained an options/`streamBase` param for this and default to the World Cup's tags.
- **`IntlCareer.confederationCups`/`confederationCupTitles` are separate counters, deliberately.** `tournaments`/`titles` have meant World Cups since they shipped and are already ranked on by Frivolities' International board and `goat.ts`; folding a second, easier trophy into them would silently restate every existing all-time record. `IntlSeasonLine.kind` gains `"confederation"` for the same reason — see the awards note below.
- **Ballon d'Or credit (2026-08-19, user call).** `WORLD_AWARD_INTL_CONTINENTAL_MULTIPLIER` (1.5, between qualifying's 1 and a World Cup's 2) and `WORLD_AWARD_CONTINENTAL_BONUS` (0.7, half `WORLD_AWARD_WORLD_CUP_BONUS`) feed the existing **international** component rather than a new one. Sized on the same `POTY_GOAL_WEIGHT.FWD` exchange rate as the rest of the team-achievement block: ≈9 goals — second-smallest of the five, above only the domestic cup's ≈3 — because a confederation cup field is a *subset* of the world and its winner is already being paid for that summer's qualifying caps. Applied uniformly whatever the field size — scaling by entrants would punish a Copa winner twice. Re-run `scripts/worldAwardsAudit.ts` (winner's world-ovr rank) before touching either; the whole block trades against that rank and raising these alongside the others cancels.
- **Bug this exposed, and it was latent rather than new:** `intlComponent` read `seasons.find(l => l.season === season)` — the *first* line for a season. A confederation cup offseason gives a player **two** (its qualifying leg and the championship), so one would have been silently dropped. It now sums every line for the season. Pinned by a test.
- **State + UI.** `InternationalState.confederationCups: IntlConfederationCup[]` (live, replaced only when a new edition is drawn, so the last one stays browsable) and `confederationCupHistory: IntlTournamentSummary[]` (same Light summary a World Cup collapses to, plus `confederation`). Kept out of `history`/`nationHistory` so the World Cup record keeps meaning what it did. New `/national-teams/confederation-cups` page shows every championship of one summer on one page; `KnockoutColumns` takes `totalRounds` so a 2-round bracket's round 0 reads "Semi-finals", not "Quarter-finals"; `liveCampaign` treats a confederation cup stage as *not* a World Cup stage (it runs in a qualifying offseason, so Rosters/Schedule should keep showing the live qualifying campaign). Migrated to `[]`/0 — past seasons played none, so the blank is exact rather than a guess.
- **Watch on any future change:** save size (three more live tournaments hold box scores until the next edition) and injury load (that offseason now plays a leg *and* a tournament, so more knocks carry into the club season via `stageInjuries`).

**Loans** (`core/loans.ts`)
- Fixed 1-3 season move to another roster; flat non-negotiable fee (`computeLoanFee`) + wage handoff (wages key off roster membership, so moving the pid *is* the mechanism). User lists via `/loans` (Accept/Reject only). AI↔AI loans (`runAILoanMarket`) restricted to age ≤ `LOAN_AI_MAX_AGE` (23) and **players outside their club's starting XI** (only buried youngsters). `processLoanReturns` runs early in `simOffseason`. State: `LeagueStore.activeLoans`/`loanListings`/`loanRejections`. No loan-in browsing UI, no early recall (disclosed scope cuts).
- **The Division-2 prevention guard was missing here until 2026-08-13, and was the *only* remaining way to breach the ceiling.** The buy paths (`transferMarket.ts`, `inboundOffers.ts`) both refuse to put an `ovr >= DIVISION_2_REFUSAL_OVR_THRESHOLD` player at a tier-2 club; `runAILoanMarket` never imported the constant. The function's own doc comment argued the restriction to buried under-24s made it impossible — "a 75+ prospect is starting somewhere" — but **the threshold is 70, not 75**, and a 70-73 under-24 outside a strong club's XI is ordinary. Measured (`scripts/loanCeilingProbe.ts`, 12 seasons, `userTid` excluded): **16 breaches, and 100% of every over-threshold tier-2 resident**, i.e. owned players never breach and this was the whole leak. **It is the worst place to have a hole**, because `enforceDivision2Ceiling` cannot clean it — the sweep deliberately skips loaned pids (moving one leaves `processLoanReturns` handing a copy back to the parent, putting one pid on two rosters) and won't release a loaned-in player to make room — so each breach sits for the loan's full 1-3 seasons. Guard added in the buyer loop **after the jitter draw** (same RNG-stream-order rule as the market's identical guard); breaches → **0 in all 12 seasons**, loan volume unchanged (~630/season). Two general lessons, both cheap to repeat: **a doc comment asserting a guard is unnecessary is not a measurement** (this one and `LOAN_AVAILABILITY`'s were both wrong in the same file), and **when a mechanic's cleanup pass is forbidden to touch a category of state, prevention is the only option for that category.**
- **`LOAN_AVAILABILITY` is gone (2026-08-13) and the loan market was nearly a dead mechanic without knowing it.** The screen skipped any player whose keep-value to his parent exceeded 0.95 × his market value — the same club-relative-vs-club-blind category error that `AI_MARKET_AVAILABILITY` made, kept deliberately when that one was deleted so as not to move two markets at once, with a comment conceding its justification was "reasoning, not a measurement". Measured, it was binding: it excluded **~71% of clubs' best loan-eligible players** (`scripts/loanAvailabilityProbe.ts`, median keep/market 1.30). **Volume is the wrong metric here and this is the durable lesson: the loan market is cap-bound (`AI_LOAN_MAX_MOVES`), not screen-bound**, so removing a filter that excluded 71% of *candidates* left executed loans flat at ~635/season — it changes *which* players move, not how many. On quality (`scripts/loanCeilingProbe.ts`, 12 seasons): loans involving an ovr-65+ player went **4.3 → 29.7 per season (6.9×)**, mean loaned ovr 38.8 → 41.1. Four useful loans a season across 320 clubs meant the screen was filtering out exactly the rated prospects a loan exists to serve, leaving only players nobody wanted. Protection is by price alone now (`LOAN_MIN_SURPLUS`: the borrower must value him above his parent's reservation). **The risk this created is on the wage channel, not the receipts one** — wages key off roster membership, so a loan moves salary to the borrower, and 6.9× more well-paid players moving redistributes materially more wage bill toward the (often weaker) borrowing clubs; that is what the ladder/solvency audit gates, not the transfer-receipts table.

- **Contract expiry and loans collided, and the offseason order is now load-bearing (2026-08-18).** A loan deliberately leaves the contract alone — it travels with the player and comes home with him — so nothing reconciled the two, and `releaseExpiredContracts` (step 1) ran *before* `processLoanReturns` (step 1.5). A loaned player sits on the **loanee's** roster, so expiry dropped him *there*: he ended up on no roster at all while `freeAgentPids` still counted him as rostered (he was on loan), i.e. unplayable, unsignable and invisible, and was then handed back to his parent carrying an already-dead contract. `runAILoanMarket` screened on age and "outside the XI" but **not on contract status**, so it could loan him straight back out and restart the loop. Measured across six real player saves (`docs/player-save-findings.md` #2): **71-281 stale contracts each, 100% of them loan returns**, worst six seasons past expiry; ages 19-24, median ovr 38 — exactly the loaned-out population. Knock-ons were all downstream of the dead contract: `departsAtRollover` true forever so the market would never buy him, `trueTransferValue` pinned at the minimum contract multiplier, a permanent "Final year" badge. **No money hole** — wages charge off roster membership, so this never touched finance, which is why nothing caught it. Fixed as all three of the shapes the findings doc listed, because each closes a different half: **(1)** returns run **before** expiry, so he lands home first and his contract is settled there — released into free agency in the same rollover, in time for step 4 to sign him; **(2)** expiry **skips pids still out on loan** (`onLoanPids`), or a multi-season loan strands him again; **(3)** a loan whose player's contract has expired is **terminated at step 1.25** rather than run on, so he can't sit out the rest of it on a dead deal — only reachable on saves predating (4). **(4)** `maxLoanSeasons`/`loanOutlivesContract` cap a new loan at the seasons his deal covers (the Loans page's duration picker offers no more, `listPlayerForLoan` and `loanOfferCandidates` refuse the rest, and `runAILoanMarket` skips an expired contract — inert going forward since AI loans are 1 season, and it is what repairs an old save's loop). **Renewals now follow ownership, not roster membership** (`runAIContractRenewals` takes `activeLoans`): the club **borrowing** a player used to be the one deciding his contract, which is what rescued the other ~73% of loan returns and hid the bug's true size, while his actual owner — who cannot see him on any roster — had no way to renew him at all. The user is affected identically and had it worst (his club is skipped by AI renewals entirely, so *nothing* could rescue his loaned-out player), hence the **Extend control on the Loans page's "Players Out on Loan" list** — the only surface where he appears, since a loaned-out player is not on the Roster page. `extendContractAction` resolves the **parent** club for `wouldRefuseExtension`, not whichever roster holds the pid. **This reorders the offseason, so it is rng-load-bearing** — a player released or not released shifts every downstream draw; the dynasty is re-baselined and single-season metric moves are noise until re-measured over ≥15 seasons. Verify with `scripts/loanContractProbe.ts` (stale + limbo counts per season, exits non-zero if either is ever above 0); `scripts/playerSaveAudit.ts` reports the same thing on a real save.

**Scouting fog-of-war on potential** (`core/scouting/potentialFog.ts`)
- Fogs **POT only** (OVR/attributes stay exact) as a low-high range, narrowed by scouting spend + ownership tenure, clearing to exact over ~2-3 seasons. `StoredTeam.scoutingObserved` (pid→first-seen season, user only, reconciled at league creation + each offseason). `<PotDisplay>` replaces every raw potential render; AI clubs unaffected (they have their own `perceivedValueToClub` noise). Team-level aggregates stay exact.
- **Scouting spend is locked per season** — `StoredTeam.nextScoutingSpend` (editable only in offseason) becomes the committed `scoutingSpend` at rollover, closing a peek-then-lower exploit.

**Career charts** (`ui/components/ValueHistoryChart.tsx`, `OvrHistoryChart.tsx`, shared `chartColors.ts`)
- **Transfer-value chart** on the **active** Player Profile (2026-08-12, replaced the OVR chart there): value on y, season on x, area colored by the club that season, crests at transfers, hover card with value / age / OVR / fogged POT / G-A / appearances / avg match rating / club. A **Value/OVR pill toggle** (`careerChart` state) swaps the same panel to `OvrHistoryChart` — kept because the two genuinely diverge (a veteran's rating holds flat while the age curve guts his value). **Retired** profiles get `OvrHistoryChart` alone (a retiree has no market value, and `ArchivedPlayer` carries no potential or contract to price one from).
- Crest tooltips on **both** charts go through `transferFeeLabel` — a bare `fee > 0` test rendered a loan and a loan return as "(free)", i.e. exactly the confusion that helper exists to prevent (pre-existing bug, fixed 2026-08-12).
- **Derived, not stored** (`core/finance/valueHistory.ts` `careerValueHistory`) — replays `trueTransferValue` over `player.hist`, so no schema change and existing saves chart their whole past immediately.
- **Season offset is load-bearing.** A `RatingsSnapshot` is stamped at the *end* of a season, so the one labelled N is what he carried through **N+1** — the same convention `awards.ts`'s `ovrDuringSeason` reads and `archive.ts` already bakes into `ArchivedSeason`. Points plot at `snap.season + 1`, which is also what makes the final point exactly his value today. The Profile's OVR/POT/attribute *table* deliberately keeps labelling rows by the stamp season (its footnote says so), so table and chart legitimately differ by one label.
- **`RatingsSnapshot.academy` does NOT take that offset** — progression reads it for the season that just *ended*, so it describes season N while the ratings beside it describe N+1. Shifting it would label a promoted youngster's first senior year "(Academy)". `careerValueHistory` therefore drops it; `PlayerProfile` resolves it per played season (`academyBySeason`, falling back to live squad membership for the current season, which has no snapshot yet). Caught in runtime verification, pinned by a test.
- **Contract term is held flat** at the player's *present* years-remaining for every point — old contract lengths aren't stored, so this keeps the curve a read on ability/age/potential (one constant multiplier) instead of distorting it with a guess.
- **POT goes through the scouting fog before pricing** (`pricedPotential` in `PlayerProfile`), or the dollar figure becomes an exact read on a hidden number (`trueTransferValue` pays a potential-gap premium). The fog band is taken once at `league.season` so its seeded jitter is one constant and the line stays smooth; the hover card still quotes each season's *own* band, matching the table.
- **One real point per season, drawn as a curve.** Ratings only move in the offseason, so there is no intra-season measurement — the line is a Fritsch–Carlson monotone cubic (no overshoot, can't draw a value he never had or dip below zero) sampled `SAMPLES_PER_SEASON` times and split into club-colored runs by nearest season. Hover always snaps to a season. y-axis is zero-based (money).

**Retirement** (`retirementProbability`/`isWantedForRetirement`, `players/progression.ts`; offseason step 3)
- **Age sets the curve's shape, last season's roster status sets its scale** (2026-07-28 rework; was age-only, identical odds for a 33-year-old star and a 33-year-old benchwarmer). Rostered → age curve × `RETIREMENT_ROSTERED_DAMPING` (damped, never zeroed: age still dominates). Unrostered → `RETIREMENT_UNROSTERED_BASE` at *any* age plus the undamped curve, so unsigned players drift out instead of sitting in the pool from 16 until 33. **Exception:** under `RETIREMENT_PROSPECT_MAX_AGE` **and** potential > `RETIREMENT_PROSPECT_POT_THRESHOLD` falls back to the damped curve, so high-ceiling kids between clubs aren't washed out.
- **The exemption's age bound is load-bearing.** `estimatePotential` seeds its peak at current ovr and only raises it, so `potential >= ovr` always. Without an age gate the exemption catches *every* unrostered player above ovr 65 — a released 37-year-old included — and hands him the damped curve (0.318 at 37 vs 0.53 under the old age-only model), i.e. it would make good unsigned veterans retire ~40% *less* than before the rework, and leave the ovr-66+ slice of the pool as the one population nothing removes (the cull spares it too, on `FREE_AGENT_CULL_MAX_PEAK_OVR`). Caught in review; a test pins it.
- **Both exemption bounds are pinned to the pool cull's constants by reference, not copied** (`RETIREMENT_PROSPECT_POT_THRESHOLD` = `FREE_AGENT_CULL_MAX_POT`, `RETIREMENT_PROSPECT_MAX_AGE` = `FREE_AGENT_CULL_MIN_AGE`), so the pair can't drift apart on either shared axis. They are **not** fully complementary: the cull also spares career peak > `FREE_AGENT_CULL_MAX_PEAK_OVR`, which retirement ignores on purpose.
- **"Rostered" means *last season*, snapshotted before step 1**, because retirement is step 3, step 1 has already released every expired contract into the free pool, and AI free agency doesn't re-sign anyone until step 4 — a live read retires a crowd of players about to be picked back up. Uses `freeAgentPids`, so academy players and players out on loan count as rostered.
- **Known gap in that grace:** it covers contract expiry (step 1, before free agency at step 4) but *not* mid-offseason releases. `trimRosterSurplus` (step 6) and `enforceDivision2Ceiling`'s weakest-player release both run *after* step 4, and `runAIFreeAgency` is offseason-only, so a trimmed player's first free agency is the next offseason's step 4 — which falls after his step-3 retirement roll. He is rolled once without ever having been offered. Fixing it properly means reordering the offseason (RNG-order consequences), so it is documented rather than patched; empirically it costs nothing measurable (min AI roster size *improved* and D1 mean ovr held).
- **One `rng()` draw per player either way**, so the shared stream's draw *count* is unchanged (outcomes move, which is the point). Retirees are stripped from `academyRoster` as well as `roster` — defence-in-depth only, still unreachable, since `freeAgentPids` counts academy players as rostered and the damped curve is exactly 0 below `RETIREMENT_START_AGE`.
- **Retirement scrubs live references but keeps history.** Retirees are dropped from `activeLoans`, `negotiations`, `inboundOffers`, `loanListings`, `loanRejections` — state pointing at a player who no longer exists (an un-scrubbed `activeLoan` would have `processLoanReturns` hand a dead pid back to its parent and log a phantom transfer). `transfers`/`newsEvents`/cup box scores are deliberately **kept**: unlike a culled nobody, a retiree had a real career. **Pre-existing consequence, made more frequent by this change:** those rows render as "Player &lt;pid&gt;" once he's deleted, and `awardedPids` protection (which the cull honours) does not apply to retirement, so an award winner who retires can leave an honours-board slot resolving to `undefined`. Both predate this rework; the honest fix is a retired-player archive, which is a design call.
- **Retirees are snapshotted onto the season-history entry, because they're deleted** (`core/players/retirements.ts`, `SeasonHistoryEntry.retirements?: RetirementSummary`, rendered as the Season Preview's Retirements section). `summarizeRetirements` copies name/nationality/pos/age/ovr/last club/career line/caps — a *copy*, not a pid reference, since the pid resolves to nothing a moment later (the same reason his surviving transfer rows read "Player &lt;pid&gt;"). Three gotchas: **(a)** the last-club map (`tidLastSeason` in `offseason.ts`) is built from the **pre-step-1** rosters, alongside the `unrosteredLastSeason` snapshot and for the identical reason — a live read files a fifteen-year club legend whose contract just expired as a free agent on his way out. **(b)** `notable` is capped at `RETIREMENT_NOTABLE_LIMIT` (15) and this is a *save-size* cap as much as a DOM cap: the list is persisted per season and thousands of unsigned players now retire per offseason, so an uncapped list is the 88 MB save and the `/transfers` freeze at once. `total`/`rostered` carry the true numbers. The user's own retirees are never dropped (same guarantee `WINDOW_TRANSFER_LIMIT` makes about his own deals), but they still sort by ovr rather than being pinned top. **(c)** The field is **optional and deliberately never backfilled** — a season that ran before the record existed deleted its retirees without a trace, so `migrate.ts` leaves it absent and the page says so rather than inventing a list. Also: no `/player/<pid>` link on those rows, the profile would be empty.
- Audited with `scripts/retirementAudit.ts` (pool size, **min AI roster size** — the real safety metric, since retirement runs immediately before AI free agency draws from the pool — D1 mean ovr, squad age, count still active at 38+). Measured vs an origin/main baseline, same seed, at season 13: free-agent pool 5194-and-still-climbing → **2136 and plateaued** from season 9, players still active at 38+ 24 → **71**, min AI roster 18 → **22**, D1 mean ovr **55.6 → 55.7 (unchanged)**. **The prospect exemption is what holds that last number**: without it D1 mean fell to 52.4, because washing out young FAs starved AI free agency of the useful under-24s it fills holes with, leaving barbell squads of teenagers and veterans. Any future move on `RETIREMENT_UNROSTERED_BASE` or the exemption threshold must re-check D1 mean ovr against a baseline, not just pool size.

**Extremism** (occasional extreme outcomes without reopening inflation)
- **Generational talents** — `isGenerational(pid)` (`players/progression.ts`), ~1/2500 per pid, softer growth-damping + floored bias → a true 90+ legend ~once/30 seasons. **Deliberately unannounced and unbadged (2026-08-17, user call).** The arrival used to fire a `generationalTalent` News Feed event; that event type is **deleted**, and `migrate.ts` strips it from saves in progress (an append-only feed would otherwise keep leaking it forever). Two reasons, both worth keeping: (a) the trait is hidden by design and the only intended tell is a scout's unusually high `estimatePotential` ceiling, so announcing it handed the user a hidden number; (b) **the flag is read from a pid hash before ratings exist**, so it can land on a player who is structurally incapable of ever being good — a real user save had an announced "generational talent" at **OVR 9 / POT 51-55**. Note the perk that makes the name mean anything (relaxed damping) is **inert below `GROWTH_DAMPING_START` (65)**, so on a weak prospect only the floored bias applies and the flag is worth ~+25 potential, not the ~+80 it is worth to a healthy academy prospect (measured: broken kid POT 35→61, healthy kid 60-69→82-87). Don't re-add an announcement without gating it on the player actually having a ceiling.
- **Historic team seasons** — `core/teamSeasonForm.ts`, hidden ±season-long form swing (1.5% each way), applied to composites in `simThrough` (cup too). On-pitch only (no market side effects). Both derived from hashes (no shared-rng consumption). User's club eligible symmetrically.

**The `/transfers` freeze — root cause (2026-07-25)** — *the actual fix for "the transfers tab freezes and I can't open it".*
- **`WINDOW_TRANSFER_LIMIT` (50, `constants.ts`) caps the "Completed This Window" list**, which was uncapped. A 240-club world moves thousands of players per summer window; a real user save (season **5**, so this is not an aged-save problem) rendered **2056 `<li>` rows, 2066 flag `<img>`s, 10684 DOM elements and ~1 MB of SVG flag art**. After the cap: **603 elements, 60 flags, 17 SVGs**.
- **Why every profiling pass missed it:** the JS render of that page is **147ms** even at 2056 rows. The cost is entirely **layout, image decode and paint** — invisible to Node and to jsdom (neither lays out or paints). Measuring core functions, `renderToStaticMarkup` timings and client mounts all came back fast while the page was unusable. **When a page is slow but every JS measurement is fast, count DOM nodes and image bytes, not milliseconds.**
- **Flag SVGs are the multiplier**: `src/ui/assets/flags/` holds coats of arms up to **240 KB** (`bo`), 217 KB (`ec`), 153 KB (`es`), 143 KB (`mx`) — all rendered at **13px tall** by `<Flag>`. Any surface listing many players pays this. Keep per-page flag counts bounded; `scripts/flagWeightProbe.ts` weighs a list.
- The user's own deals are always shown; the remainder is the biggest-by-fee, with a count and a News Feed link. `test/ui/windowTransferCap.test.tsx` pins the row/element/flag ceilings.
- **`scripts/probeUserSave.ts`** times every Transfers derivation against a real exported save — the tool that finally located this. Point it at a `/leagues` → Export JSON.

**Split player storage — saves write only what changed (`src/db/`, 2026-08-10).** Plan and measurements: `docs/save-performance-plan.md`. **The reframe worth internalising: save *size* was never the real problem — single-record *atomicity* was.** Every prior fix here (the free-agent cull, `archiveCup`, `WINDOW_TRANSFER_LIMIT`, `RETIREE_ARCHIVE_LIMIT`) shrank the save, which only helped because we had made total size the thing touched on every action. BBGM's database is also large at 100 seasons; it stays fast by storing entities as separate records so cost tracks what changed. Shrinking buys a constant factor, splitting changes the exponent.
- **Schema v3 split `retiredPlayers` out too, and it is the same bug one field along (2026-08-22).** The split above stopped rewriting the *pool* on every mutation; the whole **non-player** record is still rewritten every time (`leagues.put({ ...rest })`), and the retiree archive was sitting in it. So the archive was re-serialised on every lineup change and signing. Measured at 2,204 bytes a row (`scripts/archiveWriteCost.ts`): **11ms per save at 2,000 rows, 46ms at 10,000, 91ms at 20,000**, before mobile's documented 5-10x — i.e. exactly the budget #210 existed to reclaim. **`RETIREE_ARCHIVE_LIMIT` was therefore bounding write latency, not disk**, which is why it could be raised **2,000 → 20,000** the moment the archive moved to its own `retirees` store (same out-of-line `[lid, pid]` key, same identity diff, same transaction). Sized against measurement, not a round number: `scripts/archiveGateProbe.ts` puts `isArchiveWorthy` at **~270 retirees/season at maturity** (5 in season 3, 184 by season 11 — careers must lengthen before anyone clears 200 appearances, so a short probe badly under-reads it), so 20,000 is ~75 mature seasons of full coverage against ~7 before, at 44 MB on disk. Three gotchas. **(a)** `loadLeague` splits a v1/v2 record lazily and keys off the field being **present**, not non-empty — an empty inline array must still count as unsplit, or a save with a legitimately empty archive rewrites itself on every load. **(b)** `remove` matters here in a way it rarely does for players, because the cap genuinely prunes rows. **(c) The `DB_VERSION` one-way door is now wider**: a v3 build opening the database locks every *older* build out of **all** saves (`VersionError`), so a deploy rollback is a total outage until you roll forward. Export JSON is the escape hatch.
- **Schema v2** (`database.ts`): a second store, `players`, one record per player keyed **out-of-line as `[lid, pid]`**. The compound key makes a league's pool a single range query (`IDBKeyRange.bound([lid], [lid, []])` — arrays sort after numbers, so `[lid, []]` is an upper bound), so **no index is needed**. `StoredLeague` = `LeagueStore` minus `players`, plus optional `players` (v1 records) and `writeSeq`.
- **`loadLeague` reassembles** the two halves into an ordinary `LeagueStore`, which is why `migrate.ts`, `exportImport.ts`, `src/worker/*` and every reader of `league.players` are **untouched**. Containment is what made this a one-file change.
- **The dirty set is a reference-identity diff**, valid only because the core is purely functional — it maps over players and passes unchanged ones through *by reference* (the sole `players.push` in the repo is a test fixture). **`test/db/playerIdentity.test.ts` is the gate, not a nicety**: if anything ever mutates a player in place, the diff calls it clean and the edit is silently never persisted — no type error, no crash, and nothing else in the suite would notice.
- **The last-written pool lives in the db layer**, keyed by lid, *not* in `LeagueContext` (the plan assumed the latter). No call site can forget it. Cross-tab staleness is caught by **`writeSeq`** on the league record: if disk doesn't match what we last wrote, the save degrades to a full rewrite rather than merging two states that never coexisted. `loadLeague` deliberately does *not* seed the cache — migration rebuilds player objects, so a loaded pool can't be assumed to match disk; first save of a session is therefore full.
- **One transaction over both stores is a correctness requirement**, not tidiness: `teams[].roster` holds pids, so a crash between the two writes leaves rosters pointing at players that don't exist.
- **Migration is lazy, in `loadLeague`, not in `upgrade()`** — testable, and a large save can't stall a versionchange transaction at startup. Interrupted = save left in its old shape, retried next load.
- **Lazy careers (`docs/lazy-career-plan.md`, 2026-08-24).** The splits above all fixed *write* cost and deliberately left `loadLeague` reassembling one ordinary `LeagueStore`; that containment is why the pool is still **fully resident**, which is the separate problem this plan attacks. Measured on the reported season-60 save: 275.8 MB of live JS objects (~1.52x its 181.6 MB serialized form), of which a player's identity is 4.5 MB across the whole world and his career records are **45.2 MB** — ten to one, worsening every season. Survey finding that makes it tractable: the hot pages (Roster, Dashboard, Leaders, awards) all do `p.stats.find(s => s.season === season)` — **one season, not a career**.
  - **`Player.career` is the whole trick, and it is what dissolved both open questions.** A `CareerSummary` (totals + best-single-season + a line per season) costs **13.5 MB against the 45.2 MB of per-season history it stands in for**, and *every* consumer that used to walk a career reads it instead: the all-time boards (so Frivolities loads nothing and no board loses a filter or a sort), `archivePlayer` and its worthiness gate, `playerGoalTotals`' milestone check, and the retiree farewell notice. The plan's fallback designs — pre-filter and load the top 500 for Frivolities, splice a retiree's final snapshot back on the main thread for the archive — turned out to be unnecessary and were never built. **Measure before designing here; both were sized by guess and both guesses were wrong by ~2x.**
  - **The contract: a stored summary covers seasons the player has FINISHED.** The one in progress is not in it, so a live number is the summary plus the current row — which is exactly what the resident window keeps. Folded once per offseason (in the progression map, step 2, which is *before* retirement at step 3, so a retiree's final season is already in it) rather than maintained per matchday, because one call site is testable and twenty are not.
  - **`peakOvr`/`peakOvrSeason` are authoritative once present, and that is an invariant with teeth.** `careerPeakOvr` and `peakOf` skip the history scan when the field is set, so anything building a `Player` with a `hist` must set it to match — `generatePlayer`, `createCustomPlayer` and the roster importer all do. A stale one makes a player read as worse than he ever was and the scan will *not* save you.
  - **Careers cross the worker as a window** (`detachCareer`, the last `POSITION_CHANGE_SEASONS` snapshots and 2 stats rows), sized from the code: the position-change spell walk reads the last `POSITION_CHANGE_SEASONS - 1` snapshots *with their full ratings*, and `ovrDuringSeason` wants the one stamped season − 1, a step further back once progression has appended. **Reading the constants cannot prove a window is wide enough** — running a season *and* an offseason on it and demanding the same league out can, and that gate caught two silent under-counts a narrower test would have missed (a 100-goal milestone firing twice, and a retiree's permanent farewell line).
  - **Cumulative worker payload on the real season-60 save, with the news and transfer detaches below: end of season 235.3 MB → 46.3 MB (80%), and flat across the season.**
  - **Still resident, still to do:** the main thread holds all 275.8 MB either way — everything above changes what *crosses*, not what is *held*. Making careers non-resident is the rename (`stats` → `recentStats`), which breaks all 113 call sites at compile time. That churn is the point: a truncated array read as a career returns a wrong number rather than an error, and in this branch alone that failure mode fired four times.
- **Splitting a store changes what "changed" means, and that nearly shipped a 2.2x regression (v4, phase 2).** Diffing by object identity is correct while both halves live in one record. Once they are apart it is not: a simmed matchday replaces `stats` on every player, so everyone arrives as a *new object* with identical ratings/contract/ovr, and the identity diff then rewrote ~11k rows byte-for-byte identical to disk **on top of** the career rows it genuinely had to write. Two puts per player instead of one: matchday save 622ms → **1459ms**. `rowsToWrite` now asks the halves separately — career by reference compare (`stats`/`hist` are never mutated in place), identity by *field* compare (sound for the same functional-core reason: nested values are replaced, not edited) — and most saves touch one or the other, never both. Back to ~660ms. **If you split another field off a record, re-ask what the diff is comparing.**
- **The one-way door is wider than it looks, and this was verified rather than assumed.** Once a `DB_VERSION` 2 build opens the database *once*, a version-1 build's `openDB` fails with **`VersionError`** — IDB refuses to open below the stored version. So an older build loses access to **every save in that browser profile, migrated or not**, not just the one that was upgraded. **Deploy rollback is therefore a total outage** for anyone who loaded the new build (no data loss — rolling forward restores it). Matters doubly here: two accounts share this repo, so whoever is on the older branch hits it too. Export JSON is the escape hatch.
- **Measured** (`scripts/savePerfProbe.ts`): single-player actions **1 dirty player, 0.01% of the save**; lineup/scouting/release write **zero** players. 8-season save: routine action **281ms → ~118ms** (3-season: 99 → 35). **Phase 1 alone was a regression** (99 → 335ms writing every row individually) — it must never ship without the dirty set. **Sims are barely helped** (a matchday dirties 8076 of 8076 by identity, 5992 genuinely) and their real cost is the worker `structuredClone`, which this doesn't touch.
- **Two live follow-ups.** (a) The remaining floor is the non-player fields, ~7.8 MB at 8 seasons and **almost all append-only** (`powerRankingHistory` 2.3, `transfers` 1.7, `newsEvents` 1.3, `seasonHistory` 0.7, `cupHistory` 0.6) — splitting those is the next win and is *easier* than this was. (b) **Making `simThrough`'s blanket player copy lazy was measured and rejected**: 26% ceiling on the one action users already accept as a pause, against touching the hot path in a repo with a history of RNG-order accidents. Don't revisit without new numbers.
- **Unverified in a real browser:** the save now reads and writes inside one IDB transaction, and `fake-indexeddb` is more forgiving about transaction auto-commit than Safari. Every await is on a request in that transaction, which should hold, but confirm by playing a save before trusting it.

**`league.played`'s box scores are the biggest single thing in a mid-season save, and half the cause of the reported crash (`detachPlayed`, `core/simArchive.ts`, 2026-08-24).** Measured on the **real reporter save** (`soccer-gm-league-4`, season 60, 59 completed seasons, the **shipped** 16-competition / 320-club world — not a custom one).
- **`played` is invisible to every save-size probe in this repo**, including `leagueSizeTiming.ts`, because it is wiped every offseason and rebuilt every season and they all sample *after* the offseason. It is driven by **world size × how far into the season you are**, not by season count. On the real save it is 60.5 MB at matchday 23 and ~99 MB at matchday 38 (6,080 league matches × ~16.4 KB a box score: 25 player lines ~6.6 KB, **181 events ~10.8 KB**).
- **Real-save totals, at end of season:** 221.7 MB, `structuredClone` **4788 ms** on a fast desktop. Composition at matchday 23: `played` 60.5 (33.3%), `players` 49.7 (27.3%), `powerRankingHistory` 18.9 (10.4%), `transfers` 14.8, `newsEvents` 11.6, `seasonHistory` 5.6, then the cup histories at 4-5 each.
- **A long-lived save does NOT match a simulated one of the same age, and this bit me.** A simulated 56-season world put `domesticCupHistory` at 42.9 MB and called it the dominant history; the real 60-season save has **4.3 MB**, because domestic cups only shipped recently and the save predates them. **Simulated projections over-weight every recently-added feature** — measure a real save before naming the biggest field.
- **Cumulative effect of everything in this change, on the real save: 221.7 MB → 99.3 MB (55%), clone 4788 ms → 1209 ms**, and the payload is **flat across the season** (~99 MB at matchdays 26/30/34/38) where it used to climb 189.8 → 221.7. What is left is dominated by `players` (49.7 MB), which must cross.
- **The sim does not read them.** `applyInjuries`, `applySuspensions` and `detectMatchdayNewsEvents` all take *the matchday's own* results, which the worker just generated; the markets, `computeStandings` and `computeTeamForm` read scores only. The **single** exception is `computeTeamSeasonStats` at `offseason.ts`, so `simOffseason` gained an **optional third param** for a precomputed aggregate — optional precisely because the function has ~60 call sites across tests and scripts and none of them should have to care.
- **`detachPlayed` swaps each box score for a `{home:[],away:[],events:[],stub:true}` marker.** Scores, possession and matchday survive because the sim genuinely reads those. `reattachPlayed` counts the **leading run of stubs** rather than matching positions: `simThrough` only appends and the offseason only clears, so the stubs come back as a prefix, and a result with no leading stub means the array was wiped and is the worker's own. **`jump` is deliberately exempt** (it crosses offseasons, so the leading-stub rule does not hold) — one slow deliberate action against every matchday advance.
- **Effect of `detachPlayed` alone**, measured on a 32-competition custom world: matchday 38 payload 216.1 MB → 27.4 MB. On the real shipped-world save it is the largest of the three held-back fields (~99 MB of the 122 MB held back at matchday 38).
- **Still open, and it is a product call:** this keeps box scores out of the worker but not out of IndexedDB, so on-disk size is unchanged. The lever if that matters is the **181 events per match (62% of a box score)** — thinning event timelines for matches that are not the user's would cut most of it, at the cost of the timeline on other clubs' old matches.

**The worker boundary is the other half of the save-size problem, and it is the one that CRASHES rather than freezes (`core/simArchive.ts`, 2026-08-24).** Splitting storage fixed what a *mutation* costs; it does nothing for what a *sim* costs, because `postMessage` structured-clones the whole `LeagueStore` to the worker and the whole result back. Reported as "my save is crashing at season 56 on mobile", and it is real: PostHog carries production `$exception` rows reading `DataCloneError: Failed to execute 'postMessage' on 'DedicatedWorkerGlobalScope': Data cannot be cloned, out of memory` — on **desktop**, on `/dashboard`. A phone tab that gets OOM-killed reports nothing at all, so absence of mobile events is not evidence against.
- **Measured, on the current 16-competition world** (probe shape in the commit; ~20s/season, so chunk it): a season-56 save is **165.6 MB** serialized and ~150 MB as live objects, and a sim round trip holds **≥4 copies ≈ 560 MB** before the sim's own working set, React and the DOM. Growth is ~2.2 MB/season and does **not** plateau: `players` flattens at ~46 MB by season 16, and everything after that is append-only history. Composition at s56: players 46.3, `domesticCupHistory` 42.9, `retiredPlayers` 22.4, `transfers` 14.5, `newsEvents` 12.3, `powerRankingHistory` 9.0, `seasonHistory` 5.9, `cupHistory` 4.3, `international`/`shieldHistory` 2.9 each. **Users really do go this deep** — the top saves have 326/199/118 offseasons, and mobile users reach 73.
- **`detachArchive`/`reattachArchive` hold back the history the sim writes but never reads.** Wired into `useSimWorker.ts`'s `post()`, which is the single choke point every command *and* every result passes through, so no call site can forget it (same containment argument as `loadLeague` and `CrestArtProvider`). The payload carries **empty arrays, not missing keys**, so the sim needs no branch and whatever comes back in those fields is exactly this run's delta — appending to `[]` yields the delta for free. Currently `powerRankingHistory` + `retiredPlayers`: **30.8 MB off each direction at s56 (19%), clone 1699ms → 1130ms.**
- **The invariant, and it is silent when broken:** a held-back field must be append-only across the *entire* worker-side call graph. A read sees `[]` — no type error, no crash, just wrong output. `test/core/simArchive.test.ts` is the gate, and it is an end-to-end deep-equality check (a detached offseason, and a detached season+offseason, must land on exactly the league an undetached run does), not a unit test of the split.
- **`detachNews` took the news feed and the three cup histories (~23 MB), and they needed more than an empty array.** They look append-only from outside, but two offseason steps genuinely read them: `cullFreeAgentPool` scrubs culled players' rows out of them, and `extendPlayerNames` walks the cup `statLines` to decide which of this offseason's retirees are still referenced. Each got its own answer — the culled pid set is **reported back** out of `simOffseason` and the main thread applies the identical scrub through the very same exported function (`scrubHistoryForCull`, so the two cannot drift), and the referenced set is **precomputed here and handed in**. Getting a value out of `simOffseason` went through a **reporting variant beside it** (`simOffseasonReporting`), **not** a changed return type, which has ~60 call sites across tests and scripts; `cullFreeAgentPoolReporting` is the same shape. **Do not "simplify" by dropping the scrub:** culled players' rows would survive and render as "Player 4821", the exact bug `playerNames` exists to fix.
  - **A precomputed `referencedPids` must be UNIONED with the live walk, never substituted for it** — this was got wrong first and the deep-equality gate did not catch it, because the fixture had no case. The caller measures the league *before* the offseason, and the offseason then adds references of its own: this season's cup is archived into `cupHistory` by the same run, so a one-club retiree whose only surviving mention is a cup line from his final season is referenced by the finished league and not by the one the caller measured — he would silently lose his name forever. The union cannot over-name: the extra pids it carries belong to players the cull has since deleted, and a retiree is never one of those (retirement is step 3, the cull is the last thing that happens).
- **`detachTransfers` is a WINDOW, not an empty array, and it is the only held-back field the sim genuinely reads.** 14.8 MB / 186k rows on the real save. The read is `joinedSeasons` feeding `settledMultiplier` in `runAITransferMarket`, and it has a horizon: `settledMultiplier` **returns 1 for a player who arrived `PLAYER_SETTLED_SEASONS` ago and 1 for a player with no record at all**, so a row older than that is not merely unlikely to matter, it is provably inert. The log is written in season order, so the window is a suffix and the retained rows are the prefix ahead of it — concatenating them back needs no merge. Cut at `season - PLAYER_SETTLED_SEASONS`: one season wider than the winter market needs, two wider than the summer one. Measured on the real save: **166,394 of 186,032 rows held back, 13.2 MB, and the end-of-season payload 59.5 → 46.3 MB.** The retained rows take the same `culledPids` scrub the news history does. `jump` is exempt with the rest — each of its offseasons culls and only the last one's pids come back. **If anything else ever reads the transfer log inside the sim this stops being safe**, and it fails as a plausible wrong answer ("he has always been here") rather than a crash.
- **`seasonHistory` (5.9 MB) is the one that can never move.** It is read for real sim decisions (`academyForm`, `protectedStars`) and, unlike the transfer log, nothing bounds how far back those look — so there is no window to cut and no answer to precompute.
- **`POWER_SNAPSHOT_INTERVAL` is a save-size constant, not a UI one** (5 → **10** in the same change, so four snapshots a season counting the finale). A snapshot is a row per club for the whole world and is never pruned, so the cadence is a permanent per-season tax; at 5 it reached 448 snapshots / 143,360 club-rows / 18.2 MB by season 56. Price any increase in MB per 50 seasons. Pure and rng-free, and nothing in the sim reads the history back, so scorelines are unaffected (`touchStats.test.ts` hash unchanged).

**Exported saves are compact JSON + gzip (`db/exportImport.ts`, 2026-08-15).** `Export Save` writes `soccer-gm-league-<lid>.json.gz`. Two independent wins, both lossless: dropping the `JSON.stringify(league, null, 2)` indentation is **half the file on its own** (nothing ever read the export as formatted text), and gzip takes the rest — measured 8 seasons **83.6 MB → 43.3 MB → 5.2 MB (16.2x)**, 3 seasons 42.4 → 2.76 MB (15.3x, `scripts/exportRoundTrip.ts`, which also asserts the decoded bytes are identical to what was encoded). **This is emphatically *not* open design decision 6** — no history is pruned, the round trip is byte-for-byte, and the in-browser IndexedDB save is untouched (this is the export *file* only, so it does nothing for clone/save latency). Three things to know: **(a)** `readLeagueFileText` is the **single reader** for every file the game accepts (`importLeagueJSON`, the Leagues import router, the NewLeague roster picker) and it **sniffs the gzip magic bytes `1f 8b` rather than the extension**, so back-compat with old `.json` exports and with never-compressed roster files is free and a renamed file still works. Add a reader without going through it and gzipped saves read as garbage on that surface alone. **(b)** `exportLeagueJSON` is now **async** (`CompressionStream` is a stream) — its two call sites await it. **(c)** Browsers can only *compress* gzip/deflate via `CompressionStream`; **brotli would be 4.66 MB but is decompress-only in browsers**, so don't reach for it. `scripts/probeUserSave.ts` reads user exports through the same helper, so it takes either form.

**Save size & the free-agent cull** (`core/players/freeAgentCull.ts`, 2026-07-25) — *the fix for the "transfers page freezes the whole game" reports; see resolved design decision 6 for the measurements.*
- **Two separate problems shared one symptom. The `/transfers` freeze is fixed by `WINDOW_TRANSFER_LIMIT` (below), NOT by the save-size work here** — that was a real but distinct problem, and attributing the freeze to it was wrong. That page's own *derivations* are flat ~40-100ms even on a 24-season save. The cost is **total save size**: every mutation writes the *whole* league to IndexedDB and every sim `structuredClone`s it to the worker, both on the main thread, both scaling with size. `/dashboard` was nearly as bad. Baseline at 14 seasons: **88 MB, clone 4230ms, save 2756ms** (superlinear; mobile is 5-10× slower, matching production INP p75 31.5s / worst 539s).
- **Two bloat sources, both now fixed.** (1) **`archiveCup`** (`core/cup/archive.ts`) folds a finished cup's box scores into one `CupPlayerLine` per player (`CupState.statLines`) and drops them, at the offseason archive point and in `migrate.ts` — **18 MB of an aged save down to 431 KB across 13 cups (~8×)**. Everything the UI draws is stored separately and survives (scorelines, aggregates, `legs`, winners, the LP table, the bracket); the box scores' only reader was `cupStatsForPlayer`, which now prefers `statLines` and falls back to summing box scores for the *live* cup. Verified on real simmed cups (`scripts/cupBoxScoreCheck.ts`): all three stages → 0 box scores, ~369 stat lines kept, scorelines/winners intact, idempotent. **`CupTie.boxScore` is now `BoxScore | null`** — note **international tournaments reuse `CupTie`**, so `simIntl.ts`/`tournament.ts` needed null guards. Every list read in the archive path is defaulted (`?? []`) because it runs inside `migrate` on every archived cup, where a throw would stop the save loading at all (verified: `cupStatsForPlayer` iterates only `cup.ties`; `Cup.tsx` has no `boxScore` reference, its table comes from `leaguePhaseTable`; `clubHistory` only keys cups by season). (2) `cullFreeAgentPool` deletes unsigned free agents who are `age ≥ FREE_AGENT_CULL_MIN_AGE` (24) **and** career-peak ovr ≤ 65 **and** potential ≤ 65. Result: **88 → 54.7 MB, clone 4230 → 370ms (11×), save 2756 → 736ms**, and the pool plateaus (~5.3k, increments decelerating) instead of growing forever.
- **Aggregating fixed a long-standing cup-stat under-count.** The cup's three stages live in three places (`leaguePhase.matches`, `playoff.ties`, top-level `ties`) and `cupStatsForPlayer` read **only the last**, so league-phase and playoff appearances never reached a profile: a club that played 6 group games and lost the playoff showed **0** cup appearances for every player, and even a quarter-finalist lost his group games. Measured on one real season: **1857 appearances played, 199 counted** (253 of 374 players showed nothing). `aggregateCupStats` now sums all stages, so cup appearances/goals jump for anyone who played group games — that's a correction, not inflation, and it's player-visible (Manual + Changelog both say so). `scripts/cupUndercountDemo.ts` reproduces the old behavior.
- **Retirement already deletes players outright** (offseason step 3), so a save holds **no retired players** — every off-roster player is an unsigned free agent, and nothing ever culled them (9245 unsigned vs 5996 rostered at 14 seasons, 96% never past ovr 55). Don't repeat the mistake of reading that bucket as "retired".
- **The age+potential gates are load-bearing, not caution.** A 17-year-old at ovr 45 with potential 80 has a career *peak* of 45, so culling on peak alone deletes the youth pipeline before the user sees it on `/incoming-talent`. Award winners are protected too (`awardedPids`), so no honours board can point at a deleted player.
- **`LeagueStore.nextPid` is a persisted monotonic pid allocator, and this is a correctness fix, not bookkeeping.** Pids used to be `max(players.pid) + 1` at each use (`offseason.ts`, `godMode.ts`), which silently reuses a pid whenever the highest-pid player is removed — and removal already happened via retirement. The reused pid then inherits that player's transfers/newsEvents/cup lines, since a pid is the only link. Backfilled as `max(pid)+1` so no save changes behavior on upgrade. Both call sites guard a missing cursor (`Number.isFinite`) because `Math.max(undefined, n)` is `NaN`, which would land straight in a player's pid — a test fixture casting `as LeagueStore` hit exactly this.
- **The cull necessarily shifts the RNG stream** (offseason step 2 progresses *every* player in the array with a draw each, so a shorter array = fewer draws = different downstream league). That's inherent to deleting players, not a slip, but it means the pre-cull dynasty baseline no longer applies. `scripts/cullDynastyAudit.ts` re-checks the invariants; **the only trustworthy way to read it is against the same script run on `main`** (copy it into a `git worktree add` of `origin/main`), because several metrics drift on main too. Measured 25 seasons, main → cull: inflation drift **+4.17 → +4.26** (seed 1), **+4.24 → +4.23** (seed 2); AI tier-2 players over the 70 ceiling **579 → 581** (seed 2); champion pts mean **83.8 → 84.1** / **85.3 → 87.0**; worst AI budget **+7.9M → −0.8M** (seed 1) but **+10.6M → +11.1M** (seed 2), so that lone small deficit is stream-shift noise, not a systematic effect. Free agents at season 25: **13961 (still climbing) → 5689 (plateaued)**; prospects **6157 → 5534**, so the pipeline is intact.
- **Two pre-existing findings this audit surfaced, neither caused by the cull** (both identical on main, both left alone): league-wide mean ovr drifts **~+4 over 25 seasons**, and `enforceDivision2Ceiling` leaks **~23 over-threshold AI tier-2 players per season**. If either matters, they're separate work. **The leak figure is stale and the leak is now closed (2026-08-13).** Re-measured over 12 seasons excluding `userTid` (`scripts/loanCeilingProbe.ts`) it was **0-3 per season**, not ~23 — it shrank with the 2026-08-08 market fix, which also cut the sweep's own workload 61→18 — and **100% of what remained arrived by loan**, through a missing tier-2 guard in `runAILoanMarket` (see the loans entry below). With that guard added the count is **0 in every season**: the sweep handles owned players exactly.
- **Exclude `userTid` from D2-ceiling metrics**: a relegated user squad keeps 70+ players in tier 2 by design (`enforceDivision2Ceiling` never sweeps it), which otherwise reads as a breach every single season. Comparing the best D2 player against the tier-1 *full-roster* mean (~57) is likewise a miscalibrated check — it "fails" on main too.
- **`awardedPids` protects honours-board pids, and getting this wrong is silent.** `SeasonAwards` stores **bare numbers** under `playerOfSeasonPid` / `goldenBootPid` / `teamOfSeason[]` — there is no `pid` key — so an earlier version that walked for objects with a `pid` property returned an **empty set for every save**, i.e. the protection did nothing and nothing failed. It now matches `*Pid` keys plus `teamOfSeason`, tolerates all three historical award container shapes (single / `[D1,D2]` tuple / `Record<compId,…>`), and covers `international.history[].topScorer.pid` (its `name` fallback saves the label but the profile *link* still uses the pid). Reachable, not theoretical: tier-2 squads are capped below `DIVISION_2_REFUSAL_OVR_THRESHOLD`, so a second-division Golden Boot / Team-of-the-Season pick can sit at peak ovr ≤ 65. **`scripts/freeAgentPoolAudit.ts` shared the same bug**, which is why it reported zero award references — don't read that as evidence.
- **The load-time cull is gated on pool size** (`cullOnLoad`, `FREE_AGENT_CULL_LOAD_THRESHOLD` 7000). Culling on *every* load makes mid-season deletion immediate — release a player by mistake, reload, and he's gone instead of re-signable from `/free-agents`. Only a genuinely bloated pool (the frozen-save case, 9245 in the save that prompted this; a maintained pool plateaus ~5.3k) is drained at load; everything else waits for the offseason cull.
- **`loadLeague` writes the shrunk record back** when migration removed players or collapsed a cup. Without it the on-disk save stays full size and every startup re-reads it and re-runs `aggregateCupStats` over every archived cup before first paint — the exact main-thread cost this set out to remove. The check is deliberately cheap (player count + `statLines` identity), since serializing twice to compare sizes is itself the cost being avoided.
- **There are THREE pid allocators, all now on the cursor:** `offseason.ts` (youth intake), `godMode.ts` (`createCustomPlayer`), and **`rosterImport.ts` (`applyRosterFile`)** — the last one was missed initially. It matters most there because **retirement deletes players without scrubbing** their transfers/newsEvents/cup lines, so a reissued pid inherits real history.
- Dangling references are scrubbed with the player (transfers, newsEvents, negotiations, inboundOffers, loan listings/rejections, `scoutingObserved`, **every cup stage's box-score lines and the archived `statLines`** — `scrubCupLines` covers `leaguePhase`/`playoff`/`playIn`/`ties`, not just `ties`, because `cupStatsForPlayer` reads them all, **and the live international campaign's `NationSquad.pids` + `stageInjuries`** — squad selection reads end-of-season club rosters and a weak nation can genuinely name a sub-65 player, so a culled player really can be sitting in one; archived campaigns already discard squads, and `IntlTournamentSummary.topScorer` carries a `name` fallback, so neither needs it) — not a crash if left (every reader guards the lookup) but it renders as "Player 4821" in history.

**God Mode** (`core/godMode.ts`) — per-save sandbox (`LeagueStore.godMode`). Guardrail-free editing (bypasses fees/budget/cap/depth-floor): move/release/edit/create players, set club finances; un-fogs potential everywhere. `detachPlayer` scrubs a pid from all rosters + transient state. `PlayerEditModal.tsx`, `/god-mode` hub. Scope-outs: no add/delete clubs, no hard-delete (release instead), no forcing match results.

## Open design decisions (need a user call before coding)

From the 2026-07-11 bug hunt; each has more than one reasonable fix — discuss options first:
1. **Winter-sale wage dodge** — season wages charged once at offseason settlement against the current holder, so selling a high earner in winter dodges his whole season bill. Pro-rate, charge-at-transfer, or accept+document.
2. **Deficit at the 30-man cap** — the "no club runs a deficit" tuning was only proven for the 25-man composition; a stacked full user squad with a low finish can go negative. Retune, cap scouting relative to wages, or allow user deficits + add debt UI.
4. **Mid-season transfer stat attribution** — `SeasonStats` is one running total; Leaders/Roster credit the whole line to the *current* club. Per-stint stats (schema change) or a "joined mid-season" UI marker.
6. ~~**Unbounded save size**~~ — **RESOLVED 2026-07-25, see "Save size & the free-agent cull" below.** ⚠️ Note the framing here is *wrong*: this was diagnosed as the cause of the `/transfers` freeze, and it is not. The freeze is an uncapped DOM list (see "The `/transfers` freeze — root cause"). Save size was a genuine, separate problem. Original measurement kept here because it's the reference baseline: **Unbounded save size — the real cause of the "transfers page freezes" reports (measured 2026-07-25).** The save grows without bound and **every mutation writes the whole object to IndexedDB** while **every sim `structuredClone`s it to the worker** — both block the main thread, both scale with total size, so the whole app freezes and it gets worse the longer you play. Measured on a fast desktop (`scripts/leagueSizeTiming.ts`): season 1 → 9 MB / clone 67ms / save 75ms; season 9 → 59 MB / 716ms / 542ms; season 14 → **88 MB / clone 4230ms / save 2756ms**, growing superlinearly. Mobile is 5-10× slower, matching production INP on `/transfers` (p50 6.3s, p75 **31.5s**, worst 539s) — and `/dashboard` is nearly as bad, because **it is not a transfers-specific bug at all**. Per-field at 14 seasons (`scripts/leagueSizeBreakdown.ts`, `scripts/leagueSizeDeepDive.ts`): `players` 56.2 MB (64%; `hist[]` **34.0 MB** / 127k rows, `stats[]` 16.0 MB), `cupHistory` **18.6 MB** (21%), `transfers` 5.2 MB, `powerRankingHistory` 4.0 MB, `newsEvents` 2.4 MB. Candidate savings: drop every off-roster player 24.7 MB (28%) · **strip `boxScore` from archived cups' `leaguePhase` matches 14.8 MB (17%)** · drop `hist[]` for off-roster players 17.5 MB (20%) · `powerRankingHistory` 4.0 MB · off-roster `stats[]` 3.3 MB. **The league-phase one is free of feature cost — verified nothing reads it:** `cupStatsForPlayer` (`core/cup/cupStats.ts`, the Player Profile Cup tab) iterates only `cup.ties`; `Cup.tsx` has no `boxScore` reference and builds the table via `leaguePhaseTable` from scores; `clubHistory.ts` only keys `cupHistory` by season. Everything else trades away real history (retired players' OVR chart / career stats), hence a user call. Any fix needs a `migrate.ts` change and **deletes data from existing saves**, so confirm before shipping.

7. ~~**Honours boards go blank as a dynasty ages**~~ — **RESOLVED 2026-08-21 to 08-23.** The call went to the *middle* option, a name table for award winners only: `core/awardWinners.ts` snapshots every award pid's name onto the season entry (see "Award winners carry their own names" above), the farewell lists are read back (#263), and `RETIREE_ARCHIVE_LIMIT` went **2,000 → 20,000** once the archive moved to its own store (#266), since the cap was bounding write latency rather than disk. Original measurement kept as the reference baseline: award slots resolving to nothing were **8.5% blank at season 10, 25% at 27, 54% at 47, 69% at 75**, alongside 20,855 distinct players rendering as `Player <pid>` on the season-75 save. **Still open, and still a user call:** the name table covers award winners only, so a rank-and-file player the archive drops can still print as `Player <pid>` on Transfers / News Feed / Club History. The measured "name table for everyone" option (~68 bytes a row, **1.42 MB** on the worst save) covers those too and was not taken.
